# Releases (maintainers)

How a release is built, checked, signed and published, and how the signing keys are kept.

A tag `vX.Y.Z` starts `.github/workflows/release.yml`: it builds Linux assets in the pinned Fedora 44 container and macOS
assets on a macOS runner (`build`, `build-macos`), joins the manifests (`manifest`, `scripts/release-merge.sh`), attests
every asset and creates a **draft** release. The workflow has no secrets and cannot sign or publish. The maintainer
checks the draft locally, signs `manifest.json` with minisign and publishes (`scripts/release-sign.sh`); `tona` trusts
that signature, the attestation is the second proof.

## Assets and install layout

Every file is its own asset; `manifest.json` maps each to its path and platform (`linux-x86_64-gfx1200`, `macos-arm64`,
`any`).

| Asset | Path in the manifest | Notes |
|---|---|---|
| `tona-server` | `bin/tona-server` | the server |
| `linux-x86_64-gfx1200-tona` | `bin/tona` | the one program of the user: setup, control centre, commands, agents, updater. The asset name is what the install command downloads; other tools stay in the checkout |
| `rocm-<lockhash12>-<lib>` | `runtime/<lib>` | ROCm libraries from the wheels of `toolchain/rocm-10.1.lock` (`<lockhash12>` = first 12 hex of its SHA-256) |
| `rocm-<lockhash12>-LICENSES.txt` | `runtime/LICENSES.txt` | licence texts of the shipped ROCm parts |
| `tona-LICENSES.txt` | `runtime/tona-LICENSES.txt` | MIT licence of Tona and compiled-in code (cpp-httplib, nlohmann/json, ports from llama.cpp/ggml) |
| `SHA256SUMS` | (not in the manifest) | all assets except `manifest.json` |
| `manifest.json`, `manifest.json.minisig` | (not in the manifest) | the signed manifest; the draft carries an unsigned one |

macOS (Apple silicon, macOS 15+, experimental): prefix `macos-arm64-`, built by `scripts/release-build-macos.sh`.

| Asset | Path | Notes |
|---|---|---|
| `macos-arm64-tona-server` | `bin/tona-server` | Metal backend |
| `macos-arm64-tona.metallib` | `bin/tona.metallib` | Metal kernels, next to the server |
| `macos-arm64-libomp.dylib` | `bin/libomp.dylib` | Homebrew OpenMP, install name `@loader_path/libomp.dylib`, re-signed ad hoc |
| `macos-arm64-tona` | `bin/tona` | OpenSSL linked statically |
| `macos-arm64-tona-LICENSES.txt` | `bin/tona-LICENSES.txt` | Tona, vendored code, libomp, OpenSSL |

The Mac has no `runtime/`. Programs are not notarized; browser downloads need the
`xattr` command of `docs/use/macos.md`. Homebrew packages are unpinned, so the attestation is the proof there
(`release-verify-build.sh` rebuilds Linux only).

```
~/.local/share/tona/
  versions/<version>/bin/…           programs, RUNPATH $ORIGIN/../lib
  versions/<version>/lib -> ../../runtime/rocm-<lockhash12>
  runtime/rocm-<lockhash12>/…        shared by all versions with the same lock file
  current -> versions/<version>      the systemd user unit starts current/bin/tona-server
```

## Installation without a checkout

`tona` alone (the release page download) carries the model catalog (`toolchain/models.toml`) and expert profiles
(`toolchain/profiles/`), generated by `tools/gen_installer_data.py`. Steps (`installer/core/release_steps.cpp`):

1. **Release:** `check_for_update` and `install_release` of `engine/update/`: signature of `manifest.json` against the
   compiled-in keys, size and SHA-256 of every asset, then the layout above. No valid signature, no install.
   `TONA_UPDATE_BASE`, `TONA_INSTALL_DIR` apply.
2. **Model and drafter** into `<root>/models/<id>/` (`--models-dir`) from Hugging Face at the pinned revision, resumed
   from `<file>.part`, checked against the catalog; a wrong file is deleted. `--model-from DIR` verifies and links an
   existing download.
3. **Expert profile** to `<root>/profiles/`, **API key** to `~/.config/tona/api-key` (0600).
4. **Systemd user unit** `~/.config/systemd/user/tona-server.service` (`installer/core/unit.cpp`):
   `ExecStart=<root>/current/bin/tona start --foreground` and nothing else of the settings, `MemorySwapMax=0`,
   `Restart=on-failure` after 30 s, at most three starts in ten minutes. `tona start --foreground` reads `tona.conf`,
   sets `MemoryMax` of the unit to the RAM limit (recommended: installed RAM minus 6 GB) and becomes `tona-server`
   (`engine/client/foreground.cpp`), so a change of settings never rewrites the unit, and an update moves `current` and
   restarts it. `systemctl --user enable` only with autostart (`--autostart`, default off). On macOS the LaunchAgent runs
   the same command. `scripts/tona-service.sh` writes a unit for a checkout.
5. **Settings and link:** `~/.config/tona/tona.conf`; the link `tona` in `~/.local/bin` into
   `current/bin/` (if not in PATH the installer prints the line for bash, zsh, fish; it edits no profile).

Expected from the base system, not shipped: glibc, libstdc++, libgcc_s, libgomp, OpenSSL. `env -i ldd
versions/<v>/bin/tona-server` must resolve every ROCm library next to the programs.

## Sources of the LGPL libraries

`librocm_sysdeps_elf.so.1` (elfutils 0.195, LGPL-3.0-or-later or GPL-2.0-or-later) and `librocm_sysdeps_numa.so.1`
(numactl 2.0.19, LGPL-2.1) are unmodified AMD builds from the pinned wheels, separate shared objects a user can replace.
Source: AMD TheRock tag `therock-10.1`, <https://github.com/ROCm/TheRock/tree/therock-10.1> (recipes in
`third-party/sysdeps/linux/elfutils/` and `.../numactl/`; tarballs
<https://sourceware.org/elfutils/ftp/0.195/elfutils-0.195.tar.bz2> and
<https://github.com/numactl/numactl/releases/download/v2.0.19/numactl-2.0.19.tar.gz>; AMD mirror
`https://rocm-third-party-deps.s3.us-east-2.amazonaws.com/`). Versions and licences of all bundled libraries:
`licenses/rocm-sysdeps.txt`.

`libgomp.so.1` / `libomp.so` (one file, SONAME `libomp.so`) ships under both names; the system `libgomp` lacks
`__kmpc_*`. `scripts/release-build.sh` fails through `scripts/release_needed.py` when `tona-server` needs a library that
is neither shipped nor base system (libc, libm, libstdc++, libgcc_s, loader); test `tools/tests/test_release_needed.py`.

## Licence texts

`licenses/` holds checked-in texts with a pinned source URL (commit) in each header; nothing is downloaded at build time.
Pins: ROCm/llvm-project `d6f6cb69...`, ROCm/rocm-systems `7da43026...` (submodules of the TheRock tag). Research:
`research/28-release-licenses.md`; `tools/tests/test_release_licenses.py` checks the markers.

On every ROCm version change (new `toolchain/rocm-*.lock`):

- [ ] Read the new pins from the TheRock tag (`compiler/amd-llvm`, `rocm-systems`, glog and fmt submodules of
  `projects/rocprofiler-register/external`); update the header URLs.
- [ ] Diff licence files at the new pins against `licenses/` (`llvm/LICENSE.TXT`, `libhsakmt/LICENSE.md`, glog
  `COPYING`, fmt `LICENSE`, `amd/device-libs/LICENSE.TXT`, `COPYRIGHT.regex`, `BLAKE3/LICENSE`) and the excerpts
  (xxhash.cpp, regcomp.c, ConvertUTF.cpp, UnicodeNameToCodepointGenerated.cpp, MD5.cpp, elfio.hpp, topology.c,
  virtgpu_drm.h); check line ranges.
- [ ] `grep -rL 'Part of the LLVM Project'` in llvm/lib and clang/lib for new third-party code.
- [ ] `strings` and `nm -D` on every shipped library for `hsaKmt`, `GLOG_`, `fmt::`, `ELFIO`, `__ockl_`, new vendor
  names; compare `ldd` with the previous list.
- [ ] Compare the wheels' licence files (`share/doc/hip`, `amd_comgr`, `rocr`, `rocprofiler-register`) with upstream at
  the pins; `hip/LICENSE.md` must still be there.
- [ ] Check `licenses/rocm-sysdeps.txt` against the recipes of the new tag.
- [ ] `release-build.sh`, read the top of `LICENSES.txt`; `just test` passes.

## The release build

`scripts/release-build.sh OUTDIR` builds HEAD from `git archive` with `-DTONA_RELEASE=ON`: `RUNPATH` `$ORIGIN/../lib`
only; `-ffile-prefix-map` for source tree, build directory, toolchain venv and `ROCM_PATH`; `-Wdate-time -Werror`;
`SOURCE_DATE_EPOCH` = commit time; Build ID = SHA-1 of the content. Without the option the reference build is
unchanged. Builds from different directories are identical; `work/`'s toolchain must match the commit's
`rocm-10.1.lock` (checked).

## Release steps

The first release prints `0.1.0` (`release-next.py --first-version`) with hand-written notes; afterwards the version is
computed from the log since the last `vX.Y.Z` tag.

1. **Prepare.** `main` green, `BENCHMARKS.md` current. `scripts/release-next.py` reads `git log <last tag>..HEAD` (PR
   titles, `tools/gates/pr_title.py`), applies SemVer (header of the script, versioning section of `CHANGELOG.md`) and
   prints the version, a draft section and the `git tag` line; `--write` puts the draft below `## [Unreleased]`. Choose
   `seq` (last published plus one). Edit the notes in `CHANGELOG.md` (`## [X.Y.Z] - YYYY-MM-DD`, empty `[Unreleased]`
   above): short lines on what users get, what breaks, security fixes with CVE. The first release names the key IDs
   (first line of `release/main.pub`, `release/backup.pub`). Notes are fixed once the tag is pushed
   (`scripts/release-build.sh` copies them into the signed manifest; no section, no build: `scripts/release_notes.py`).
2. **Tag.** `git tag -s vX.Y.Z && git push origin vX.Y.Z` (not below the proposal; only admins can tag).
3. **Wait** for workflow `release` (15 to 30 min): draft with assets and attestations.
4. **Rebuild locally (required):** `scripts/release-verify-build.sh vX.Y.Z` compares SHA-256 of every Linux asset and
   writes a proof into `~/.local/state/tona/release/`. `release-sign.sh` refuses without it. A mismatch: do not sign
   (`diffoscope`, `readelf`). macOS assets cannot be rebuilt and keep the attestation check only.
   Before signing, read the changes to `scripts/release-*`, `engine/update/keys.h` and `release/*.pub` since the last tag in
   your editor. Anything you did not make yourself: do not sign.
5. **Test.** Install the draft into a scratch `~/.local/share/tona`, start `tona-server`, run `scripts/golden.sh compare`.
   On a Mac: `macos-arm64-tona`, `tona start`, one request (Metal library found, no Homebrew path left).
6. **Sign and publish:** `scripts/release-sign.sh vX.Y.Z --seq N` (`--expires-days D` default 180, `--severity
   security`). It checks attestations, hashes and `seq`, writes `manifest.json`, asks for the key password, verifies
   against the key compiled into `tona`, uploads, asks again, publishes and verifies the published files.
7. **Afterwards**, on a second machine: `tona` shows the update, or by hand the commands below.

Signature: minisign prehashed (`ED`, BLAKE2b-512); trusted comment exactly `tona schema=1 seq=<seq> version=<version>`.
Sign: `minisign -S -s <key> -m manifest.json -t "<trusted comment>"`.

### Check a release by hand (users)

```sh
# 1. The maintainer's signature (assets manifest.json and manifest.json.minisig).
#    The key is the second line of release/main.pub; its ID (first line) is in the notes of the first release.
minisign -V -H -P <public key of release/main.pub> -m manifest.json
# 2. The build attestation: which workflow built the file, from which commit
gh attestation verify tona --repo tobias-nawa/tona \
    --signer-workflow tobias-nawa/tona/.github/workflows/release.yml
```

`sha256sum -c SHA256SUMS` checks the manifest's hashes. A release without `manifest.json.minisig` is a draft.

### Dry run without GitHub

`release-build.sh` (Linux), `release-build-macos.sh` (Mac), `release-merge.sh` joins them. On a Mac newer than macOS 15
`release-build-macos.sh` refuses; `--allow-newer-deps` builds a dry run that is never released. A dry-run version needs a
changelog copy with a `## [0.0.1]` section:

```sh
scripts/release-build.sh /var/tmp/tona-dry --version 0.0.1 --changelog-file /var/tmp/changelog-dry.md
minisign -G -W -p /var/tmp/test.pub -s /var/tmp/test.key          # test key without a password
scripts/release-sign.sh v0.0.1 --seq 1 --local /var/tmp/tona-dry --key /var/tmp/test.key --pubkey /var/tmp/test.pub --no-builtin-check
```

Both platforms: `scripts/release-merge.sh /var/tmp/tona-dry-all /var/tmp/tona-dry /var/tmp/tona-dry-macos`, then
`release-sign.sh --local /var/tmp/tona-dry-all`. Notes: `scripts/release_manifest.py get --manifest manifest.json
changelog`. Test keys never go into `engine/update/keys.h`.

## Keys

Two key pairs known to `tona`: the **main key** signs releases; the offline **backup key** only replaces the main key.
`tona` picks the key by the ID in the signature.

### Create them

```sh
mkdir -p -m 700 ~/.minisign
minisign -G -p release/main.pub   -s ~/.minisign/tona-main.key       # asks twice for a password
minisign -G -p release/backup.pub -s ~/.minisign/tona-backup.key
chmod 600 ~/.minisign/tona-*.key
```

- Password per key: at least six random Diceware words or 20 random characters.
- Put the second line of each `.pub` (base64 key) into `engine/update/keys.h` (main and backup slot) and commit both
  `.pub` files; `release-sign.sh` refuses keys not in `keys.h`. Key IDs (first lines) go into the first release's notes.

### Back them up (offline)

1. Copy each `*.key` to two labelled USB sticks in two places.
2. The **backup key** lives only on the sticks: delete it from `~/.minisign/`.
3. Passwords: password manager plus paper in a sealed envelope next to the sticks, never beside the key in one cloud
   account.
4. Test the restore in a clean directory: `echo test > t && minisign -S -s tona-main.key -m t && minisign -V -p
   release/main.pub -m t`. Repeat after every key or password change and yearly.

### Replace the main key (lost, leaked or old)

Installed programs accept both keys, so a backup-signed release is accepted everywhere.

1. Create a new main and backup key; put both into `engine/update/keys.h` **instead of** the old ones; commit, tag.
2. Sign the draft with the old backup key, handing the script the previous release's keys:
   `git show vPREV:engine/update/keys.h > /var/tmp/keys-prev.h`, `git show vPREV:release/backup.pub >
   /var/tmp/backup-prev.pub`, then `scripts/release-sign.sh vX.Y.Z --seq N --key <old backup key> --pubkey
   /var/tmp/backup-prev.pub --keys-h /var/tmp/keys-prev.h --severity security`.
3. Then sign with the new main key; store the new backup key offline; destroy the old ones.

Installs that have not updated still trust a stolen old main key: announce it (notes, security advisory) and keep
`--severity security`.

### Both keys lost or stolen

Installed copies cannot learn a new key. Generate new keys, put them into `keys.h`, release from source, and tell users
(README, advisory, notes, new key IDs) to reinstall by hand (`git clone`, `scripts/setup.sh`, `just build`, or download
and `minisign -V -H -P <key>`); old installs report "signature invalid" and keep running. If stolen, treat every release
since the theft as suspect (`research/27-updates-signing.md`, "Decision").

## When something goes wrong

- **Workflow fails on disk space:** the runner needs about 20 GB ("Free disk space" prints `df`).
- **`release-verify-build.sh` differs:** do not sign; build twice locally with two `--work` directories; if those differ,
  a path or time slipped into `engine/CMakeLists.txt`.
- **A published release is wrong:** releases are immutable; publish a fixed version with a higher `seq` (`--severity
  security` if needed).
