# Scale run 2026-11-18 on main 14cad0f (first on the Ryzen 9 9950X)

Rule 2 plan, written before the first run. Results are read against it below the line `## Results`.

## Plan

Why now: the scale run is due every three days (`docs/contribute/measurement.md`); the last one is `2026-11-14-scale-run.md` (9600X, commit
7d7108a). **This run repeats its nine blocks on the Ryzen 9 9950X** (installed 2026-11-17, #164; 16 cores, bigger L3, same DDR5-6000,
72 GB/s read with both CCDs against 55 to 58 GB/s on the single CCD of the 9600X; the server sets `OMP_NUM_THREADS` to the 16
physical cores itself, `backend/runtime_env.h`). The PC was reserved for the day. **Hard end: every GPU job is finished by
19:45** (the night run of #165 starts at 20:00 and is not touched). Block g (ClassLRU) stays out as before.

**Time plan.** The 11-14 run took 97 min. Start about 13:45 after the build and this plan are committed; expected end about 15:30,
which leaves four hours of reserve; the target end of 19:00 holds even with one requeued block (exit 75 of the desktop guard) per
three blocks. **No block is dropped in advance.** If a block would not finish by 19:30, it is not started and the plan is amended.

One build: `work/build/scale1118`, built from the branch `scale-run-1118` (main 14cad0f, worktree
`<worktree>`, `work/` a symlink to the main checkout) through the cpu queue before the start. Nothing is
built after the run starts. Drivers: copies of the 11-14 drivers in `/var/tmp/claude/scale1118/` (`master.sh`, `run.sh`, `i.sh`,
`curve.py`, `drive.py`). Changes against 11-14: paths and build name `scale1118`; **`OMP_NUM_THREADS=6` removed from `drive.py`
(block e) and `i.sh` (block i, Tona server)**, because the server now sets the physical cores itself (16 here; `curve.py`, `ab.py`
and the goldens never set it, so blocks a to c4, f, f2 already ran with the server default; on the 9600X both are 6). One
more change (coordinator, before block i started): **llama.cpp-hip in block i gets the full CPU too**, `scripts/baseline.sh` takes
the physical cores (16) instead of the hard-coded `-t 6`; the yardstick must not be handicapped against Tona's 16 threads. **The
11-14 llama.cpp numbers are `-t 6` on the 9600X, the new ones `-t 16` on the 9950X.** Every server runs in a `systemd-run --user --scope` with `MemoryMax=54G`, `MemorySwapMax=0`, port 8097. All GPU
steps go through `scripts/gpu_queue.py` with the desktop guard on (never off). If the guard stops a block (exit 75) it is requeued
once; a second stop leaves it and is noted.

**Desktop VRAM before the start** (`mem_info_vram_used`, 12:36): 2,366,296,064 bytes = 2,257 MiB (2.2 GiB), held by others, without
an engine. That is above the 1.5 GB of the 11-14 plan (1,395 to 1,565 MiB there). Same rule as 11-14: the run goes on, the value is
written before each block (`master.log`), and each long block is read at the slot count of its start. **Slot counts are not
comparable with 11-14 for two reasons**: the desktop holds about 0.8 GB more, and the desktop reserve default is now 1024 MiB
instead of 640 (87c65ea, 11-15: about 4 of 86 slots). Estimate: 8 to 12 slots fewer than on 11-14 at every ctx (70 -> about 60 at
1M, 77 -> about 67 at 262144, 81 -> about 71 at 140000); this is an estimate, the real counts are recorded. If the desktop VRAM is
lower at the start (the value is read again right before `master.sh`), the plan keeps the number given here and the actual value is
noted in the results.

### Findings (outside the plan's range, or worth a line)

1. **Every Tona decode number is higher than on 11-14, by +1.6 to +8.7 %** (b +4.4 / +4.3, c1 +4.8 / +4.6, c3 +4.4 / +3.4, c4 +5.8 /
   +3.1, f +5.0, i +1.6 / +5.7 / +8.7 %), prefill +1.8 to +5.3 % at 30K to 250K and +1.5 % at 512K. This is the sum of the 11-17
   thread result (+1.3 to +4.3 %), the tile (#130), the pragmas (#163) and #159 / B7 for prefill, as the plan expected; the split between them
   was not measured here (single-arm blocks). Finding 1 of 11-14 (deterministic **decode** 7 % below S2) is not repeated: 70.7 / 63.1

2. **Block a goldens are 33 to 37 % shorter** for the first three goldens (17 to 18 s against 26 to 28 s): model load is
   10 s here against 20 s on 11-14 (the plan already guessed 16 threads and #159); the split of the saved 9 s between load and
   compute was not measured. Not a finding about correctness.
3. **1M prefill per slot.** c4 1,073 at 60 slots and f2 1,021 at 59 slots against 1,104 at 70 and 1,089 at 69 on 11-14. The 11-10 slot curve
   (about 0.8 % per slot) predicts -8 % at 10 fewer slots; c4 gives -2.8 % (so the +3 % from #159 / B7 and the faster CPU
   offset part of it), f2 -6.3 %; the difference between the two runs at the same slot count (60 against 59) is 5 %, bigger than the
   slot step: the 1M **prefill** has a spread between runs at fixed slots (as with 11-14 c4 against f2: 1,104 against 1,089 at 70 and 69
   slots) that one round cannot separate. Unchecked.
4. **R8: no slow request and almost no eviction.** 0 of 20 below 55 tok/s (11-14: 3), evicted time per pressured request 0.01 s against
   1.90 s on 11-14, and the pressured 30K **decode** mean 62.0 against 55.1 (the 11-14 finding 3 is gone). The pressure was real:

   12.5 GB, Cached 0.5 to 12 GB. That the eviction fell to near zero is not explained by this run; candidates (not tested): 16
   threads let the reader and the server coexist, 11 slots fewer means less registered memory exposed (3.6 GB at 66 slots against 3.6 at
