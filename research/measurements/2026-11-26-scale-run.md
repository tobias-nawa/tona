# Scale run 2026-11-26 on f5518b76 (Coder, Ornith and Bolt)

Rule 2 plan, written before the first run. Results are read against it below the line `## Results`.

## Plan

Why now: the scale run is due every three days (`docs/contribute/measurement.md`); the last one is `2026-11-18-scale-run.md` (Coder only, main
14cad0f). Since then Ornith and Bolt became offered models and the engine changed a lot (prefill attention kernels, Ornith and Bolt
architectures, KV hot head, layered short prefill for Ornith, history drafts for Bolt). The numbers the installer and the client
show (`data/modeldb/offer.json`: **decode** at 2K / 16K / 64K per model) come from single runs of 11-20 on older builds; this run
measures them again on the engine that is shipped. The engine to measure is `f5518b76`; the branch `n2-scale-run` is cut from
the main branch (0f073663), whose `engine/`, `scripts/`, `tools/` and `bench/` are byte-identical to `f5518b76`
(`git diff --stat f5518b76 main -- engine toolchain scripts tools bench` is empty; only docs differ).

**Hard end 07:30 on 2026-11-26.** Start about 00:20 after the build and this plan are committed; expected end about 03:00, so there
are four and a half hours of reserve. The desktop guard is off on this machine on purpose (`~/.config/tona/desktop-guard-off`);
every GPU step still goes through `scripts/gpu_queue.py` (kind `exclusive`, which blocks the CPU jobs of other workers).

**One build**, `work/build/scale1126`, built from the checkout of the branch (`0f073663`) through the cpu queue before the start.
Nothing is built after the run starts. Drivers: copies of the 11-18 drivers in `/var/tmp/claude/scale1126/` (`master.sh`, `run.sh`,
`i.sh`, `curve.py`, `drive.py`; kept in `2026-11-26-scale-run-logs/`). Changes against 11-18: paths, build name, test port **8126**
(11-18 used 8097, which is reserved now), `curve.py` takes its scripts from this worktree, block a dropped, block i without
llama.cpp, new `ab.py` blocks `o-coder`, `o-ornith`, `o-bolt`. Every server runs in a `systemd-run --user --scope` with
`MemoryMax=54G` (`curve.py` through `ab.py`'s default of RAM minus 6 GiB, `drive.py` fixed) and `MemorySwapMax=0`.

Whether to raise them is the maintainer's decision; this run changes no file besides the measurement records.

### Findings (outside the plan's range, or worth a line)

1. **More slots than in the source runs.** With the desktop holding 1.1 GiB (11-20: about 3.4 GiB; 11-18: 1.9 to 2.3 GiB) the slots per
   layer are 76 / 103 / 125 (Coder / Ornith / Bolt at ctx 262144) against 55 / 74 / 70 in the 11-20 offer runs. **Decode** is 0 to 2.8 %
   above the offer rows and **prefill** 3 to 6 % above (Coder 16K / 64K, Bolt, Ornith 2K). That slots are the cause was not tested
   (unchecked: no run here varies the slots of one model). The offer rows hold for a desktop that holds up to about 3 GiB; with a heavier
   desktop the rates may be lower.
2. **2K prefill is the first request of every start and varies 4.5 to 6.4 % between starts** (Coder 1,064 to 1,188, Ornith 2,687 to 3,191,
   Bolt 1,432 to 1,558) while 16K and 64K vary 0.05 to 0.6 %. The A/A comparison of o-coder therefore reports -5.8 % for **prefill** at 2K on
   one and the same build. A 2K **prefill** claim needs more starts than the 2 to 3 rounds here. The cause of the 2K spread is unchecked.
3. **Huge pages for the registered memory are gone: 0.0 of 3.6 GB in R8 and f, 0.4 of 11.3 GB in c4, 1.7 of 11.3 GB in f2** (11-18: 3.5 / 3.6,
   5.1 / 11.3, 10.9 / 11.3). At the end of the run the machine had its 8 GiB swap full (34 MB free) and about 12 GiB of page cache
   (`/proc/meminfo`: MemFree 32.7 GB, 3,285 free blocks of order 10, `AnonHugePages` 0). Why the server got no huge pages is unchecked; the
   engine warns about it at every start.
4. **One slow request in R8: pair 1, 130K, pressured, 36.2 tok/s decode** (expectation: none below 50), with 3.92 s of evicted time (the only
   pressured request above 0 s), GPU clock 1,913 MHz on average (minimum 792) against about 2,950 in the other 130K requests, GPU busy 66 %
   against 98 %, the largest page-cache scan of the series (6.6 million pages) and the lowest MemAvailable (10.9 GB). It is the first
   pressured 130K request after the first pressured 30K one. The other nine pressured requests ran at 59 to 65 tok/s. 11-18 had none (lowest
   59.9), 11-14 three below 55. One event in 20 requests: the rate cannot be bounded below about 22 % (one-sided 95 %, exact), and a repeat
   is needed to say whether it is a start effect. Whether finding 3 (no huge pages) is the cause is unchecked.
5. **Long blocks at 69 slots at ctx 1048576** (11-18: 60): **prefill** 1M 1,164 and 1,132 (c4 and f2, same slots, 2.8 % apart), 512K 1,536.
   This answers the open point of 11-18: the spread between two starts at a fixed slot count is about 3 %. **Decode** 57.2 / 57.0 at 1M
   against 56.5 / 56.2 on 11-18.
6. **Swap grew from 5.1 to 8.0 GiB during the run** (the servers have no swap): swap-ins of the servers 5 to 318 MiB per start (c4: 318 MiB,
   11-18: 6.5 MiB). The machine ends with swap full; which processes hold it is unchecked.
7. **Ornith 2K prefill gain is smaller than the +15 % of the short-layered file**: +7.5 % (median) to +9.6 % (mean) against the 11-20 offer
   row. The offer row came from another machine state (finding 1) than the A/B of that file, so the two are not the same comparison (not
   tested here).

### Open points

- A 2K **prefill** measurement with 5 to 8 starts per model would settle findings 2 and 7 (one `ab.py` job, about 10 min per model).
- A repeat of the R8 series (about 20 min) would show whether the slow request of finding 4 returns, and whether it goes with finding 3.
- Whether the slot count explains finding 1: one `ab.py` run per model with the same desktop VRAM as on 11-20 (about 3.4 GiB held).
