# Evictions under page-cache pressure: mechanism and fix

Date 2026-11-11. Platform: RX 9060 XT, Ryzen 5 9600X, kernel 7.2.15-200.fc44, 60 GiB RAM, GTT total 32.5 GB. Build
`work/build/w103b` (main 8239485, no source change). Server on port 8099 under
`systemd-run --user --scope -p MemoryMax=54G -p MemorySwapMax=0`, GPU lock held. Driver `idle.py` (not in the repo): starts the
server, waits 15 s, then runs the page-cache pressure reader (`cat` loop over the 55 GB of model files) for a fixed time and
samples `evicted_ms` of all KFD processes every 10 ms (an episode is a run of samples where it grows), plus `/proc/vmstat` and PSI.
Raw data: `/var/tmp/claude/w103/` (not kept). Every rate is a decode rate unless it says prefill.

## Re-reading the three R8 series (no new run)

## Plan E1: is the userptr overflow the source?

1. Scope: idle server (no request), 120 s of pressure. Arms: A = `--ctx 140000` (start log: overflow registered as userptr, 0.7 to

   files; the 11-01 probe (GTT 0 to 0.2 s, userptr 4 to 66 s per minute). If B also evicts, the userptr overflow is not the only source.
3. Tooling: `TONA_DECODE_DIAG=1` (no effect idle), `kfdshim.so` (LD_PRELOAD tally of KFD allocations per type with size) in an extra

The idle server alone, with no request, loses 16 to 32 s per 120 s with a 0.7 GB overflow: the counter grows on page invalidation
and not on GPU work. Without overflow it still loses about 2 s per 120 s (second source, below).
`LD_PRELOAD` tally of the KFD ioctls (`kfdshim`, extended by `AMDKFD_IOC_SVM`): the registered overflow is **not** a
`ALLOC_MEMORY_OF_GPU` userptr but one SVM range (`hipHostRegister` goes through `AMDKFD_IOC_SVM` set_attr on this runtime:
one call of 684,240,896 bytes with `ACCESS_IN_PLACE` for both GPU nodes); ctx 65536 has no such call. A second class shows in both
arms: 5,272 SVM set_attr pairs of 2 to 33 MB (33 GB in total at start-up), from the pageable `hipMemcpy` copies at load (the runtime pins
the source per copy); their ranges sit in the address space of the file mappings that are kept (experts, embeddings).
Kernel source (torvalds/linux master, read online, 7.2.x not checked line by line): a userptr/SVM invalidation under
`mmu_interval_notifier` stops all queues of the process (`kgd2kfd_quiesce_mm`, `amdgpu_amdkfd_evict_userptr`; for XNACK off ranges
`svm_range_evict`), and the restore worker revalidates the invalid range before `kgd2kfd_resume_mm`, so the time the queues stand
still grows with the size of the range that was hit (unchecked for 7.2.15: that the SVM path scales the same way).

## Finding E9a: 1 MB pieces break the copies; the kernels read through one device base

First R8 start of `w103f` (1 MB pieces, ctx 262144): all 9 requests failed with `hipMemcpyAsync(... M.pin_[l].host ...): invalid
argument`: one copy from pinned experts must not span two `hipHostRegister` registrations (the prefill copies runs of experts, and
a single 3 MB expert crosses a 1 MB piece). Goldens and `ab.py` ran at ctx 32768/140000 where the registered overflow does not reach
the copy paths or did not exist, so they could not see it. Fix (`w103g`): `copy_pinned_to_device` (`gpu/gtt.cpp`) copies a range that
crosses a piece in one call per piece, used at the five sites that copy from `PinLayer::host` (grep: `prefill_moe_run.cpp` 2,
`mega_prefetch.cpp`, `prefill_plan.cpp`; the other users of `PinLayer::host` are CPU reads). Default 4 MB. The kernels do not copy: they
read pinned experts as `slot0 + j` from the device base `dev` of the layer buffer (`mega_experts.cpp` `pin_layer`, `P.slot0`, only
`mega_select_cpu.cpp:141` uses it), i.e. the device address of piece `i` must be `dev + i * piece`. `register_host_memory` now checks
the device pointer of **every** piece against that offset (`contiguous_for_gpu`) and falls back to one registration if one differs
(for a userptr the device address is the host address and every piece is mapped at its own address, so a read across a boundary
is a read in the next piece's mapping).

## Summary

1. **Mechanism:** the part of the pinned experts that does not fit the GTT (32.5 GB = `ttm.pages_limit`) is anonymous memory registered with `hipHostRegister`, which on this
   runtime is a KFD SVM range with an MMU notifier. When the kernel migrates or reclaims a page in it (compaction, reclaim under page-cache pressure), KFD stops all queues of the
   process until the range is validated again (`evicted_ms`). An idle server with no request loses 16 to 32 s per 120 s of pressure with 0.7 GB registered, 30 to 75 s with 4.1 GB,
   0.8 to 2.1 s with nothing registered (the floor, source unchecked).
2. **Variation:** the registered size = pinned bytes minus free GTT at the start; the desktop's GTT use (0.2 to 1.8 GB) changes it, at `--ctx 140000` 0.1 GB switch it between 0 and 0.7 GB; at
   the service default `--ctx 262144` it is 4.1 GB. Plus +-40 % between starts of the same configuration.
3. **Fix:** 2 MB-aligned mapping with `madvise(MADV_HUGEPAGE)`; no root, no sysctl, needs THP `madvise` or `always` (the reference PC has `madvise`). Pieces, re-mapping the kept file
   mappings and moving the overflow into the GTT were tested and dropped (decode -21 to -27 % at <= 16 MB; no effect; the GTT cannot exceed `ttm.pages_limit`).
4. **Open:** (a) the 1 s floor per 120 s without registered memory; (b) the share of the evictions that comes from the kept file mappings was only tested by the remap; (c) a raised
   `ttm.pages_limit` / `amdgpu.gttsize` (root, kernel parameter) would remove the registered part entirely: untested; (d) the warning line for a low huge-page share is untested at run time;
   (e) behavior with a full page cache at the start (compaction at the creation of the buffer) is unchecked; (f) other distributions' THP defaults are unchecked.
