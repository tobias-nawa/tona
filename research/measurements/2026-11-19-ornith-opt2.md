## Plan

### Item 1: per-layer decode tap (D4)

**Question.** In which layer, and in which part (mixer or MoE block), does the Ornith decode path first leave the oracle's
residual stream by more than rounding?

**Mechanism (no change to numbers).** `TONA_TAP_OUT=file` (Ornith only, off by default) adds two `OP_RES_NORM` steps per layer
that copy `R` (without `y`, without a norm: a pure copy) into tap buffers, after the mixer's residual add and after the layer;
the host writes them after the pass (`engine/gpu/mega_tap.*`). `TONA_REF_TRACE_OUT=file` of `tona-check` writes the oracle's
`Trace` in the same layout (new `Trace::residual_mid`, Ornith oracle). `tools/tap_compare.py` prints the relative L2
difference per slot and the first slot above 1e-3 per step. The Coder's program has no tap step (the variable is read only in
`qwen35moe/program.cpp`); the changed shared files (`mega.h`, `mega_serve.cpp`, `mega_init.cpp`) hold a null pointer test.

**Run.** One `gpu` job: `tona-check` on the Q4_K_M file, 20 prompt tokens, 100 generated, ctx 4096 (as D2/D3), both taps on, all
steps against the oracle. One run (deterministic on both sides, no spread). Why this size: D2/D3 used it, the deviation is at
every step, step 0 is the worst.

**Expectation (with source).** D2/D3: worst logit deviation 0.12 at step 0, 1.5 to 4 % typical. A rounding-level start
shows relative L2 of the residual of 1e-4 .. 1e-3 growing slowly with depth (F32 against double, int8 activations of the
kernels: block-wise rounding error 2^-8 per matvec input, so about 3e-3 per matvec output at worst). **Decision rule, fixed
before:** if the first slot above 1e-3 is at the same layer in most steps and the error jumps there by 10x over the slot
before it, that op is a suspect and I split it further (more taps) or read its kernel; if the error grows smoothly (at most
2x per layer) from the first layer on, it is the int8 activation rounding accumulating (the D3 test excluded it as the
main cause for the logits, so a smooth growth would re-open that and be reported with numbers).

**Active tooling.** `TONA_TAP_OUT`, `TONA_REF_TRACE_OUT`; no `TONA_DETERMINISTIC`, no profiler.

**Stop.** First answer: the slot and kind of the first step with a jump. Out-of-memory or GPU fault: stop and report.

### Item 3: prefill attention beyond 16K (plan, written before the run)

**Reading of the code.** `k_fattn_prefill` (`engine/gpu/prefill_fattn.hip`) ran one tile of 16 rows per block; Ornith has 8 q heads per KV
head (16 / 2), so a tile is **2 tokens** x 8 heads, and every 2 tokens the block stages the whole prefix of K and V again
(global loads, int8 to f16, transposed LDS writes, 5 barriers per 16 cells). Bolt (32 / 2 heads: 1 token per tile) is worse.
The cost grows with N^2 and has no reuse. From the table of `2026-11-19-ornith-prefill.md` (ms per token: 4K 0.288, 16K 0.368,
32K 0.504) the quadratic part is about 7e-6 ms per token squared: **30 % of the prefill at 16K, 60 % at 64K**.

**Change.** Up to 8 tokens per block: MT tiles share each staged chunk (stage once, then scores, softmax, accumulate per tile).
Each row sees the same chunks in the same order with the same operations: **bit-identical** to the single tile (checked by
`test_gpu_fattn` against the oracle primitives, and by the output SHA of Ornith). `TONA_FATTN_PF_MT1=1` restores the single tile.
The Coder does not use this kernel (QSA); Bolt does (tests: `test_gpu_mamba`, `test_gpu_moe_latent`, `test_gpu_bolt_quant`).

**Run (one `exclusive` `ab.py` job).** Both arms the same build `ornith2-fa`; A with `TONA_FATTN_PF_MT1=1`, B default. Workload
server, targets `2000:100,16000:100,64000:50`, `--ctx 70000`, MTP head from the file, `--drafter none`, rounds 2 (no noise
entry for 16K and 64K), alternating AB/BA, no other variables. Why this size: the question is the shape of the curve (2K, 16K,
64K); decode tokens are few because only the prefill rates are the target (decode after a 64K prefill is a by-product).
**Expectation (B against A, source: the quadratic fit above, attention part taken down 2 to 3 times):** prefill@2000 -1 to +2 %
(attention is a few % of 2K), prefill@16000 +10 to +25 %, prefill@64000 +30 to +80 %. Decode: no change (the decode step is not
touched; +-1 %). Active tooling: none beyond the above. Output SHAs equal in A and B (the kernel is bit-identical).

**Decisions fixed before:** if prefill@64000 gains less than 10 %, the staging is not the cost and the kernel is profiled before any
further change (the change then stays only if it is not slower anywhere); if a SHA differs, the change is wrong and goes out.

## Results

### Item 1: D4, the per-layer tap (jobs `ornith2-d4`, `ornith2-d4-q8`, build `ornith2` at `ed59d24`)

Run 1: 20-token prompt (12 prompt tokens by the tokenizer), 100 generated, 112 steps, ctx 4096, oracle as it is (F32 inputs, double
dots): **top-1 equal in 109 of 112, worst logit deviation 0.117 (as D2: 0.120)**. Run 2: the same with `TONA_REF_Q8ACT=1` (oracle rounds
every matvec input to int8 blocks of 32 like the kernels), 8 generated (20 steps). Quiet state: the desktop's 0.98 GiB VRAM; the CPU
was loaded by other programs (the check said do not measure; both runs are correctness comparisons, no rate).
Relative L2 difference of the residual stream, GPU against oracle (`tools/tap_compare.py`, medians over the steps):

| Slot | GPU vs oracle as is (112 steps) | GPU vs oracle with Q8ACT (20 steps) | oracle Q8ACT vs oracle as is (20 steps, no GPU) |
|---|---|---|---|
| L00 mixer (DeltaNet) | 8.0e-3 | **4.3e-5** (step 0: **1.4e-7**) | 8.2e-3 |
| L00 layer | 8.8e-3 | 4.8e-4 | 8.5e-3 |
| L03 layer (first attention) | 1.2e-2 | 5.8e-3 | 1.1e-2 |
| L11 layer | 2.7e-2 | 2.1e-2 | 1.7e-2 |
| L19 layer | 5.2e-2 | 1.5e-2 | 3.0e-2 |
| L39 layer (last) | 4.9e-2 | 3.7e-2 | 3.8e-2 |

Reading, against the rule fixed in the plan (a jump of 10x at one layer in most steps = suspect; smooth growth = rounding that
accumulates):
- **No layer or op jumps.** The error grows smoothly (about 1.1 to 1.3x per block) from the first block to about layer 24 and
  then stays at 3 to 6 % of the residual's norm; the first slot above 1e-3 is slot 0 (L00 mixer) in all 112 steps without Q8ACT.
- **The DeltaNet path is bit-level right:** with the oracle rounding its inputs like the kernels, the mixers of layers 0, 1, 2 at
  step 0 agree to **1.3e-7** (float rounding), through `dn.in`, conv, recurrence, norm, `ssm_out`. At step 0 the first block above
  1e-3 is the first attention layer (L03 mixer, 2.8e-3): the int8 KV cache (V of the first token is read back rounded), by design
  and as D3's `TONA_REF_Q8KV` emulation would show.
- **Why D2/D3 did not find it:** the deviation of the final logits is the end of a chain in which an error of 8e-3 at layer 0 (the
  int8 activation rounding) is amplified to 3 to 5 % by layer 39; the same amplification appears **between two oracles that differ
  only in that rounding** (last column: 8e-3 to 3.8e-2). Taking away one source (Q8ACT or Q8KV) therefore leaves the other sources
  to be amplified the same way, which is why the end-to-end rule "half of the worst deviation" could not show it. The per-layer view
  does: at layer 0 the activation rounding explains the deviation completely (8e-3 to 4e-5, DeltaNet to 1e-7).
- **Verdict: by design, no bug.** The decode kernels' int8 activations (the same rounding as llama.cpp's MMVQ) and the int8 KV
  cache are amplified through 40 layers (about 5x) to 3 to 6 % of the residual's norm and 1.5 to 4 % of the largest logit, top-1
  equal in 109 of 112 (the misses are near-ties). Changing it would be a numbers change (maintainer). Not tested: the top-8 expert
  flips on near-ties (no counter of the kernel's choice in the tap; the oracle's choices are in its trace).

### Item 2: acceptance (tokens per pass) of this run, a by-product of the new counters

Server counters per request (identical in A and B, they differ only in the prefill kernel; MTP head, history drafts on, no
`TONA_DETERMINISTIC`, sum-the-code prompts of the corpus): **tokens per pass / MTP draft steps per pass: 2K 2.30 / 2.49, 16K 3.57 /
1.64, 64K 1.81 / 1.56.** So the acceptance is not a function of the context length but of the text of the answer (the 16K summary
quotes code, which the history drafter predicts: 3.57 tokens per pass with fewer draft steps); the 64K one is the worst.
This explains round 1's +20 % at 2K against +5 % at 16K: the truncated MTP head saves a fixed time per draft step, and the draft steps
per generated token are **1.08 at 2K and 0.46 at 16K** (2.49 / 2.30 and 1.64 / 3.57). Saved per token about 1.08 ms x 1.08 = 1.2 ms of
a 9.6 ms token at 2K (+12 %, plus less verify work) and 1.08 ms x 0.46 = 0.5 ms of 6.6 ms at 16K (+7.5 %); measured +20.4 % and +5.3 %.
The order and ratio (about 4x vs 2.3x predicted) fit, the absolute 2K value is above the estimate (the shorter MTP head also shortens
each pass's CPU wait; not separated). Counts per request are also in the server log line "tokens per pass" for every arm
(`work/ab/<name>-logs/`).

### Item 4: decode step (no change taken in this round)

Read-only so far (spills, prior art above). No lever was measured or taken: the round-1 profile (D1) has the dense matvecs and the head
