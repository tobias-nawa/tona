# 2026-10-23: Matvec formats, root-cause analysis and the int8 path

Own measurement. Tools `ie-gpu-matvec` (large matrices from real tensors, up to 512 MB), `ie-gpu-chain`
(all matvecs of one token), `ie-gpu-gen` (real forward pass). RAM 32 GB, DPM `auto`.

## Why the formats were slow: three hypotheses, two discarded

Starting point (float path, large matrices): IQ2_S 40 %, IQ3_XXS 41 %, Q5_K 42 %, IQ4_NL 46 %, IQ3_S 48 % of 315 GB/s.

| Attempt (for measuring only, result wrong) | Effect | Conclusion |
|---|---|---|
| always read x from 1 KB (stays in L1) | +0–15 % | x traffic is not the bottleneck |
| lookup tables replaced by computation | −10 to +10 % | tables are not the bottleneck |
| row with 16-byte accesses into the LDS, unpack there | 0 to −20 % | load scheme is not the bottleneck |

Estimate: for 315 GB/s, IQ2_S has to unpack ~1 billion values per ms. At ~6 trillion lane instructions/s
(32 CUs × 64 lanes × 3 GHz) that allows ≤ 6 instructions per value, the float path needs ~15. Control:
IQ4_NL (rows of 640, 20 of 32 lanes active) lies below IQ4_XS (same unpacking) by exactly that share.
**The kernels were compute-bound.**

## int8 path

- x rounded to int8 per block of 32 (d = max|x|/127), plus the sums of the two halves of 16
- weights unpacked to int8, `v_dot4_i32_iu8` (4 products per instruction)
- IQ4_NL/IQ4_XS: 16-entry table in registers via `v_perm_b32`
- grid formats: signs as a byte mask, Σ±g·x = dot(g,x) − 2·dot(g∧m,x)
- L lanes per row (largest power of two that divides the sub-blocks), 32/L rows per wave
- grid tables per block in the LDS

Check against the CPU with the same rounded x: error ≤ 5e-8 relative to Σ|w·x| in all formats.
Rounding error of x itself: 0.7–2.0e-3 relative.

are therefore done alternately in several rounds.

### All matvecs of one token (`ie-gpu-chain`, 2 runs, median of 9 × 10 tokens)

| Variant | float | int8 |
|---|---:|---:|
| A: one kernel per matvec | 27.0–27.4 ms | 26.1 ms |
| B: one kernel per phase | 44.6 ms | 28.4 ms |
| **C: persistent, 48 blocks** | 22.2 ms | **18.7 ms (267 GB/s, 85 %)** |

Lower bound 15.84 ms. **C with int8 saves 8.3 ms per token compared with the current state (A, float).**

### Real forward pass, one kernel per step

Without reloading (measurement mode), 100 tokens, 3 runs: float **27.6** tok/s (decode), int8 25.4–26.8 tok/s (decode).
Profile: matvec time 23.8 (float) against 23.0 ms (int8), plus 1.0 ms for 673 quantization kernels and more gaps.
The expert matvecs are small (0.9 MB, 5.7 µs instead of 2.9 µs read time): ramp-up and tail of the kernel
determine their duration, not the unpacking. **The int8 path pays off only in the chain or in the megakernel.**
The forward pass therefore defaults to float, `IE_GPU_INT8=1` switches int8 on.

### Quality

Teacher forcing, 1,363 tokens of Python (CPython asyncio), 96 slots:

| | NLL | Perplexity | Top-1 |
|---|---:|---:|---:|
| float | 0.8225 | 2.276 | 82.2 % |
| int8 | 0.8139 | 2.257 | 82.1 % |

No measurable loss. Against the CPU reference ("The capital of France is", 10 steps): top-1 equal in all,
largest logit deviation 2.4 (relative 0.15).

## Side finding: reloading with 32 GB is noisy

With reloading the same generation fluctuates today between 14 and 21 tok/s (decode) (yesterday 24.4): the page cache
(24 GB) cannot hold the 25 GB of experts, what of them sits in RAM depends on the runs before. Reliable
numbers with reloading only with 64 GB.

## Open

- IQ2_S (70 %) and IQ4_NL (73 %): IQ4_NL has only 4 lanes per row with 5 sub-blocks
- BF16 (88 %, float path) and Q2_0 (29 %, 0.04 GB per token) without an int8 path
- `IE_MATVEC_STAGED` (LDS path of the float kernel) stays off; re-measure with int8
