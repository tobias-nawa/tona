# Scale run 2026-11-14 on main e76184f (last baseline on the Ryzen 5 9600X)

Rule 2 plan, written before the first run. Results are read against it below the line `## Results`.

## Plan

Why now: the scale run is due every three days (`docs/contribute/measurement.md`); the last one is `2026-11-10-scale-run.md` (build 1f81397
plus plan commits, run 11-11 03:49 to 08:14). **This run is the 9600X baseline for the CPU swap**: the Ryzen 5 9600X of the
reference PC is replaced by a Ryzen 9 9950X on 2026-11-19, and after the swap every block is measured again and compared with
this file. So the numbers, the slot counts and the desktop VRAM of every block are kept exactly (raw files, `*.tc.log`), and the
drivers stay as they are for the repeat. The machine was rebooted at 18:44 on 11-14 (clean memory, no swap, empty page cache).

Since the 11-10 build the engine changed a lot (360 commits, 137 files in `engine/`); most are the Mac backend. The commits that
can touch this machine are sorted below under "What changed on main". Block g (ClassLRU, #98) is not run: decided on 11-11.
Block e (R8) now runs at `--ctx 262144` (the service default), because #103 (huge pages for the registered overflow, 11-11) was
only tested there and the overflow at `--ctx 140000` comes and goes with 0.1 GB of desktop GTT use (`2026-11-11-evict.md`).

One build: `work/build/scale1114`, built fresh by the coordinator right before the start from the branch `scale-run-1114`
(`cmake -S engine -B work/build/scale1114`, the worktree `<worktree>`, `work/` a symlink to the main
checkout; the branch differs from main e76184f only by this file). Nothing is built after the run starts. Drivers: copies of the
11-10 drivers in `/var/tmp/claude/scale1114/` (`master.sh`, `run.sh`, `i.sh`, `curve.py`, `drive.py`); changes: paths and build
name `scale1114`; GPU steps take their turn in the GPU line (`scripts/gpu_queue.py`, which holds `work/gpu.lock`) instead of a bare
`flock`; `curve.py` writes the load log of every server start (ours, system, other: `scripts/ab_load.py`, the same record as
`ab.py --load-log on`; field `load` of each job in `<block>.json`); `master.sh` writes `python3 tools/hw_report.py` and
`python3 tools/quiet_check.py` before and after every block into `<block>.tc.log`, the desktop VRAM before each block and the
expert-slot count and the huge-page line of every server start; `drive.py` takes `DRIVE_CTX` (default 262144; it was fixed at
140000); block g is removed (no `ab.py` call is left, so `--load-log on` has no place; `curve.py` carries the load log instead).
Every server runs in a `systemd-run --user --scope` with `MemoryMax=54G`, `MemorySwapMax=0`, port 8097. No other worker may
measure or build while the run goes (the GPU line orders the GPU jobs, not the builds that hold only CPU).

**Desktop VRAM before the start.** Long **prefill** depends on the free VRAM through the expert slot count (11-10 re-run: 72 slots
at 1M, 1M **prefill** 1,122 tok/s; 51 to 53 slots gave 953 to 956). The start wants at most 1.5 GB desktop VRAM without an
engine; the coordinator reads `mem_info_vram_used` first. Above 1.5 GB the run still goes (the 11-11 decision, nothing is
postponed for it; `drive.py` itself stops above 3 GB: "VRAM not free"), the value is written before each block, and each long
expectation is read at the slot count of its start: the ranges below hold at 70 slots and more at 1M, with fewer slots against
the 11-10 numbers per slot count (59 slots: 512K 1,347, 1M 1,018 tok/s, 11-05 c4r).

### 3. Active tooling

- `TONA_DIAG=1` in every Tona server and golden run (no rate effect). `OMP_NUM_THREADS=6`, `ROCR_VISIBLE_DEVICES=0`,
  `TONA_EXPERT_PROFILE=work/profile/experts-coder.bin` (set by the drivers like `ab.py`). No `TONA_*` variable is set in the shell.
- b: `TONA_DETERMINISTIC=1`. e: `TONA_DECODE_DIAG=1`, 10 ms `evicted_ms` sampler, GPU/CPU sampler, `DRIVE_ULIMIT_C=unlimited`
  (core dumps allowed). f2: `TONA_ROUTE_TRACE`. i: llama.cpp with `--metrics`, no profiler.
- Memory sampler 1 Hz in `curve.py`: VmRSS/VmHWM, `mem_info_gtt_used`, `mem_info_vram_used`, MemAvailable.
- Load log per server start in `curve.py` (ours, system, other; GPU share; page-ins, swap; idle seconds before the start),
  field `load` in `<block>.json`. No program names are written: sums only (AGENTS.md rule 2, principle 7).
- Test conditions: `python3 tools/hw_report.py` and `python3 tools/quiet_check.py` before and after every block (`<block>.tc.log`);
  they are copied into the results. The run starts only after `quiet_check.py` says ok (or the warning is only the desktop VRAM).
- No warm-up start before block c1: the goldens and R4 before it loaded the model several times. The first request after
  idle is cold (GPU clock ramp, S4); the blocks start a fresh server each, so this holds for the 11-10 numbers too.
