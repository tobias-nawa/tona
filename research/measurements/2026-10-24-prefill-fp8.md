# Prefill: dense weights in FP8 (E4M3) instead of f16, 2026-10-24, own measurement

Profile before (20,000 tokens of code, rocprofv3): k_gemm (dense weights, f16) 27 % of the GPU time at ~26 TFLOPS
effective; experts (gemm_q) 26 %, DeltaNet recurrence 12 %, attention 8 %.

## Kernel (ie-gemm-check, T = 2,048, random data with outliers in X)

| Shape | f16 | FP8, factor per row | FP8, factor per 128 block in K |
|---|---|---|---|
| 2560 → 10240 | 2.94 ms = 36.5 TFLOPS | 2.31 ms = 46.4 TFLOPS | 3.56 ms = 30.2 TFLOPS |
| 2560 → 12288 | 3.47 ms = 37.2 | 2.53 ms = 50.9 | 4.20 ms = 30.6 |
| 6144 → 2560 | 2.00 ms = 32.2 | 1.42 ms = 45.5 | 2.21 ms = 29.2 |

Mean deviation against f16: 3.74 % (per row) and 3.63 % (per block). Converting X: 0.07–0.18 ms per call.
The kernel is built like the f16 kernel (tile 128 × 128, one group per CU because of 40 KB LDS) and reaches 27 % of the
measured FP8 peak (186 TFLOPS).

## In the prefill (12,000 tokens of code, chunk 2,048, with drafter)

| | Perplexity | tok/s (prefill, 3 runs) |
|---|---:|---|
| f16 | 2.497 | 859 / 1,009 / 929 |
| FP8, factor per row | 2.510 (+0.5 %) | 1,083 / 1,071 / 1,114 |
| FP8, factor per block 128 | 2.520 | 914 (1 run) |
| Decode path (reference) | 2.503 | – |

- The block factors do not help: the error comes from the 3 mantissa bits of E4M3, not from outliers.
- Result: FP8 brings ~15 % prefill for +0.5 % perplexity. As a switch `IE_PREFILL_FP8=1`, default off.
- More speed at the same accuracy is more likely to come from the f16 kernel itself (37 of 93 TFLOPS: one group per CU,
  double LDS buffer), which then helps FP8 as well.
