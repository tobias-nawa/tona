# Does the 512-expert branch (#146) leave the Coder alone at long context and under page-cache pressure?

## Question and decision

`tools/select_checks.py` names two runs on the real model for this change (class C8): the long-context run (R7,
`prefill_plan.cpp`) and the pressure series (R8, `mega_op_wait.h`, `mega_prefetch.cpp`). The branch adds a second
router-row size to the megakernel; for the Coder (256 experts) the kernel machine code, the goldens and the unit tests
are identical (`isa-diff` shows only additions). Question: do the Coder's long-context speed and retrieval and its
behaviour under page-cache pressure on the branch equal those of `main` 51d57d6?

| Outcome | Decision |
|---|---|
| Every number of the branch inside the expectation below and no worse than the base beyond the margin | merge-clean for R7 and R8 |
| A number of the branch outside the margin against the base | finding; look at the cause before the merge (the reference never gets worse, AGENTS.md rule 1) |
| A number outside the expectation for base and branch alike | not caused by the branch: record as a scale-run finding, merge not blocked |

## Plan

### Scope (one run per arm, as in `docs/contribute/measurement.md`; base = `work/build/f512-base`, branch = `work/build/f512`)

1. **R8, per arm** (base first, then branch): `drive.py press 10` as in block e of `2026-11-14-scale-run.md`: 10 pairs of
   30K and 130K prompts, 200 tokens, greedy, `--ctx 262144`, MTP, `MemoryMax=54G`; the odd pairs run while a reader
   `cat`s 55 GB of unused model files (page-cache pressure inside the server's own scope; no second GPU program, no VRAM
   pressure). `TONA_DIAG=1`. The driver is the one of that run with port 8091 and its own output folder. About 20 min per arm.
2. **R7 speed**: `scripts/ab.py --workload huge` (512K and 1M prompts, 200 tokens, `TONA_SEQS=1`, `--ctx 1048576`), A = base,
   B = branch, one round, fixed. About 1 h for both arms.
3. **R7 retrieval**: `bench/needle --hard`, text 0 at 131072 and 1048576 tokens (one text each, as the recipe says), per arm,
   server with `TONA_SEQS=1 TONA_PROMPT_RAM_GB=0` (the README's rule for long contexts), `--require-cache`. The branch
   runs first, then the base. About 20 min per arm (1M prefill about 17 min).
All steps go through `scripts/gpu_queue.py`; hw_report and quiet_check before and after each block go to the
`.tc.log` files. Why not more: the decision needs "no worse", not a small difference; the same-build spread in the
last scale run is the yardstick, a second round only if the first misses the expectation.

- **`ab.py --workload huge` did not run.** It stopped at once with "need 2 <= --min-rounds <= --max-rounds" (the tool needs two
  rounds at least; the plan said one). The first R7 block (20:28:53 to 20:36:20, 7 minutes) therefore measured nothing. R7 speed
  was re-run with the single-arm driver of the scale run (`curve.py`, workload `huge`, the same prompts, one run per arm,
  base first, then the branch), as block c4 of `2026-11-14-scale-run.md` did.
- **The 1M needle failed at 1,048,576 tokens** (HTTP 400 from the server: the first message left no room for the question
  and answer in `--ctx 1048576`). It was re-run with a text of 1,000,000 tokens, the size of the scale run's 1M requests. The
  128K needle (131,072 tokens) ran as planned in the first pass.
- The R7 speed arms did not alternate (base, then branch). The base arm ran at 20:49 to 21:29, the branch arm at 21:29 to 23:25.
  Other workers' CPU work ran beside the branch arm (load record below), not beside the base arm.

## Plan 2: repeat of the 512K decode comparison on the current main (added 2026-11-16, before the run)

### Question and decision

The first R7 run found the branch's **decode** at 512K and 1M 3.8 % and 4.7 % below the base, one run per arm, with 115.6 % of foreign CPU
load in the branch arm and 2.0 % in the base arm. The reference must not get worse (AGENTS.md rule 1), so this is not settled. Question:
is there a **decode** gap between main and the branch at 512K beyond the noise of the same workload?

| Outcome | Decision |
|---|---|
| B against A within +-2 % (and the pairs show no order effect) | no gap; the first result was load; merge-clean |
| B slower by more than the noise and 2 % | look for the cause in the host diff first (mailbox extension in `mega_build_bufs.cpp`/`mega_types.h`, the `k_route<MaxE>` launch, `max_experts` plumbing), then 1M |
| B faster | no action |
1M is run only if 512K shows a gap.

### Scope

1. Rebuild both arms on the current main 4b4589b (`mega_experts.cpp` changed under the branch): base = main 4b4589b in `work/build/f512-base`, branch = the rebased head in `work/build/f512`, through `gpu_queue.py`, `-- -k 0`.
2. Re-run the server golden on the rebuilt branch (`scripts/golden-server.sh compare work/build/f512`): all 36 cases identical.
3. `scripts/ab.py --a f512-base --b f512 --workload server --targets 512000:200 --ctx 1048576 --env TONA_SEQS=1 --env TONA_DIAG=1
   --fixed-rounds --min-rounds 2 --max-rounds 2 --load-log on`: 2 alternating rounds (AB, BA), a fresh server per arm and round,
   the same 512K summarize-code prompt as `huge`. `hw_report` and `quiet_check` before and after inside the job; the load
   record (own, system, other CPU) per start is in the ab.py report. About 2 x 2 x 25 min of GPU time.
Why this size: 512K is the smaller of the two sizes of the first run and shows the same effect (-3.8 %); two rounds are the minimum
`ab.py` allows and give an order effect and a paired difference, which one run per arm could not.

### Expectation

B against A: **decode** -1 to +1 % (source: the kernel for 256 experts is identical, `isa-diff`; SHAs and expert counters of the first run
were equal), **prefill** -1 to +1 % (-1.3 % in the first run). The same-build spread of this workload is not known (no entry in
`bench/noise.toml` for 512K), so with two rounds a difference below about 3 % is not resolvable and is reported as such.

### Active tooling

`TONA_SEQS=1`, `TONA_DIAG=1`, `--load-log on`, production mode, MTP, `MemoryMax` from ab.py's default.
