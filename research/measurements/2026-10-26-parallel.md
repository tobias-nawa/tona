# Two conversations in one pass (stage 3)

Own measurement, 2026-10-26, ie-server with MTP, `--ctx 16384`, greedy. Compartments (slots) per conversation in VRAM fixed at
start (IE_SEQS, default 2), multi-conversation program in the megakernel, planner in the generator.

## Equality

`ie-gpu-gen --mega --multi-check 200` (two token sequences from the same text, in separate slots, first each alone,
then together in the same passes, partly rejected; also with swapped slots):

| Passes | per conversation | rows | bit-exact |
|---|---|---:|---:|
| 2–4 tokens | 1–2 | 450 | 450 (both slot orders, IE_DETERMINISTIC=1) |
| 5 tokens | 1–4 | 523 | 523 (with and without IE_DETERMINISTIC) |

Teacher-forcing time of the same passes: alone one after the other 6.3–8.6 s, together 5.0–5.4 s.

## One conversation (bench-set, decode)

| | Code tok/s | Text tok/s | Expert slots | Tokens |
|---|---:|---:|---:|---:|
| IE_SEQS=1 | 90.2 / 90.2 / 90.3 | 65.3 / 65.3 / 65.3 | 85 | 3139 / 1148 |
| IE_SEQS=2 (default) | 89.4 / 89.6 / 89.7 | 64.9 / 64.9 / 64.9 | 80 | 3094–3139 / 1148 |

- The new kernel code (steps with slot, dispatcher) and the split generator cost nothing: IE_SEQS=1 equal to
  before (90.3–90.9 / 63.8–65.5), the same tokens.
- The second compartment costs ~0.7 % (state 149 MB, KV 245 MB and pool 27 MB at 16K context in VRAM: 5 expert slots
  fewer). At 256K context the KV is in pinned RAM (~3.9 GB per further compartment), in VRAM state and pool ~585 MB.
- One run with IE_SEQS=2 delivered 3094 instead of 3139 code tokens (one prompt different); the second again 3139. Slot 1 was
  unused, so an existing runtime dependency already, not this change (not pursued further).

## Two conversations (scripts/bench-parallel.py, 11 code prompts per client, decode)

| | total (wall clock, with prefill) | per conversation | draft per pass | Tokens per pass, accepted |
|---|---:|---:|---:|---:|
| one client | 82.1 tok/s | 89.7 | 5.3 ms | 3.46 / 3.19 |
| two, drafts per conversation by own rate, then distributed | 85.7 / 87.0 tok/s | 45.1–46.4 | 10.8 ms | 7.20 / 6.69 |
| two, chain by the rate of the whole pass | **90.0 tok/s** | **47.4–48.1** | 6.7 ms | 7.01 / 6.50 |

Verify pass with two conversations by tokens (mean, ms): 4: 41.7, 5: 48.9–49.2, 6: 54.0–54.3, 7: 58.4–58.8, 8: 63.0
(one conversation: 36.7 / 43.7 / 49.3 / 52.7 / 58.1, measurements/2026-10-26-mtp). Two foreign conversations cost 8–14 % more
at the same number of tokens (more distinct experts, measurements/2026-10-26-overlap).

In the shared passes: 0.100 accepted tokens per ms (100 tok/s) against ~90 tok/s for one conversation alone (+10 %).
The wall clock also counts prefill and the time in which only one conversation runs.

## Conclusion

- Goal "+25 % total, ≥ 45 tok/s per conversation": reached per conversation (47–48), total +10 % instead of +25 %.
- Reason: MTP already fills the pass with one conversation (3.5–3.7 tokens per pass, 90 % acceptance). A second conversation
  brings tokens with fewer shared experts; per token the pass then costs almost as much as alone.
- Benefit already now: the second conversation no longer waits until the first is finished (before, up to minutes with
  long answers), both run at ~48 tok/s.
- Next levers: fewer distinct experts in the shared pass (stage 4, batch-aware routing), MTP steps
  of both conversations in one MTP pass (6.7 ms draft per pass, about half of it).
