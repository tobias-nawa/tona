# 2026-11-11: SSD reads of expert-sized blocks on the Mac, M1 Max 32 GB (#107)

Phase 0 of the Mac backend, point 3: the reference model (58.4 GB file) does not fit into the 26.8 GB the GPU may use
([2026-11-11-mac-bandwidth.md](2026-11-11-mac-bandwidth.md)). The "large" tier would stream experts and the n-gram
table from the SSD. This file measures what the internal SSD delivers for the read sizes of that model. Speed
numbers on this machine are provisional (second project of the owner on the same machine).

## Read sizes, from the GGUF layout

From the header measurement in [research/06-qwen38-architecture.md](../06-qwen38-architecture.md) (section
"Bytes per part"), Coder file (256 experts per layer):

| Read | Size | Per token (decode, 1 token) | Why |
|---|---|---|---|
| one expert matrix (gate, up or down) | 0.68 MB (2.046 MB / 3; the three types differ, gate/up IQ2–IQ4, down IQ4_NL/Q2_0) | 3 per used expert | GGUF stores `ffn_gate_exps`, `ffn_up_exps`, `ffn_down_exps` as separate tensors; expert e at offset e × bytes per expert in each |
| one packed expert (gate + up + down) | 2.046 MB | 480 (48 layers × top-10), 0.98 GB | a repacked file with one blob per expert (as llama.cpp `--moe-pack-dir`, [research/36](../36-llama-cpp-expert-streaming.md)) |
| n-gram table row | 90 B, read as one 4 KiB page | 16 | `io/uring.h`: 16 rows of 90 bytes per token from the 28.8 GB table |
| sequential | 16 MiB | - | upper bound of the SSD |

## Plan (written before the run)

**Scope.** Tool `bench/mac/ssdbench.cpp` (pread from N threads, each thread one request in flight, so queue depth =
threads). Test file `work/ssd/blocks.bin`, 16 GiB of random bytes, written once with `F_NOCACHE` (so the first
buffered read is cold) and deleted after the run.

| Block | What runs | Rounds | Duration |
|---|---|---|---|
| W | write the 16 GiB test file | 1 | ~5 to 10 s |
| A | `F_NOCACHE`, random offsets aligned to the block size over the whole file: 4 KiB at QD 1, 8, 32; 0.68 MB and 2.046 MB at QD 1, 4, 16; 16 MiB sequential at QD 1 and 4. Each point reads 2 GiB (4 KiB: 20,000 reads) | 3 runs | ~25 s per run |
| B | buffered (page cache), 2.046 MB random at QD 16: pass 1 over 4 GiB of fixed offsets (cold), pass 2 the same offsets (warm) | 1 | ~5 s |

Pauses of 10 s between runs. Per point: throughput (GB/s), IOPS, and latency per request (median, p99).

**Expectation.**

| Rate | Expected | Tolerance | Source |
|---|---|---|---|
| 16 MiB sequential, QD 4 | 5.5 GB/s | 4 to 7.5 | MacBook Pro M1 Max 1 TB, Blackmagic/AmorphousDiskMark reviews ~5 to 7 GB/s read (knowledge, unchecked) |
| 2.046 MB random, QD 16 | 5 GB/s | 3.5 to 7.5 | large blocks reach near sequential with enough depth (knowledge, unchecked) |
| 2.046 MB random, QD 1 | 2 GB/s | 1 to 4 | one request in flight: latency ~0.5 to 1 ms per 2 MB (knowledge, unchecked) |
| 4 KiB random, QD 1 | latency 60 µs median | 30 to 150 µs | Apple NAND QD1 4K latency (knowledge, unchecked) |
| 4 KiB random, QD 32 | 300k IOPS | 100k to 600k | (knowledge, unchecked) |
| buffered warm pass | ≥ 20 GB/s | - | page cache = memory copy; only the cold/warm ratio matters |

Consequence to test (not a pass criterion): with misses at 5 GB/s, every 100 MB of missed experts per token costs
20 ms, i.e. at most 50 tokens/s from the SSD part alone.

**Active tooling and conditions.**

- `clang++ -std=c++20 -O3 -mcpu=apple-m1` (Apple clang 21). No profiler, no `TONA_*` variables, no sudo, no
  `purge` (needs root; the cold read comes from writing with `F_NOCACHE`).
- `F_NOCACHE` on the file descriptor for block A; `F_RDAHEAD` off for random reads.
- Disk: internal SSD, APFS, volume `/` (926 GiB, 103 GiB free at 11:35). FileVault state is recorded with the run.
- Load and power are recorded right before each block (load average, CPU % of the busiest processes, `pmset -g batt`).

**Addendum to the plan, 12:22, after block B and before block C.** Block A gave 13 GB/s for 2.046 MB random at QD 16,
above sequential (7.2 to 8.0 GB/s) and above the known figures for this SSD. Suspicion: the test file was written
seconds before and is still served from the SSD's fast write cache (SLC), which an old model file would not be. Block
C repeats the 2.046 MB and 0.68 MB random points (QD 1, 4, 16) and 16 MiB sequential (QD 4) with `F_NOCACHE` on an
old file not written since 2026-03-28 (8.49 GB iOS simulator image under `/System/Library/AssetsV2`, read only), 3
runs, then block A once more on the test file. Expectation: if the suspicion holds, the old file stays at or below
sequential (≤ 8 GB/s) for every point and the test file still shows ~13 GB/s; if the old file also reaches ~13 GB/s,
the SSD reads scattered large blocks faster than one sequential stream and the number stands.

## Evaluation against the plan

| Rate | Expected | Measured | |
|---|---|---|---|
| 16 MiB sequential, QD 4 | 4 to 7.5 GB/s | 7.0 to 8.1 | at the upper end, partly above |
| 2.046 MB random, QD 16 | 3.5 to 7.5 GB/s | **12.9 to 13.2** | **above, finding** |
| 2.046 MB random, QD 1 | 1 to 4 GB/s | 3.3 to 3.7 | inside |
| 4 KiB random, QD 1 | 30 to 150 µs | 86 µs median | inside |
| 4 KiB random, QD 32 | 100k to 600k IOPS | 165k to 170k | inside |

- **Finding: scattered 2 MB reads at depth 16 reach ~13 GB/s, 1.7× one sequential stream of 16 MiB requests.** The
  suspicion of a fresh-write effect is ruled out (block C: an eight-month-old file gives the same). The SSD serves
  many mid-sized requests in parallel better than few large ones. Published figures for this machine (~7.4 GB/s)
  measure the sequential case. unchecked: whether 16 MiB requests at higher depth also reach 13 GB/s (not measured).
- **Block size matters twice over.** 0.68 MB blocks (one matrix, as the GGUF lays out experts) reach only ~7 GB/s at QD 16
  against ~13 GB/s for 2.046 MB (one packed expert). A Mac backend streaming experts needs a repacked file with one
  blob per expert.
- **Buffered reads lose 40 %** against `F_NOCACHE` when cold (7.8 against 13.1 GB/s at the same depth). A streaming
  path reads with `F_NOCACHE` into its own cache.
- n-gram table: 16 rows per token as 4 KiB reads at QD 16 to 32 take ~0.2 ms per token (one round of 190 µs latency).
  The table can stay on the SSD.

### What this means for the "large" tier (estimate, not measured)

**Added after the run (2026-11-11, research update):** open-source engines with the same design measured about 8 tok/s decode
(ds4) on an M1 Max 32 GB with the 512-expert model ([../39-mac-engines-2026-11.md](../39-mac-engines-2026-11.md)). The
estimate below is unconfirmed until reconciled with them.

Per token (decode, one pass): dense part 4.11 GB plus 480 experts of 2.046 MB (0.98 GB)
([06-qwen38-architecture.md](../06-qwen38-architecture.md)). All resident, the GPU alone needs 5.1 GB / 334 GB/s =
15.3 ms, at most ~65 passes/s.

The experts (25.15 GB) do not fit beside the rest. Expert cache of 14 to 18 GB of the 26.8 GB working set (the rest:
dense 4.1 GB, embedding, KV, buffers; the owner's other programs need RAM too) holds 56 to 72 % of the experts. Hit rate
from the same Coder model: 33 % cache → 85 %, 67 % → 94 % ([03-feasibility.md](../03-feasibility.md), llama.cpp #29887);
so ~90 to 94 %, i.e. 29 to 48 misses per token, 59 to 98 MB.

| Miss handling | SSD time per token | Decode estimate | Note |
|---|---|---|---|
| on demand per layer (miss known after the router, ~1 miss per layer, QD 1, 0.6 ms each) | 17 to 29 ms | **~22 to 31 passes/s** | latency-bound, depth 1 |
| prefetched (predicted, all misses of a token in flight together, QD ≥ 16, 13 GB/s) and overlapped with the GPU | 4.5 to 7.5 ms | up to ~50 to 65 passes/s | needs a predictor (research/14-expert-prefetch.md) |
| GGUF layout, 3 matrices per expert, 0.68 MB at QD 16 (~7 GB/s) | 8.4 to 14 ms | lower by ~2× than packed | reason for a repacked file |

With MTP drafts more than one token comes out per pass (reference: tokens per pass in BENCHMARKS.md), but wider passes
also touch more experts; not estimated here.
