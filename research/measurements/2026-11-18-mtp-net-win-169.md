# Is MTP speculation a net win on our verify path, and what does the DeltaNet state cost per verify? (#169)

Branch `worktree-<worktree>`, Coder IQ1_M, RX 9060 XT (gfx1200), Ryzen 9 9950X. Desk research:
`research/65-gdn-verify.md`.

## Plan (written before the first run)

**Question.** vLLM #68081 reports MTP as a net loss on Qwen3.5/3.8 GDN hybrids (-10 % single-stream decode). Is our
MTP/suffix speculation a net win on the bench set, and by how much? Decision: if decode with speculation is above
decode without by more than the noise, the "MTP is a net loss" finding does not transfer and the verify path needs no
rescue; the remaining DeltaNet cost per verify (dn.recur) is then judged by its share of the pass.

**Deterministic counters first (no timing, any load).** From code and one server start: bytes of the DeltaNet state
(`snap_bytes` in the start log, `Mega::state_bytes()`), bytes per replay ring per token, number of `save_state` calls
per verify (by code: 0, it only runs at prefill boundaries, `server/prefill*.cpp`). One request on the bench set code
prompt with `TONA_DRAFT_LOG` gives passes, width and accepted drafts per pass.

**Timed run.** One new switch `TONA_SPEC_OFF=1` (early return in `Generator::draft`: block = last token only, no
drafter, no history; one token per pass, `engine/server/draft.cpp`). `scripts/ab.py`, same build both arms, A default
(production speculation: MTP chain up to 7 drafts plus history drafts), B `TONA_SPEC_OFF=1`, workload `set` (bench-set:
11 code and 3 text prompts, greedy, up to 400 tokens each, ctx 32768), metrics `decode-code` and `decode-text`
(**decode** tok/s, sums over the group). Alternating AB/BA.

**Why this size.** The question has a large effect: the pass table says t(1) = 24.2 ms (41 tok/s without speculation)
against 92.2 (code) and 67.0 (text) tok/s with it (2026-11-15-self-spec-layer-skip.md, 9600X). Noise of the group
metrics is 0.07 to 0.6 % (bench/noise.toml), so two rounds decide an effect of tens of percent; `--max-rounds 3`, early
stopping on. A shorter workload cannot carry the text group, and a longer one adds nothing to a yes/no on the sign.

**Expectation (B against A).** Code: decode -50 % (range -62 to -42), text: -38 % (range -48 to -28). Source: pass time
at W=1 of 24.2 ms (2026-11-12-verify-pass.md) against 3.98 tokens per pass at 42.1 ms mean pass; the 9950X may make
the CPU expert part faster, which lowers both arms, so a ratio is the safer reading (A/B 1.6 to 2.4 on code, 1.4 to
1.9 on text). A result with B above A would be the finding that MTP is a net loss here.

**Active tooling.** `TONA_SPEC_OFF=1` in arm B only. No `TONA_DETERMINISTIC` (it caps drafts at 3 and switches off the
wide path, which would understate speculation). `TONA_EXPERT_PROFILE` as production. Desktop guard on, queue kind
exclusive. No profiler.

**Is "spec off" the real non-speculative path?** No existing knob gives draft length 0 (`TONA_DRAFT_N` clamps to 1..7,
`TONA_MTP_FIXED` / `TONA_DFLASH_FIXED` fix the length at its maximum, `TONA_SUFFIX_MIN=0` only turns off the history
drafts, `TONA_DRAFT_SMALL` shapes the DFlash2 block). `TONA_SPEC_OFF` is therefore a documented measurement switch
(docs/use/environment.md, docs/contribute/testing.md), one early return in `Generator::draft`. With it, a pass is `forward(blk, 1)`:
the same width-1 kernel as the pass table (24.2 ms). Three checks that it is plain decode: (1) default off is
bit-identical: `scripts/golden.sh compare` and `scripts/golden-server.sh compare` on the new build, token SHAs equal
(kind gpu); (2) the B arm's decode ms per token must agree with the width-1 pass time of
`tona-gpu-gen --mega --batch-bench` (`TONA_BENCH_WIDTHS=1`), within 5 %; (3) tokens per pass of B = 1.00 and `draft_n` = 0
in the server timings.

## Results

`scripts/ab.py` A `w169` default against B `w169` `TONA_SPEC_OFF=1`, workload `set`, 2 rounds (AB, BA), alpha 0.05;
raw report `work/ab/w169-spec-off.md` (not in the repository), values below.

| Metric (**decode** tok/s, bench-set) | A: speculation (round 1 / 2) | B: spec off (round 1 / 2) | B vs A, mean [CI] | Expected |
|---|---|---|---|---|
| decode-code (11 prompts) | 96.4 / 96.5 | 41.3 / 41.5 | -57.08 % [-57.97, -56.19] | -62 to -42 %: within |
| decode-text (3 prompts) | 69.1 / 69.1 | 41.1 / 41.5 | -40.23 % [-41.19, -39.28] | -48 to -28 %: within |

Speculation gives **2.33x on code and 1.67x on text** over plain decode. Counters from the B server log: 4,163 tokens in 4,157
passes (1.00 tokens per pass), 0 passes from the history, so B really is one token per pass. B's 41.3 tok/s is 24.2 ms per
token, the width-1 pass time of the pass table (24.21 ms, 2026-11-12-verify-pass.md, 9600X): spec off is the plain decode
path, not a verify at a wider width. A's server log (round 2): 4,087 tokens in 1,033 passes (3.96 tokens per pass), 26 passes
from the history.

**MTP is a clear net win on our path** (the vLLM #68081 reading, -10 %, does not occur). Against the 9600X numbers of
2026-11-15 (92.2 / 67.0) the 9950X gives +4.7 % / +3.1 % with speculation.

## Deterministic counters of the DeltaNet cost per verify (code reading, no timing)

| Quantity | Value |
|---|---|
| `save_state` calls per verify pass | 0 (only `server/prefill_warm.cpp:34`, `prefill.cpp:224,280`) |
| State copy bytes per verify | 0; the state (~108 MiB, 36 layers) is read once and written once in `op_dn_recur` |
| dn.recur per pass, W=1 / 4 / 8 | 0.91 / 1.20 / 2.07 ms = 3.8 / 3.3 / 3.7 % of 24.2 / 36.2 / 55.3 ms (9600X, 2026-11-12-verify-pass.md; not re-profiled here) |
| Floor of dn.recur at W=1 | 216 MiB (state read + write) / 315 GB/s = 0.72 ms, so 0.91 ms is 1.27x of the floor |

Not re-measured here: the per-op profile (`TONA_MEGA_PROF`). The 2026-11-17 CU-scaling run (9950X, 32 CUs) has dn.recur
0.93 / 1.22 / 1.66 ms at W = 1 / 4 / 8 (2026-11-17-cu-scaling.md), in line with the older table (0.91 / 1.20 / 2.07 ms).
