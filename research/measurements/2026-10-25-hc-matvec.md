# 2026-10-25: matvecs with 2 sub-blocks per lane at once

Own measurement. Starting point: gr.down (320 × 10240) and gr.up (10240 × 320), both Q8_0, 97 times per pass, do not
get slower with 16 instead of 32 blocks, so they are not limited by bandwidth.

## Probe (`ie-wide-probe --hc`, 64 copies alternating, ~2 µs kernel launch included)

| | cold | warm (always the same copy, L2) |
|---|---:|---:|
| 320 × 10240, 1 token | 22.6 µs | 16.3 µs |
| 10240 × 320, 1 token | 20.9 µs | 14.1 µs |

More rows (`IE_HC_MULT`): 1× 22 µs, 2× 32, 4× 53, 8× 97: slope ~320 GB/s, plus ~10 µs fixed cost. Even warm,
~12 µs remain. Cause in the machine code: load instructions count in order (`s_wait_loadcnt`). Whoever needs the x values of a
sub-block also waits for all weights sent earlier. Per lane, one latency after the other elapses
(5–10 sub-blocks per lane).

Rejected in the probe:
- `#pragma unroll 2/4` over the sub-blocks: ±1 µs, inconsistent.
- Own aligned Q8_0 (scales per 8 sub-blocks up front, 3 instead of 17 load instructions per sub-block): 22.6 → 21.1 µs at
  320 × 10240, 20.9 → 22.3 at 10240 × 320.
- The same with preloading the weights 2/4/8 sub-blocks deep: equal or slower (up to 26 µs). The x loads
  come after the preloaded weights and wait for them.
- Probe error: with 10240 columns and 4 tokens x does not fit in the probe's LDS buffer (checksum 0). That row
  is invalid.

## In the pass: `row_q8` loads G sub-blocks (weights, then x and scales of all G), then computes in the same order

Bit-exact (NLL 1.561826915 as before). ms per pass, `ie-gpu-gen --batch-bench 600`, two series:

| | 1 token | 4 tokens | 8 tokens |
|---|---:|---:|---:|
| before | 25.43 / 25.40 | 39.28 / 39.36 | 62.56 / 62.56 |
| G = 2 only at 1 token | 24.67 / 24.69 | 39.40 / 39.37 | 64.18 / 64.12 |
| **G = 2 everywhere** | **24.68 / 24.72** | **38.90 / 38.91** | **61.17 / 61.19** |
| G = 3 at 1 token | 24.87 / 24.87 | 39.31 / 39.20 | 64.10 / 64.27 |
| G = 4 everywhere (own series) | 25.32 / 25.30 | 40.07 / 40.08 | – |

Per step at 1 token (µs per pass, before → G = 2): gr.down 2,533 → 2,444, gr.up 1,761 → 1,653, moe.gate_up
3,177 → 3,096, moe.down 2,459 → 2,384. So it works in all `row_q8` matvecs, not only in the hyper-connections.

## Rejected (2026-10-26): inject in Q8_0

`IE_BAR_PROF` per block for gr.down (B = 1): 4 blocks 25.2 µs, the rest 16.6 µs. The four compute `inject`
(4 × 10240, BF16, one wave per row and token). Control: with `IE_MEGA_TSPLIT=0` the slow blocks move along.
inject in Q8_0 (like gr.down next to it, one wave per row and token, bit-exact across the width):

| | BF16 | Q8_0 |
|---|---:|---:|
| gr.down per step, 1 token | 25.2 µs | 18.7 µs |
| pass 1 token (3 runs) | 24.72–24.76 ms | 24.12–24.16 ms |
| pass 8 tokens (3 runs) | 61.54–61.58 ms | 61.67–61.70 ms |
| NLL 1,500 tokens | 2.190080910 | 2.190284686 |
| top-1 | 58.9 % | 58.8 % |

Server, `scripts/bench-set.py` (11 code, 3 text prompts, up to 400 tokens each, greedy), two series:

| Decode tok/s | BF16 | Q8_0 |
|---|---:|---:|
| code | 85.5 / 86.5 | 82.3 / 83.1 |
| text | 59.3 / 59.8 | 56.9 / 57.5 |
| tokens per pass (all 14) | 3.60 | 3.46 |
| ms per pass (all 14) | 46.50 | 46.35 |

The passes hardly get faster (in the server mostly wide), but the drafter hits 3.9 % less, across 13 of
14 prompts. Presumably the drafter reads intermediate values of the model that it is used to with BF16 inject. With
bench-openai.py (3 prompts) it looked like text chance (explain +9 %, csv −2.3 %). Conclusion: evaluate rounding changes only with
bench-set.py.

Also without effect (bit-exact): Q8_0 with a 2 × 16-byte load at a 2-byte address instead of 16 × 2 bytes; matvec
units spread over all 32 blocks instead of block by block (1 token 24.65 → 25.29 ms); 3, 4 or 5 sub-blocks per lane for
Q8_0 only.

## Adopted (2026-10-26): BF16 rows load 4 pieces per lane at once

Instead, `row_bf16` (inject 4 × 10240 BF16, 40 pieces of 16 bytes per lane): first load the weights and x of G pieces,
then compute in the same order. Bit-exact (NLL 2.190080910 at G = 1, 4, 8). ms per pass, two series:

| | G = 1 (before) | **G = 4** | G = 8 |
|---|---:|---:|---:|
| 1 token | 24.50 / 24.45 | **23.96 / 23.96** | 24.04 / 24.02 |
| 4 tokens | 38.38 / 38.41 | **38.15 / 38.07** | 38.98 / 38.92 |
| 8 tokens | 60.10 / 60.11 | **59.44 / 59.40** | 60.13 / 60.13 |

Server, `bench-set.py`, two series equal (bit-exact, the same 3,124 and 1,045 tokens):

| Decode tok/s | before | G = 4 |
|---|---:|---:|
| code | 86.5 | **87.4** |
| text | 59.9 | **60.8** |
