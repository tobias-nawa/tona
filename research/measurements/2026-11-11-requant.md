# Middle model tier: requantized Coder variants A, B', C and the bring-up file (#108)

Status: PLAN, written before any run. Results are appended below the plan; a result outside the expectation is a
finding, not noise.

## Question

How far does each variant of the middle tier (about 20 GB trunk) deviate from the IQ1_M Coder, on code and on prose?
The variants: **A** 256 experts, gate/up IQ2_XXS; **B'** 216 experts, gate/up IQ2_S; **C** 192 experts, gate/up
IQ3_XXS; down Q2_0 in all; everything else a byte copy from the Coder. Experts are requantized from the base Q8_0
(`tools/coder_requant/`). The **bring-up file** is A made from the IQ1_M Coder itself (`--allow-requantize`, double
loss, stopgap for the Mac session) and is measured as a fifth arm.

## Scope (what runs, how many)

| Part | What | Size |

| spread | KLD and top-1 agreement per chunk give mean and standard error; delta-PPL from the two PPL values with the tool's uncertainty; the whole 8-run block is repeated once to show run-to-run noise (expected 0, the tool is deterministic) | 2 repeats of one arm |
| tool call | one short JSON tool-call test per arm if a server path works for the file, otherwise reported as open | optional |

Why this size: the teacher logits file stores about 2 bytes per vocabulary entry (248 K) per token, i.e. ~0.5 MB per token: 100 chunks would be 25 GB per text, 50 chunks 13 GB. 50 chunks x 512 tokens = 25.6 K tokens per text gives a standard error of the mean KLD of a few percent
(unchecked, to be read from the per-chunk output), and the teacher logits stay at 13 GB per text (size estimate unchecked, read from the first file). 512 matches the imatrix context. Expected duration: unchecked; prefill-bound on a 55 GB
model with CPU offload for the experts that do not fit 16 GB; the first run (imatrix, 200 chunks) is timed and the rest
is scaled from it.

## Expectation (with tolerance)

All numbers are **unchecked**: nothing like it has been measured for this model.

- Source: llama.cpp `tools/perplexity` README ranges for KLD of requantized models (KLD below 0.01 is very close,
  0.1 to 0.3 clearly lossy); the Q8_0 base is lossless for practical purposes, so the arms measure our requant plus the
  IQ1_M teacher's own error against the base.
- The teacher itself is already lossy (IQ1_M, ~1.75 bit). A requantized variant from Q8_0 is **not** a copy of the
  teacher, it is closer to the base model. Expectation: mean KLD to the teacher between 0.15 and 0.6 for A (wide
  tolerance, factor 2 either side), top-1 agreement 70 to 90 %.
- Order: C below B' below A in KLD is expected from the bits per weight (3.06 > 2.56 > 2.06), offset by the expert
  drop (192 and 216 of 256). If C is not better than A the expert drop costs more than the bits gain; that is a finding.
- Bring-up (double loss) worse than A in KLD by a clear margin (more than 0.1 absolute).
- Code text KLD different from prose KLD: the imatrix is code-heavy, so code lower than prose is expected.
- Repeat runs identical (the tool is deterministic on one build and machine); any difference is a finding.

### Reading against the plan

- **Outside the expectation, finding 1:** the plan expected the bring-up file (double loss) to be clearly worse than A
  (more than 0.1 KLD). It is **better** than A against the IQ1_M teacher (KLD 0.284 against 0.338 on code, 0.485
  against 0.563 on text, outside the standard errors). Reason (unchecked): the metric is distance to the IQ1_M Coder;
  the bring-up file is derived from the Coder's own weights, A from the Q8_0 base, and the Coder was fitted by its
  authors after quantization (GSQ-RCO). So the metric favours the bring-up file by construction. It does not say which
  file is closer to the full-precision model; that needs the Q8_0 slice as a second reference (open).
- **Finding 2:** all arms have a *higher* PPL than the IQ1_M Coder on both texts (delta +0.3 on code, +1.1 to 1.4 on
  text) although IQ1_M has fewer bits. Same reason (unchecked): a model fitted after quantization beats a plain
  requantization at the same 2 bits per weight.
- **Order of the variants:** expected C better than B' better than A. Measured: B' and C better than A on both texts
  (code 0.305 against 0.338, text 0.529/0.543 against 0.563, outside 2 standard errors of the difference
  by a small margin), B' and C equal on code, B' slightly better on text (0.529 against 0.543, about 1.2 standard
  errors). So dropping 40 or 64 of 256 experts is paid for by more bits per weight, even on prefill-style text. The
  expected loss of B'/C on the prefill text against A did **not** appear. No combined selection (decode gate mass plus
  imatrix counts) was built; the data give no reason for it yet.
- Magnitude: KLD 0.3 (code) and 0.5 to 0.56 (text) against the IQ1_M Coder is large (llama.cpp's guidance puts
  more than 0.1 to 0.3 into "clearly different"); top-1 agreement 76 to 89 %. How this translates into agent quality
  (SWE-bench-like tasks) is not measured.


## Findings during preparation (2026-11-11)

- **imatrix** (`llama-imatrix`, IQ1_M Coder, calib.txt 383 KB, 200 chunks x 512 tokens, 490 s; GPU for the trunk,
  experts on the CPU): `imatrix-coder.gguf`, sha256 `73a2203e95031ecf8d522ab440526ee1ce157708b7da49f466357e74727a784a`.
- **Coverage gap.** `save_imatrix` reports "partial data" for the expert tensors of 39 of 48 layers (9 layers fully
  covered): experts the calibration set never routed to have no statistics. From the percentages: 1 to 5 experts
  per layer of 256 (layers 11 and 42: 5 = 1.95 %, layers 6, 15, 20, 23, 26, 36, 45: 2 to 4, the rest 1 or 2), the
  same count in gate, up and down. The gap is below the 2 % threshold the coordinator set, so no second imatrix is
  made for now. These experts get no importance weights in llama-quantize (unchecked: how it treats them, plain
  least squares presumably); the KLD runs show whether it matters. The variants B' and C keep the experts by router
  weight on coding load, so rarely routed experts mostly drop out there.
- **Fallback quantization (llama-quantize, bring-up file):** one tensor of 1224, `blk.1.ple_conv1d.weight` (4
  columns, not divisible by 32): F16 instead of Q8_0. It is a non-expert tensor, so `assemble` takes the Coder's
  original bytes and the fallback has no effect on the final file.
- **PLE table:** `per_layer_token_embd` (Coder: IQ4_NL, 51 billion elements) must be listed with its own type in the
  type file, otherwise llama-quantize converts it to Q8_0 (hours, 50 GB, discarded by `assemble`). Added as
  `--ple-type` of `tools/coder_requant/pipeline.py types|variant` (commit 32d4bd4). Used for the bring-up file
  (`--ple-type iq4_nl`); a base-Q8_0 source needs none.

## Routing trace for the selection of B' and C (2026-11-11)

- **Workload** (public material only: llama.cpp sources and docs, this repo, public Rust crates; not the KLD eval
  files, nothing from `work/dumps`): 230 single-turn requests (60 C++, 50 Python, 30 Rust, 40 TS/Svelte/JS, 20 shell,
  30 Markdown; tasks explain, find bugs, tests, refactor, document, rewrite, summarize; 400 tokens max) and 90 tool-call
  steps of short agent loops (read_file, search, run_command with real file excerpts as tool results), all 90 tool
  calls valid JSON. 118 K decode tokens (11.5 GB `TONA_ROUTE_TRACE_P`), 240 K prompt tokens, MTP drafter on.
- **Open point: the trace records decode passes only.** `TONA_ROUTE_TRACE_P` writes in `ExpertSelect` of the
  megakernel; the prefill has its own router (`prefill_moe_run.cpp`, `moe_route`) and writes nothing. Agents read
  far more than they write, so prefill routing is not represented in the selection. The check is the prefill-style
  KLD text of step 8 (the eval text runs as prefill in llama.cpp).
- **Stability of the selection** (computed separately on both halves of the trace, overlap of the kept sets per
  layer): 216 experts mean 98.0 %, minimum 96.3 %; 192 experts mean 97.3 %, minimum 94.8 %. The first trace of 7.6 K
  tokens (bench-set and ten slices) gave 88.8 % and 82.2 %, and its selection overlaps the final one by 93.6 % (216)
  and 91.1 % (192).
- **Dropped gate mass** (share of the summed gate weight on experts not kept): 216 mean 1.5 %, worst layer 5.7 %; 192
  mean 3.7 %, worst layer 11.2 %.
- **Prefill vs decode routing** (from the imatrix, which stores per-expert token counts of the llama.cpp prefill over
  `calib.txt`, 102 K tokens): the selection by those counts overlaps the decode-trace selection by 90.4 % (mean, min
  86.1 %) at 216 and 84.2 % (min 75.5 %) at 192. Different texts (source and docs read, against model output), so
  this is not yet a statement about the model; it says that prefill-like text would pick other experts for about a
  tenth to a sixth of the places.

## Plan, second block: origin against bits (written before the runs; coordinator request after the first results)

Question: the bring-up file beat A, so does the origin of the weights (the Coder's tuned weights, not the Q8_0 base)
count more than the bits? Three arms, same method (KLD against the IQ1_M logits, same two texts, 50 chunks x 512), and a
larger tool-call test.

| Arm | What | Size (computed from the Coder header and the formats' bytes per weight) |
|---|---|---|
| D | pure cut of the Coder: byte copy of the Coder with 164 of 256 experts (selection `keep2` of the 118 K-token decode trace), no requantization; measures the loss of dropping alone | 4.451 GB non-expert + 25.146 GB x 164/256 = 20.56 GB trunk (160 experts would be 20.17 GB; 164 is the most that stays at or below 20.6 GB) |
| E | the Coder's own experts, all 256, requantized with the imatrix, the Coder's mix kept in order: gate/up IQ4_XS and IQ3_S -> IQ2_S (11 layers), IQ3_XXS -> IQ2_XXS (17 layers), IQ2_S -> IQ1_M (20 layers); down IQ4_NL -> Q2_0 (39 layers), Q2_0 stays (9 layers) | 15.965 GB experts + 4.451 = 20.42 GB trunk |
| Q8 | the Q8_0 base sliced to the Coder's 256 experts (`base-q8_0-256e.gguf`, 124 GB with the PLE table): PPL on both texts; as a second reference also its logits for KLD of every arm (6.3 GB per text) | read through the page cache, experts on the CPU; duration unchecked |

Why E cannot keep the Coder's mix: the Coder's experts are 25.15 GB (3.33 bits per weight on average). Down has 640
columns, so only the 32/64-block types IQ4_NL (4.5 bits) and Q2_0 (2.25) fit; every IQ4_NL down must become Q2_0, which
alone saves 4.6 GB. Then gate/up must fall to 10.49 GB at most; all IQ2_XXS is 10.38 GB. So the Coder's higher-precision
layers can only be paid for by IQ1_M in the layers where the Coder itself used IQ2_S (its lowest gate/up type); E does
that. Whether IQ1_M experts survive the imatrix coverage gap (1 to 5 experts per layer without statistics) is unchecked.

Expectation (all unchecked, no source for these models; wide tolerance):
- D: the cut keeps the Coder's weights exactly but removes 36 % of the experts per layer; the dropped gate mass on the
  trace is read from the select step. KLD between 0.3 and 1.5 on code; if D is below B' and C (0.305) the cut beats
  requantization at this size, if above, bits matter more than origin.
- E: KLD within 0.05 of the bring-up file (0.284 code, 0.485 text), sign open: the mix changes 48 of 144 gate/up
  tensors (20 go to IQ1_M).
- Q8 PPL: within 15 % of the IQ1_M Coder's (code 1.524, text 3.570). Below it: the IQ1_M quantization costs something
  against the base. Above it: the Coder's tuning fits these texts better than its base.
- Tool-call JSON: 32 prompts per arm (greedy, valid = a call with parseable arguments and a known tool name), arms IQ1_M
  Coder, A, B', C, bring-up, D, E. Expectation: Coder at least 30 of 32; the binomial standard error of a count near 26
  of 32 is about 2.2, so two arms differ only if more than about 4 apart.

Tooling: llama.cpp d9ee007 as before; every GPU run under `flock work/gpu.lock`; no Tona variables; quantization on the
CPU next to the runs (no effect on quality values).

- **Reading against the plan.** D: expected 0.3 to 1.5 on code, measured 0.106, **below the range** (the expectation had no

- **DM against D.** Using half prefill counts halves the code KLD (0.106 to 0.053) and lowers text KLD (0.252 to 0.199),

- **Per-layer expert counts (D2): not buildable now.** Both loaders bind every expert tensor to the global `n_expert`

  128 to 239. Parked as its own ticket. Not measured by KLD.
- **Q8_0 reference: not measurable here.** The base sliced to the Coder's experts (`base-q8_0-256e.gguf`, 124 GB with
  the PLE table at 54 GB) does not fit 60 GB of RAM; `llama-perplexity` on it ran for 87 minutes on one thread without
  finishing a chunk (code text) and was stopped (unexplained single-thread stall; not investigated further). Planned
  PPL of the base on both texts and KLD of every arm against the base: **open**.
- **Does Tona load a 164-expert file?** llama.cpp does (these runs). The reference megakernel uses a fixed router stride
  of 256 (`mb_.router + b * 256`, `float scratch[256]` in `mega_select.cpp`); whether it loads D or DM is unchecked.
- **Stop conditions the machine state met:** `quiet_check` after the second block (21:49): warning, load average 4.64 (the copy of
