# PLE table via io_uring instead of mmap, 2026-10-24, own measurement

The n-gram table (`per_layer_token_embd.weight`, 28.8 GB, IQ4_NL, 90 bytes per row) is in shard 2. Per token
16 random rows. Previously read through the mapping (mmap): every page fault blocks its thread, and in addition the
kernel reads ahead around every page.

Measured in the prefill (embedding of a chunk twice in a row): first pass 600–1,700 ms, second 8–14 ms.
So the time is only reading. More threads (24 instead of 6) made it slower.

## Micro-measurement (`ie-ple-io`, 32,768 random rows = one chunk of 2,048 tokens, 3 runs each)

Cold: the file's page cache emptied beforehand with `POSIX_FADV_DONTNEED`.

| Method | cold | warm |
|---|---:|---:|
| mmap, 6 threads (previous) | 396–416 ms | 3.8–4.6 ms |
| io_uring O_DIRECT (4 KiB sectors, btrfs) | 78–85 ms | 78–86 ms |
| **io_uring buffered, POSIX_FADV_RANDOM** | 102–107 ms | 12.8–13.1 ms |

Depth 64 and 256 almost equal (direct ~420,000 accesses/s over dm-crypt). Chosen: buffered, depth 256.

## In the engine (A/B alternating, `IE_PLE_IO=mmap` against io_uring)

| | mmap | io_uring |
|---|---:|---:|
| Prefill 12,000 tokens, cold | 995 / 1,019 tok/s | **1,146 / 1,150 tok/s** |
| Decode teacher text 600 tokens, cold, `IE_PLAN=gpu` | 28.9 / 29.1 tok/s | **30.3 / 30.3 tok/s** |
| Decode, warm (table entirely in cache) | 30.4 / 30.5 tok/s | 30.5 / 30.5 tok/s |

NLL bit-identical in each case (prefill 0.915200778, decode 0.960647814). After four runs only 21.2 of 26.8 GB
of the file were in the page cache: in operation the table is partly cold.
