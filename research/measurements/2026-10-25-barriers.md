# Waiting at the megakernel barriers, 2026-10-25, own measurement

Coder IQ1_M, drafter DFlash, 64 GB RAM. The desktop used 2.1 GB VRAM that evening (normally ~1.5), so only
80–81 expert slots per layer instead of 90; compare only within this series.

Recording: `IE_BAR_PROF=<file>` stamps the arrival of every block at every barrier, evaluated with
`scripts/barprof.py`. Throughput test `--batch-bench 600`, B = 4, real experts.

## Where the time of a pass goes (before, 41.15 ms with stamps)

| | ms per pass |
|---|---:|
| mean work per block | 32.8 |
| imbalance (the mean block waits for the last one) | 7.3 |
| barrier latency (last block arrived → release) | 1.0 |

The barriers themselves cost ~1 ms. The real loss is waiting for the slowest block, and a large part of that was
badly distributed work:

| Step | Finding (µs per step) |
|---|---|
| gr.down | inject (bf16, 4 × 10,240) used 4 waves in block 20, all 4 tokens one after another: 43 µs, the 320 rows of down 20 µs in blocks 0–19, blocks 21–31 empty |
| dn.conv | q/k heads (32 units, 4 tokens each one after another) in blocks 0–1: 17 µs, v channels 6 µs, blocks 14–31 empty |
| qsa.merge | 96 units of 8 × 32 values: 6 blocks at 25 µs |
| dn.recur | 384 waves = 24 blocks at 44.5 µs, 8 empty |

## Changes (all bit-exact: teacher NLL at `--slots 80`, 1,500 tokens, 2.186663409 before and after)

1. float tasks with at most 64 rows (`IE_MEGA_TSPLIT`, 0 = off): one unit per (row, token). gr.down
   43 → 20 µs.
2. dn.conv per (head or 32 channels, token); earlier tokens of the pass from qkv instead of from the ring. 17 → 8 µs.
3. qsa.merge per (token, head, 32 values). 25 → 12.5 µs.

Rejected: dn.recur spread over all 32 blocks (12 waves per block) 44.5 → 46.5 µs, with 16 instead of 8 rows in flight
55 µs. The waves wait for memory, not for the CU.

Throughput test, ms per pass (everything in one run per row, B = 1 … 4):

| | B = 1 | B = 2 | B = 3 | B = 4 |
|---|---:|---:|---:|---:|
| before (`IE_MEGA_TSPLIT=0`, dn.conv/merge new) | 23.22 | 30.78 | 36.66 | 41.28 |
| after | 23.28 | 29.70 | 34.87 | 38.99 |

B = 4 alone, 2 runs each: before (only `IE_MEGA_TSPLIT=0`) 42.49 / 42.13, with change 1 39.82 / 39.80, with 1–3 39.56 /
39.56 / 39.50. Afterwards imbalance 7.3 → 4.4 ms per pass.

Teacher text through the decode path (B = 1): 39.0 → 41.7 tok/s.

## Server (median of 3, 2 runs each, same conditions: 80 slots)

| Decode tok/s | before (0bb2024) | after | width table new |
|---|---:|---:|---:|
| csv | 88.5 / 88.5 | 88.9 / 89.2 | 89.3 / 89.3 |
| rust | 74.3 / 74.4 | 74.3 / 74.6 | 76.5 / 78.0 |
| explain | 58.5 / 58.6 | 58.7 / 58.7 | 55.1 / 56.0 |
| after 13K | 51.8 / 52.6 | 52.2 / 53.2 | 53.3 / 52.2 |

In the server almost nothing remains: it usually computes 2–3 tokens per pass, and the width is chosen from a fixed
table of pass times. With the new pass times in the table it chooses wider: rust +2–3, explain −3 tok/s. The
drafter's acceptance probabilities are too optimistic for prose; the old table compensated for that by chance.
Table therefore unchanged. Open: calibrate the drafter's confidences online, then update the table.

## What is left (waiting in µs per pass, B = 4, after)

| Step | Wait | Cause |
|---|---:|---|
| host.y | 735 | block 0 waits for the CPU experts |
| moe.down | 705 | blocks 16–31 ~7 µs slower (probably GPU-direct experts over PCIe on few waves) |
| gr.down | 591 | 320 rows of 10,240 on 20 blocks, x (40 KB) does not fit in the LDS |
| moe.shared | 443 | block 0 waits in host.wait for the CPU |
| dn.recur | 438 | 24 of 32 blocks, memory-latency bound |

For dependencies instead of barriers (variant 2) that leaves at most ~1 ms of latency plus the part of the imbalance
that can be overlapped instead of removed. Research on this: research/papers.md (MPK, Hazy, Cohere,
ForgeMegakernel). ForgeMegakernel still measures 218–304 µs of waiting per token on an H100 even with counters:
counters do not replace load balancing.

## Dynamic end of the matvec steps (rejected)

Microbenchmark: `atomicAdd` with return value from L2 0.22 µs (one wave), 0.30 µs (512 waves at once). Implemented as
fixed first rounds, the last `IE_MEGA_DYN` rounds per task from a counter (bit-exact). moe.gate_up afterwards
without imbalance, moe.down still ~4 % between the block halves. Pass B = 4: off 39.58 / 39.61, 1 round 39.48 /
39.46, 2 rounds 39.48 / 39.49, 4 → 39.45, 8 → 39.42; after rebuild 8 rounds 39.70 versus off 39.71, everything dynamic
39.87. No reliable gain, removed again.

## Efficiency of the dense matvecs (all experts in VRAM, B = 4, slowest block per step)

| Step | Shape | % of 315 GB/s | Loss per pass |
|---|---|---:|---:|
| dn.out | K-quants 2560 × 6144, L 32 | 54 % | 1.2 ms |
| gr.up / gr.down | Q8_0 10240 × 320 / 320 × 10240 | 59–60 % | 1.5 ms |
| qsa.out | Q6_K 2560 × 6144, L 32 | 55 % | 0.4 ms |
| router | bf16 256 × 2560 | 35 % | 0.4 ms |
| dn.in | K-quants 16K × 2560, L 16 | 84 % | 0.65 ms |
| head.out | Q6_K 248K × 2560 | 94 % | 0.1 ms |

`ie-gpu-matvec` alone: Q6_K (row 2560, 268 MB) 98 %, Q4_K 94 %, Q8_0 640 × 2560 64 %. The kernel is good as long as
many rounds per wave occur; with few long rows each lane waits for memory per sub-block.

- Fewer lanes per row (`IE_MEGA_LANES_MAX` 16 / 8): pass 33.46 → 35.08 / 37.14 ms.
- Preload the next sub-block (software pipelining in row_q8) for all: dn.out 2.62 → 2.24, qsa.out 0.87 → 0.71 ms,
  but gr.*, dn.in, head.out together +0.5 ms, pass 33.43 (same). Only for K-quants with L 32: dn.out 2.40, but
  dn.in and head.out are slower even without the branch (code and registers of the whole kernel), pass 33.70. Rejected.

## Preload the weights of the next step at the barrier (rejected)

After "No Bubbles" (Hazy Research): waves 1–15 of a block touch, at the barrier, the rows of their first unit of the
next matvec step (one 128-byte line per lane) when at least N blocks are still missing. Bit-exact.
Throughput test B = 4, real experts:

| | ms per pass |
|---|---:|
| off | 39.19 / 39.24 |
| 8 KB per unit, N = 3 | 40.73 / 40.77 |
| 2 KB, N = 3 | 39.53 |
| 8 KB, N = 12 | 40.51 |
| 1 KB, N = 12 | 39.19 |

The more is preloaded, the slower: the loads take bandwidth away from the blocks that are still computing the step
(critical path). The fixed cost per step is not a latency problem of the first loads.

## Variant B (dependencies instead of barriers) measured

Measurement modes (output meaningless): `IE_MEGA_NOBAR=1` (no barrier), `IE_MEGA_NOBAR_STEPS=a,b,…` (no barrier after
these steps), `IE_FAKE_ROUTE=1` (router values from a hash of position, layer, expert: the union of the
experts does not depend on the data). Throughput test, ms per pass.

| | B = 4 |
|---|---:|
| real experts, with barriers | 39.16 |
| real experts, without barriers | 23.55 (too favorable: meaningless data → all tokens choose the same experts) |
| `IE_FAKE_ROUTE`, all in VRAM, with barriers | 37.37 / 37.36 / 37.34 |
| same without barriers | 31.15 / 36.41 / 31.11 (scatters: races) |

Without barriers and with real experts: `HSA_STATUS_ERROR_MEMORY_FAULT` (moe.copy reads the plan while block 0 is
writing it). Only in the measurement mode, not used further.

With no barriers at all, steps run into each other that have real dependencies (a matvec needs the whole x); variant
B cannot do that. Realistic upper bound: drop barriers only where the next step needs local data (per head, per
expert, per row): after dn.in, dn.conv, dn.recur, qsa.in, qsa.attn, moe.gate_up, moe.act, moe.down, gr.up
(373 of 1,045 steps), `IE_FAKE_ROUTE`, all in VRAM:

| ms per pass | B = 1 | B = 2 | B = 4 |
|---|---:|---:|---:|
| with barriers | 21.01 | 27.51 | 37.35 / 37.36 |
| without the local ones | 19.76 | 26.13 | 36.05 / 36.09 |
| plus latency of the remaining ~670 barriers (0.98 ms for all) | ~0.6 | ~0.6 | ~0.6 |
| upper bound for B | −1.9 (9 %) | −2.0 (7 %) | −1.9 (5 %) |

The cost of the counters themselves is not subtracted (atomic 0.22–0.30 µs per access). The server usually computes
2–3 tokens per pass: realistically a few percent of decode. Worth doing later, with time limits at every wait as with
the barriers.

## Dependencies instead of barriers, first step: dn.in → dn.conv (`IE_DEPS`, default on)

Upper bound per step individually (barrier removed, `IE_FAKE_ROUTE=1 IE_FAKE_EXPERTS=1`, B = 4, 73 slots; baseline
36.98 / 36.96 ms): dn.in −0.19, dn.conv −0.20, moe.down −0.15, gr.up −0.15, moe.act −0.10, moe.gate_up −0.09,
dn.recur −0.08, qsa.attn −0.07, qsa.in −0.06 ms per pass.

Implementation: after dn.in every block reports `done[block] = step + 1` (release), dn.conv waits only for the blocks
that compute its rows of qkv (mask per width and block, computed on the host from the distribution of the matvec
units). First version with the old distribution of dn.conv: blocks 0–7 waited for 16–20 blocks, gain within the
noise (39.07 → 39.00 ms). Then the dn.conv units were placed on a block that computes their rows itself (table per
width in p[12]): every block waits for 4.

| ms per pass, B = 4, real experts | `IE_DEPS=0` | on |
|---|---:|---:|
| pair 1 | 39.10 | 38.99 |
| pair 2 | 39.12 | 39.03 |
| pair 3 | 39.12 | 39.04 |

−0.09 ms per pass (half of the upper bound). Bit-exact (teacher NLL 2.190080910, `--batch-check` 120/120), 13/13 tests.

## Rejected: gr.down in pieces per row (`IE_GR_KS`)

Idea: 320 rows of 10,240 occupy only 320 of 512 waves (12 blocks empty, wait 0.63 ms per pass). Split each row into ks
pieces (own units, partial sums without epilogue), gr.up adds them when loading in a fixed order.

| ks | 1 | 2 | 4 | 5 | 8 | 10 |
|---|---:|---:|---:|---:|---:|---:|
| pass B = 4 (ms) | 39.68 / 39.64 | 40.30 | 40.54 | 40.64 | 40.91 | 40.73 |

Profile: gr.down 2.37 ms (ks 1) versus 3.25 ms (ks 4). A wave waits for memory per sub-block; more units do not
shorten the longest chain (ks 4: 80 sub-blocks on 32 lanes = 3 rounds, 2.5 units per wave), plus butterfly and store
per unit. Even the branch in `units_loop_q8` cost all matvecs ~0.6 ms per pass (39.02 →
39.66 with ks 1). Removed.
