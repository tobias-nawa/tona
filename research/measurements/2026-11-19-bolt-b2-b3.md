### Expectation

- N5: int8 path 1e-5 or below (the products are exact integers, only the float summation order differs from double: typically 1e-7 to 1e-6). Activation step against float x: about 0.3 to 1 % of the sum of absolute terms per row, worst row around 2 % (source: int8 rounding with step max/127 per 32 values, uniform error, rms about 0.3 % of the row's rms for Gaussian x).
- CPU twin bit-equal for IQ2_XXS: the CPU applies the same float steps (`d/8 * (1 + 2 s)`, fma sequence of `apply_q8`).
- Speed: NVFP4 and IQ2_XXS are 4.5 and 2.06 bits per weight, so the unpacking costs more instructions per byte than Q8_0. Expectation for decode (1 token): 150 to 260 GB/s of weights (50 to 80 % of 320 GB/s; source: the IQ3_XXS and IQ2_S loops measured 60 to 80 % in `2026-10-23-matvec-int8.md` class results); a result under 160 GB/s (50 %) is a finding with its cause measured.
- N1: the probe kernel has the Coder's loops minus nothing plus two decodes: expectation below 192 VGPRs; the LDS table adds 2 KB.
- C1: identical for every existing kernel; new kernels only (the probe kernel and the standalone instantiations).

## Prior art

Change type: technique (kernels) behind a profile switch, plus host-only table entries.

- [llama.cpp PR 19769 (NVFP4 type)](https://github.com/ggml-org/llama.cpp/pull/19769) and the CUDA dp4a kernel (PR 20644, merged 2026-03; read in `ggml-cuda/vecdotq.cuh` of b11822), status: read. Adopted: the E2M1 codes doubled and read as int8 (`kvalues_mxfp4`) with `dp4a`, the UE4M3 scale per 16 weights. Improved: the scale is folded per 16 values into the existing two-half scale of `Dec`, so the loop, the wide path and the GEMM need no NVFP4-specific code; the table lookup is a `v_perm` sequence from registers (`lut16`), not a memory table.
- llama.cpp PR 21074 (generic NVFP4 MMQ) and the Blackwell FP4 tensor-core path (PR 22196, via secondary sources only, unverified), status: read (title level). Not adopted: gfx1200 has no FP4 matrix instruction; the prefill goes through f16 WMMA after unpacking.
- llama.cpp `vec_dot_iq2_xxs_q8_1` (and the RDNA4 WMMA-MMQ, PR 17156, merged 2025-11), status: read. Adopted: grid of 256 entries times 8 signed bytes, the sign by the 7-bit table. Improved: the grid is in LDS (2 KB) and signs come from the existing IQ3_XXS mask table, so a sub-block is 4 LDS gathers, 4 mask gathers and `v_xor`/`v_add` sign application; no per-value branch.
- The repository's own IQ3_XXS, IQ2_S loops (`matvec_q8_iq.h`) and the CPU `decode<18>` as the template; the Metal IQ2XXS decoder was not needed.
- No 2026 paper on 2-bit grid or FP4 kernels for gfx1200 was found by one web search by hand ("NVFP4 RDNA4 gfx1200 llama.cpp mmvq IQ2_XXS 2026": only CUDA and RDNA4 MMQ results). `tools/papers/scan.py` was not run for this ticket.

### Changes to the plan

1. The new kernels of `gemm_q` and `dequant_f16` could not stay in `gemm_q.hip` and `gemm_dequant.hip`: a first
   `isa-diff` showed 32 kernels of the Coder in those units "changed". The only difference was the PC-relative offset of
   the global tables (`s_add_co_u32 sN, sN, 0x6ed0` against `0x9ea8`): appended code moves the data, so every earlier
   kernel of a unit that references a table changes its constant. The new formats therefore have units of their own
   (`gemm_q_bolt.hip`, `gemm_dequant_bolt.hip`) and the shared kernel templates moved to the headers `gemm_q_dev.h` and
   `gemm_dequant_dev.h`. The standalone `matvec_q8` and the chain kernels in `matvec.hip` got no loops (a task of type 16
   or 40 in a `MatvecChain` throws).
2. A load variant for IQ2_XXS (three aligned words and `v_alignbyte` instead of four 2-byte loads) was measured and
   dropped: 118 against 127 GB/s at 1 token.
3. `dequant_f16` for the new unit first differed in half the IQ2_XXS values: the unit's own `upload_tables()` was not
   called (every unit has its own copies of the tables). Fixed; the test found it.

### N3: decode matvec speed against the bandwidth bound (by-product, **decode** rate of one matvec, no BENCHMARKS row)

One OP_MATVEC step in the real k_mega (probe profile), 50 repetitions, matrices of 69 to 103 MB (above the 32 MB cache),
two jobs (351.2 / 351.0 us and 544.1 / 543.1 us for the same cases: spread below 0.3 %). GB/s of weight bytes read; VRAM
bandwidth 320 GB/s (`docs/backends/reference-platform.md`). 8 lanes per row is the layout of expert groups, 32 that of a dense task.

| Format | Matrix | 1 token, 8 lanes | 1 token, 32 lanes | 4 tokens, 32 lanes | 8 tokens, 32 lanes |
|---|---|---|---|---|---|
| NVFP4 (new) | 32768 x 4096 | 215 GB/s (67 %) | **220 GB/s (69 %)** | 152 | 92 |
| IQ2_XXS (new) | 262144 x 1024 | **127 GB/s (40 %)** | 85 | 36 | 22 |
| Q8_0 (yardstick) | 16384 x 4096 | 225 (70 %) | 225 | 184 | 131 |
| IQ2_S (yardstick, Coder expert loop) | 262144 x 1024 | 149 | 97 | 44 | 25 |
| IQ3_XXS (yardstick, Coder expert loop) | 262144 x 1024 | 177 | 121 | 54 | 29 |

- **NVFP4** is at 98 % of what Q8_0 reaches in the same rig (225 GB/s is this method's practical ceiling, 70 % of the peak):
  the plan's expectation (150 to 260 GB/s) is met; go on.
- **IQ2_XXS** at 127 GB/s is 2.5x below the bound: outside the 2x go/no-go of N3. The cause was measured by comparison, not
  by profiler: per weight (not per byte) it decodes at 493 Gweights/s at 1 token, 8 lanes, against 463 (IQ2_S) and 460
  (IQ3_XXS) for the existing grid loops, which have the same structure (grid and sign tables in LDS, 4 table gathers and
  4 sign applications per 32 weights). So the loop is **limited by the unpacking, as the existing grid formats' are**
  (their bytes per weight are higher, hence their higher GB/s). At 4 and 8 tokens the unpacking is done once per token
  group but the multiply-adds grow, the same fall-off as the yardsticks. One tuning attempt (aligned loads) gave nothing.
  Whether a different unpacking (for example the sign application by `v_perm` from a 128-entry table in registers, or the
  Raw pipeline with the next sub-block's bytes in flight, which helped IQ4_NL only) closes the gap is not measured; it is
  its own tuning ticket (decision per N3: tuning is a later measured ticket, the cause being the unpack throughput).
  For Bolt decode this matters: 4.82 GB per token of expert weights at 127 GB/s is 38 ms, at the bound 15 ms.
- Not measured: a program of Bolt (no model module for the kernel yet); the expert-group path with several slots; the
  wide pass speed (WMMA, only checked for numbers); GEMM speed in TFLOPS (only numbers); `dequant_fp8` (compiled, no test).
