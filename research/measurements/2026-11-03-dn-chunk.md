## Result 2: prototype and kernel time (step 3 and 4)

**Code.** `engine/gpu/prefill_dn_chunk.hip` (two kernels), test `engine/tests/test_gpu_dn_chunk.hip` (ctest
`gpu_dn_chunk`, label `gpu`), launch `launch_dn_chunk`. Algorithm as research/13: per (block of 64, K head) the Gram
matrices `K K^T` and `Q K^T` once (WMMA f16, fp32 accumulator), then for each of the 3 V heads of that K head: gate
cumsum, `exp`, mask and `A` in fp32, the triangular inverse in fp32 (16 x 16 diagonal blocks by forward substitution,
the blocks below by block rows), `-W = -T (beta e K)` and `U^T = T (beta V)` (WMMA, `T` rounded to f16), `e Q`,
`r K^T`, `Aqk` to a workspace; `k_dnc_scan` walks the blocks of one V head in order with the state `S` in registers
(fp32 accumulator, f16 copy as WMMA operand) and writes `O` and the new state.
Measured against a plain fp32 reference this is `k_dn_wave` (token by token, fp32).

**Block rule (written down).** Blocks sit at absolute positions 64 b ... 64 b + 63 (`pos0 / 64 + c` in the piece).
A piece that starts or ends inside a block computes that block with the missing tokens padded (beta = 0, g = 0, q =
k = v = 0); padding changes neither the state nor the gate sum. A piece whose start and end lie on multiples of 64 has
no partial block.

**Accuracy** (`test_gpu_dn_chunk`, random data of the real shapes: 16 K heads, 48 V heads, 128, q and k unit norm,
v ~ 0.5 N(0,1); three gate regimes; relative RMS error against `k_dn_wave`, ie `sqrt(sum d^2 / sum ref^2)`):

| Case | output rms | state rms |
|---|---:|---:|
| mild decay, 2048 tokens, zero state | 5.5e-4 | 4.6e-4 |
| typical, 2048 tokens, random state, pos0 4096 | 5.1e-4 | 4.1e-4 |
| strong decay (g about -12 .. -24 per token), 2048 | 4.2e-4 | 3.1e-4 |
| 1000 tokens from pos0 37 (partial blocks at both ends) | 5.0e-4 | 4.1e-4 |
| 50 tokens inside one block / exactly one block / 8192 | 4.9e-4 / 5.0e-4 / 5.0e-4 | 4.0e-4 / 4.1e-4 / 4.1e-4 |

All finite. The error is that of f16 operands (2^-11 = 4.9e-4); the test limit is 3e-3. This is a kernel-level number
on random data, not the quality check of docs/backends/README.md (that follows on the real model when the speed question is
answered).

**Cut test (same file).** One piece of 2048 tokens against two pieces cut at 1024: output and state bit-identical;
cut at 1000 (inside a block): output differs in 3.6 % of the values (rms 5e-5), the state is still identical (the
decay in this regime is strong, so the state forgets the rounding difference; not evidence for other regimes).

**Kernel time, one DeltaNet layer (48 V heads), `test_gpu_dn_chunk --bench`.** Events around `calls` launches of
pieces of the given size, scaled to 12,288 and 131,072 tokens; 7 rounds after one warm-up; GPU at 3.2 GHz, 100 W
during the run (sysfs `freq1_input`). Min / median / max in ms:

| Piece | Tokens | `k_dn_wave` | chunk form | ratio (median) |
|---|---:|---|---|---:|
| 2048 | 12,288 | 29.72 / 29.77 / 29.98 | 15.11 / 15.13 / 15.15 | 0.51 |
| 2048 | 131,072 | 189.5 / 191.9 / 222.2 | 125.1 / 125.6 / 125.9 | 0.65 |
| 5120 | 12,288 | 16.93 / 17.34 / 17.71 | 11.90 / 11.92 / 11.93 | 0.69 |
| 5120 | 131,072 | 177.8 / 179.1 / 179.3 | 127.4 / 127.9 / 128.4 | 0.71 |
| 8192 | 12,288 | 16.37 / 16.87 / 17.53 | 11.59 / 11.60 / 11.64 | 0.69 |
| 8192 | 131,072 | 175.5 / 177.0 / 177.2 | 123.5 / 123.9 / 125.2 | 0.70 |

The 128K rows run longer (sustained clock, power), where the compute-heavy chunk kernels lose more than the
latency-bound sequential kernel. The ratio is **0.51 to 0.71**: at the limit of the ticket (<= 0.7), not clearly
below it for pieces of 5120 and 8192 tokens, clearly for 2048.

**What the kernel time consists of** (rocprofv3 kernel trace of the test, medians per launch; 5120 tokens): prep
3.06 ms, scan 1.4 ms (2048 tokens: 0.91 + 0.56 ms; `k_dn_wave` 2.7 ms there). Steps that mattered, each measured:

| Change | chunk form, ms per 12,288 tokens (5120-token pieces) |
|---|---:|
| first version (inverse: one column per thread in LDS, loop bound t - c) | 20.4 |
| inverse by 16 x 16 blocks | 15.3 |
| Gram once per K head for its 3 V heads | 13.0 |
| scan operands through LDS, 8 waves per block (62 KB for 4 waves left 2 of 6 blocks resident: 3 rounds) | 11.9 |
| prep LDS 57 KB -> 39 KB (3 blocks per CU pair instead of 2) | 11.9 (2048: 18.1 -> 15.1) |

Two things tried that did not help: a software prefetch of the next block's operands in the scan (856 vs 757 us),
and LDS staging with 4 waves per block (863 vs 757 us). Cause of the second one, checked in the resource usage: LDS
62 KB limits the block to 2 resident per CU pair, 6 are needed.

## Proposal: keeping the prompt cache cut-invariant (#81), not built

With the chunk form the state after a prefill depends on where the prefill was cut, unless the cut is a multiple of 64
(Run 3). A prompt-cache hit must compute what a cold run computes (docs/use/prompt-cache.md), so:

1. **Checkpoints at multiples of 64.** Wherever the code asks for a checkpoint at position p (start of the last
   message, fork, warm-up head, slice boundary of an interrupted warm-up: `Generator::checkpoint_at`,
   `prefill_warm`, `split_run` in `engine/server/run_split.h`), the prefill is cut at `p - p % 64` instead and the
   state is stored there. The request that continues from it prefills the tokens from there on (at most 63 more than
   with a cut at p, about 40 ms at 1,600 tok/s). The block grid is then the grid of a cold run: pieces start at
   multiples of 64, so no block is split, and the result is byte-equal (Run 3, first three variants). `run_split`
   states the rule in one place; the unit test of it covers any cut, so the change is one function plus its test.
2. **The last token** still goes through `forward` (decode path, token by token) as today; the padded tail block of the
   prefill is the same in the cold run and in the hit run, because both end the prefill at the same token.
3. **Disk checkpoints** hold the fp32 DN state, but its numbers differ between the wave kernel and the chunk form:
   `DISK_VERSION` must change (or the key must contain the DN form), otherwise a hit made with one form continues in the
   other and is not what a cold run gives.
4. **Prefill pieces made by the engine itself** (chunk 2048, 6144, group 12288) are multiples of 64 already; the
   `IE_PREFILL_CHUNK` clamp rounds to 128.
5. Open: the speculative verify pass and the commit of open tokens (`pending`) use the sequential form; they start at
   the end of a prefill and are not affected by the block grid (not tested here, ungeprueft).
Alternative not recommended: keep the last partial block's raw q, k, v, g, beta in the checkpoint and recompute; it
needs more state per checkpoint for the same effect as (1).

## Verdict

- The chunk form is **faster than `k_dn_wave` by a factor of 0.51 to 0.71** in kernel time (0.69 to 0.71 at pieces of
  5120 and 8192 tokens, 0.51 to 0.65 at 2048): at, not clearly below the limit of 0.7.
- End to end it gives **prefill +2.3 % (30K) and +1.8 % (130K)** (ab.py, 4 rounds, CI under 0.5 points), below the
  +3 to +5 % estimated in research/13; decode is untouched in code.
- Costs: workspace of 73.7 KB per (V head, block) in the prefill arena (117 MB at C = 2048, 457 MB at C = 8192, only
  with the flag); results differ from the sequential form in the f16 digits (relative 5e-4 per kernel; Δ-NLL on 16K
  tokens: code -0.0009, prose +0.0037 with upper end 0.0089); a prompt-cache change is needed for cut invariance.
- The sequential `k_dn_conv` (3.2 %), `k_dn_norm` (1.5 %) and `k_dn_l2` (0.8 %) are 5.5 % of the prefill GPU time
  together and were not touched; fusing them is a separate lever (ungeprueft how much).
