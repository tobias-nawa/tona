# Baseline on the Ryzen 9 9950X (#164): plan

Rule 2 plan, written before any run of this file. Results are read against it below the line `## Results` (added when the
runs happen). Build: current main `0fd36c4` (no engine change on this branch), built as `work/build/b164` through the CPU
queue. The 9600X baseline stays as the archive: `2026-11-14-scale-run.md` (build `7d7108a`).

## Question and decision

The reference PC got a Ryzen 9 9950X on 2026-11-17 (Zen 5, 16 cores / 32 threads, 2 CCDs; kernel 7.3.4; RAM, GPU, PCIe
unchanged). Owner decision (#164): Tona always uses the full CPU, no CCD split, no 9600X emulation. This file answers:

1. Which CPU thread count does the CPU expert path run with on this CPU (the engine pins 6 everywhere, see below)?
2. What is the noise of the workloads on the new machine (refreshes `bench/noise.toml`)?
3. What are the numbers of every scale-run block on the full 9950X, against the 9600X run and against the code changes
   since then?

## Why this size

- Step 1: question "6 or more threads for the CPU experts", answered by a rate that carries the CPU path: decode with MTP on
  the 2K prompts of `short` (400 tokens, verify passes with CPU experts and misses) and `set` (14 prompts, the production
  mix). Not `mid` or `long`: prefill runs its expert GEMM on the GPU, so the CPU threads do not move it; long contexts add
  nothing to the CPU question. Rounds: noise of `decode@2000` is 0.23 %, `decode-code` 0.07 % (df 2) from `bench/noise.toml`; the
  expected effect is a few percent, so 2 rounds decide it; `--max-rounds 4` is the ceiling. The old noise table is from
  the 9600X and unproven here, so `ab.py` needs at least 2 rounds until step 2 has refreshed it.
- Step 2: five fixed rounds, because the table needs at least five runs (df >= 4, `docs/contribute/measurement.md`). The workloads are
  the ones the table has entries for (`decode@2000`, `@30000`, `@130000`, `prefill@...`); `long` is needed for `@130000`.
- Step 3: the same blocks with the same sizes as 11-14, on purpose, so that the comparison is per block; one round each
  as then. No size change (`docs/contribute/measurement.md` scale-run recipe).

## Active tooling

  `TONA_EXPERT_PROFILE=work/profile/experts-coder.bin`; `OMP_NUM_THREADS` as the arm or the step-1 result says (written in each
  result row). No other `TONA_*` in the shell.

  i: llama.cpp with `--metrics`. `ab.py --load-log on` in step 1 (sums: ours, system, other; the CPU share of "own" matters here).
- Memory sampler 1 Hz in `curve.py` (RSS/HWM, GTT, VRAM, MemAvailable). Sums only, no program names.
- Thread placement: no `taskset` or CCD pinning (owner: no CCD split). The hw_report CPU line and the kernel's SMT state
  (`/sys/devices/system/cpu/smt/active`) are copied into the results.
