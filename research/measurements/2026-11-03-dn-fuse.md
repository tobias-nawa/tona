# DeltaNet prefill: fusing the small kernels (#30)

## Plan (written before any code or run)

**Question.** Are `k_dn_conv`, `k_dn_l2` and `k_dn_norm` bound by memory bandwidth or by launch/latency, and what
is the upper bound of fusing them, in ms and in % of the prefill GPU time?

**Step 1, analysis (no GPU run).** Bytes per call from the sizes of the dispatches in the existing profile
(`/var/tmp/claude/w30dn/prof1/run_kernel_trace.csv`, main 15bc6be, 13,327 tokens, pieces 5120 + 5120 + 3087,
see 2026-11-03-dn-chunk.md Result 1) against the measured time; reference rate 315 GB/s
(docs/backends/reference-platform.md). Gate of the ticket: upper bound below 1 % of the prefill GPU time stops the work.

**Step 2, if the bound is above 1 %: build.** `k_dn_conv` + `k_dn_l2` in one kernel (wave per token and q/k head;
the conv values stay in registers, the normalised values are written once). Same arithmetic order per value, so
bit-identical.

**Step 3, checks.** Build `work/build/w30fuse`, base build `work/build/w30fuse-base` (main 3a70f42); unit/golden
compare through `scripts/gpu-status.sh --own`, `IE_DETERMINISTIC=1` token comparison, `scripts/ab.py` workloads
mid and long, rounds from `bench/noise.toml`, `IE_DIAG=1`; 60 s between blocks, GPU lock.

**Expectation.** Gain in prefill rate = removed GPU time / 6264 ms. Derived in Result 1. Tolerance: +-0.5 points
(the kernel time of a deterministic prefill varies little, prefill noise 0.02 %).

**Active tooling.** `IE_DIAG=1`, `IE_DETERMINISTIC=1` for bit checks; no profiler during ab.py.

## Result 1: bottleneck and upper bound (analysis of the existing profile, 2026-11-03)

Dimensions: ch = 2 * 2048 + 6144 = 10240, 16 K heads, 48 V heads, head dim 128. Piece of 5120 tokens (72 of the
108 calls; the 3087 piece the rest). Times are the means per call of the trace.

| Kernel | Bytes per call (5120 tokens) | Time | Rate | Floor at 315 GB/s |
|---|---:|---:|---:|---:|
| `k_dn_conv` | 419 MB (read qkv 210 MB, write conv 210 MB; the four tap reads hit the cache, ungeprueft) | 2.125 ms | 197 GB/s (63 %) | 1.33 ms |
| `k_dn_l2` | 168 MB (read + write of q/k, 32 heads) | 0.542 ms | 309 GB/s (98 %) | 0.53 ms |
| `k_dn_norm` | 315 MB (read raw 126, read z 126, write o16 63) | 1.017 ms | 309 GB/s (98 %) | 1.00 ms |

- `k_dn_l2` and `k_dn_norm` sit on the bandwidth limit: only fewer bytes help, not a better kernel.
- `k_dn_conv` is at 63 % of the limit: 0.8 ms per call of headroom (latency of the strided tap loads, ungeprueft).
- **Fusion conv + l2**: the l2 pass (168 MB) disappears, the fused kernel moves 419 MB. Floor 1.33 ms against
  2.125 + 0.542 = 2.667 ms today: at most 50 %, 247 ms of 6264 ms = **2.0 % of the prefill GPU time** (upper bound).
  Part from l2 alone: 50 ms = 0.8 %; the rest only if the fused kernel also reaches the bandwidth limit.
- **Fusion norm into the end of `k_dn_wave`**: saves the round trip of `raw` (write 126 MB + read 126 MB); the new
  floor is z read + o16 write = 189 MB, 0.6 ms against 1.017 ms: at most 38 % of 95 ms = 36 ms = **0.6 %**, below the
  1 % gate, and `k_dn_wave` holds only 16 columns of a head per wave, so the norm over 128 values needs a cross-wave
  step (more complex, small gain). Not built.
- Decision: build conv + l2 (bound 2.0 %, above the 1 % gate). Expectation for ab.py prefill: +1.0 to +2.0 %.

## Result 2: fused `k_dn_conv_l2` in the real prefill (2026-11-03)

Code: `k_dn_conv_l2` in `engine/gpu/prefill_dn.hip` replaces `k_dn_conv` + `k_dn_l2` (one wave per token and q/k head
with the lane mapping and the order of the sum of the separate norm; one wave per token and 32 channels for v).
Builds: A `work/build/w30fuse-base` (main 3a70f42 plus the plan file), B `work/build/w30fuse`.

- **Bits.** `scripts/gpu-status.sh --own --build work/build/w30fuse --keep-going` (golden prefill + dflash, GPU plan,
  CPU plan, server, prefill): all identical, status `C5: golden identical`. In `ab.py` the text SHAs of A and B are
  equal at 30K and 130K, stable in all six rounds, expert hits and misses identical (files `-ab.md/.json`).
- **Speed** (`ab.py`, mid + long, 6 rounds AB/BA, `IE_DIAG=1`, plan in `-ab-plan.md`): **prefill** 30K 1883.8 ->
  1900.7 tok/s = **+0.89 % [+0.81, +0.96]**; **prefill** 130K 1786.6 -> 1800.2 tok/s = **+0.77 % [+0.75, +0.79]**;
  **decode** 30K +0.19 % [-0.15, +0.52], 130K +0.07 % [-0.41, +0.55] (equal, as expected).
- **Against the plan** (+1.0 to +2.0 %): both prefill results lie just below (finding). The gain equals about the
  l2 pass alone (0.8 % predicted). Hence the fused kernel did not get closer to the bandwidth limit than `k_dn_conv`
  was (63 %); the remaining headroom of the conv part is up to about 1.2 % of the prefill GPU time. Why the conv is
  at 63 % was not measured (ungeprueft; candidates: the four strided tap loads per output, one output per thread; a
  kernel that walks several tokens per thread and keeps the taps in registers would read each input once, with the
  same order of the sum).
- `k_dn_norm` was not fused (bound 0.6 %, below the 1 % gate, Result 1).
