  kernel for every type tried, the LM head most (+2.0 ms per pass on GGUF Q6_K). The probes said the opposite.

  kernels. None of these was checked one by one.

## Finding the gap (coordinator decision A): one difference per step

`bench/mac/densek` probe (scratch copies; dense mat-vecs, phased, K split 8, matrices ≥ 2048 rows on the MMA kernel,
median of 20 command buffers, ms), all in one session 14:40:

| Step | B1 | B4 |
|---|---|---|
| f32 R4 kernel (today) | 21.73 | 40.16 |
| MMA, GGUF types | 34.66 | 38.39 |
| MMA, Q6_K as the probe's fragment order (`d` per 32-weight chunk) | 30.01 | 33.93 |
| 1: `d` per row and super-block, as TONA_Q6_K_T | 29.71 | 33.57 |
| 2: + the engine's guards (columns past B selected to zero) | 33.87 | 44.43 |
| 3: + the engine's decoder (`RowAt<Q6KT>`, `spread_pairs`) | 33.56 | 44.17 |
| 2 without the selects (pointers clamped to column B − 1 only) | 28.16 | 32.80 |
| 3 without the selects | 27.32 | 31.95 |

The guards explain the gap: selecting zeros for the input columns past B costs 10.9 ms at B4. They are not needed
(output column j depends on input column j only, and columns past B are never stored); clamping the pointers keeps
the reads inside the buffer. The engine kernel now reads column B − 1 again for those lanes, and the LM head stays on
the f32 kernel.

## W2 finding: profile, cause, fix

Profile (`TONA_METAL_PROFILE=1`, `tona-bench -b 2 -p 64 -d 64 -r 2`, 96 passes, MMA off): DM-T against DM +420 ms,
of it dn_proj +272 and attn_proj +107 (the parts with the Q6KT matrices), everything else within ±12 ms.

Microbenchmark (scratch, Swift harness over `tona.metallib`: the `mv`/`mvs` kernels of the R4 path on the 128 Q6KT
matrices' real shapes and counts, Q6K against Q6KT, B = 1 to 4, median of 14 alternating command buffers):

| Variant | B1 (ms) | B2 | B3 | B4 |
|---|---|---|---|---|
| Q6K (GGUF) | 7.6 | 8.8 | 12.0 | 13.6 |
| Q6KT as built (`dec_tile` per row) | 7.1 | **11.8** | 11.6 | 15.0 |
| integer division `rs / 210` replaced by a multiply | 7.2 | 11.9 | 11.6 | 15.0 |
| `#pragma clang loop unroll(disable)` on the group loop | 7.2 | 11.9 | 11.6 | 15.0 |
| R = 8 (a simdgroup reads whole tiles) | 7.9 | 11.0 | 15.1 | 17.7 |
| decoder writing the weights in order (no float reorder) | 7.4 | 11.6 | 11.6 | 13.9 |
| **the 4 rows' fields of a lane in one load each** | **5.7** | **7.3** | **8.2** | **12.3** |

Per shape the B2 loss sat in every matrix, `mv` and `mvs` alike (30 to 50 %). The pipelines' register use was not
the cause: `maxTotalThreadsPerThreadgroup` of Q6KT is at or above Q6K's at every B (1024/896/704/640 against
896/768/640/576). Q6K is unusually cheap at B2 (+1.2 ms over B1, then +3.3 to B3), Q6KT grew evenly; which schedule
the compiler picks per instance is not visible without the GPU's ISA.

Cause and fix: the R4 kernel's rows r0 to r0 + 3 of a lane sit at entries e0 + o + 2r of the same tile (o = bit 0 of
the group), so their low-bit words, high-bit words, scales and `d` lie in 32, 16, 4 and 8 contiguous bytes. Read
row by row, every field took four loads of 1 to 4 bytes; `Rows<Q6KT, 4>` (`kernels/decode.metal`) reads each with
one aligned load and decodes the same values in the same order. Bit-identical: MTP dumps of DM-T (128 calls, they
carry the trunk state) old against new build byte-equal, with `TONA_METAL_MMA=0`; DM unchanged likewise.

Research (2026-11-12, web search over 2026-08 to 2026-11 plus the local llama.cpp checkout `d9ee007`; topics: Metal
quantized mat-vec at 2 to 4 rows, row-interleaved weight layouts):
[cancho-gpu #24](https://github.com/alpibrusl/cancho-gpu/issues/24) (Metal NVFP4 mat-vec) names the same conflict:
a simdgroup reading contiguous bytes of one row against a row-interleaved layout, too few bytes in flight per
thread, helped by wider loads; [llama.cpp #29869](https://github.com/ggml-org/llama.cpp/pull/29869) (few-row MMA
mat-mul for speculative decoding, and a 2-row Q4_0 mat-vec variant) and llama.cpp's `mul_mv_ext` kernels for 2 to 8
rows read K-quants from GGUF order, one row per lane group, no tile layout. None names the B = 2 anomaly itself; the
fix follows cancho-gpu's direction (a lane's data in one vector load).
