# TONA_Q6_K_T (type 1019) on the reference GPU: +0.9 % decode code, bit-identical, the probe overstated it (#130)

RX 9060 XT (gfx1200), Zen 5. Branch `130-pc-q6k-tile` from main 6a8e859. Mac result to compare with: W1 -2.1 ms, W2 -1.5, W3 -3.5,
W4 -2.0 per pass (`2026-11-12-mac-q6k-tile.md`, run 6), server decode code +4.3 % (`2026-11-12-mac-dmt-server-ab.md`).

## Plan (written before the first run)

**Question.** Does reading the Q6_K layer matrices as tiles of 8 rows (1019) shorten the dense Q6_K work of a pass on RDNA4,
at W = 1..8, with identical outputs?

**What is Q6_K in the reference model** (`tools/gguf_info.py --tensors`, shard 1): layer matrices (blk.*) 1,356 MB over 9 names
(attn_qkv 473, ssm_out 374, attn_gate 181, attn_output 142, attn_q 129, shexp up and gate 35, attn_k and attn_v 23); k = 2560 for
840 MB, k = 6144 for 516 MB. Not eligible for 1019 (read by row or not a blk.* matrix): `output.weight` (521 MB, Q6_K). The
dense share per pass is 4.11 GB (reference-platform.md), so Q6_K layer matrices are about a third of it; at the measured
315 GB/s 1.36 GB take 4.3 ms, at the 125..191 GB/s the probe measured for Q6_K (2026-10-25-width-8.md) 7 to 11 ms. That bounds the
gain: the time now minus 4.3 ms at the bandwidth limit, and only if the CU loop (#128) allows it.

**Scope.** `tona-wide-probe --tile --cap 256 --runs 20` (new mode): the Q6_K blk.* matrices of k = 2560 and k = 6144 joined to 256 MB
(above the Infinity Cache), per W = 1..8 two kernels, each with GGUF order and with tile order: (a) the int8 row kernel as `row_q8`
(G = 2, L lanes per row, x in LDS, 32 blocks x 16 waves as k_mega; used at W <= 4 and for rows < 4096), (b) the WMMA kernel as `k_wide`
(rows >= 4096 at W >= 5). x of the tile run is permuted inside each 32-block so that every integer sum is unchanged. The tile
decoder reads 2 x 8 B + 2 x 4 B + 2 B + 2 B of the tile per sub-block instead of 32 x 2 B + 3 x 4 B; the unpacking costs about
12 more ALU ops. Outputs compared bit for bit. Duration: under 2 min of GPU.

**Expectation (with tolerance).** From #128 (CU loop, not DRAM, limits) and the load count: row kernel at W = 1 gains 5 to 25 %
of the Q6_K time (the 32 two-byte loads per sub-block go to 7 loads), shrinking with W as dot work grows; WMMA kernel gains
0 to 15 %. Per pass at most 1 to 3 ms. A difference inside +-3 % of the probe time (median of 20, two repeated sessions) is no effect.
Output: bit-identical for the row kernel (integer sums, same float order); the WMMA kernel may differ by the WMMA-internal
summation order (reported as error, not assumed).

**Active tooling.** Probe only (no engine run, no TONA_* variable). The machine is shared with other helpers through
`scripts/gpu_queue.py`; each run holds the lock alone.

## Deviations from the plan

1. The first probe (kernel launched with 32 blocks and 61 KB of LDS, one block per CU) showed tile 1.52x faster at W = 1 (row kernel,
   1388 against 914 us per 268 MB). That baseline was an artifact: the existing `k_probe` (run_phase, 64 blocks, 25 KB LDS) on the same rows
   reads 275 GB/s at nb = 2, my GGUF row kernel 174 GB/s. With the occupancy of `k_probe` (dynamic LDS `8 in + 8 in / 32 * 8`, 2 blocks per CU,
   `TONA_PROBE_BLOCKS_PER_CU`) the GGUF row kernel is at 266 to 281 GB/s and the tile gain falls to 1.04 to 1.10x. Only the second probe is
   reported below. The engine measurement decides anyway: the engine's dense ops already run at 291 GB/s (below).
2. The plan said "only on a clear gain" for the engine decoder. The probe gain was small, but the tile file is the one the Mac reads (a
   PC engine that cannot read it refuses the whole file), so the decoder was built to measure the real pass, the production A/B and the goldens.

## Results

### 1. What is Q6_K and the bound of the gain

Q6_K layer matrices (blk.*): 1,356 MB in 128 tensors (attn_qkv 473 MB, ssm_out 374, attn_gate 181, attn_output 142, attn_q 129, shexp 35,
attn_k and attn_v 23); `output.weight` (521 MB, Q6_K) is read by row and stays GGUF. Dense ops of the pass (profile, base build, W = 1): dn.in 4.04 + dn.out 2.09 +
gr.down 2.09 + gr.up 1.99 + qsa.in 1.26 + qsa.out 0.65 + head.out 1.62 + moe.shared 0.40 = 14.1 ms for 4.11 GB, i.e. **291 GB/s of the measured
315 GB/s**: the dense work of the pass is within 8 % of the bandwidth limit, so at W = 1 no layout can win more than 14.1 - 13.0 = 1.1 ms over *all* dense
formats; the Q6_K part of it is 1.36 / 4.11 of that. At wider passes the unpacking work grows (#128: CU loop) and the layout can gain more.

## Verdict

Tile layout on RDNA4 / HIP: **no gain at W = 1..4, 0.1 to 0.5 ms at W = 5..8, +0.9 % production decode on code (CI just above zero), +0.6 % on text (open)**, bit-identical in
every check. Not the Mac's 4 %. Why: the dense matvec phases of the pass already run at 291 of 315 GB/s, so fewer and aligned loads buy only where the unpacking work grows
(wide passes). Cost of taking it: 12 small edits in the device code (one new header `gpu/matvec_q8_tile.h`, about 70 lines), the PC then reads the same file as the Mac
(a tile file is refused by the old HIP engine). Whether PC users get a tile file or the GGUF-order file is a distribution maintainer decision; the code reads both.

## Principle 8

The gain is small, so it was weighed, not dropped: reasons it is not larger (bandwidth-bound dense phases, 291 of 315 GB/s), fresh search (below), cost attempt: the cost
of a second file variant does not arise if the Mac's DM-T file is the shipped one (the PC engine reads it with this change); re-tiling at upload (no file variant) was not tried because
it would copy 1.36 GB per start and every other reader of the weights (prefill, CPU) would need the tile order too (ungeprueft: load time).
