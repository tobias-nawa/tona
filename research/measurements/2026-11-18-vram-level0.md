# Level 0 of the compositor survival test: a polite foreign GPU program next to Tona (#166)

Plan, written before any run (2026-11-18). Level 0 of [research/62](../62-compositor-survival-test-plan.md) is approved by the maintainer; **level 1 (taking the card to full) is not approved and is not built or run here.**

## Question and decision

Question: while a second GPU program takes up to 1.25 GiB of VRAM in 64 MiB steps (and never takes the card below 1.5 GiB free), what does it cost Tona (decode rate, queue eviction time), what does the program pay (allocation latency), and does a headless Vulkan client (the stand-in for the compositor: one 64 MiB VRAM buffer, one command submission every 100 ms) see any failure or stall? This is the "no pressure" level: no eviction is expected, so it **cannot** show whether chunked slots or the GTT margin protect a desktop; it measures what a polite program costs and whether the tools work.

Decision per outcome: any canary error or kernel-log abort line at level 0 (where free VRAM stays above 1.5 GiB) is a finding that stops the whole ladder and goes to the maintainer; a decode loss in the balloon phase against the base phase above 1 % is quoted per arm; all arms equal and no error: level 0 is clean and the tools are ready for a level-1 decision, which stays with the maintainer.

## Tools (all new, gate-clean, unit-tested without a GPU: `tools/tests/test_vram_guard.py`)

| Tool | Role | Hard rules in code |
|---|---|---|
| `tools/vram_guard.py` | the rules as pure functions | free VRAM = `mem_info_vram_total` - `mem_info_vram_used` of card1; `may_allocate` refuses any step that leaves less than 1.5 GiB free; an unreadable counter refuses (fail closed); kernel abort pattern (GPU reset, ring timeout, "Not enough memory for command submission", `amdgpu_vm_validate() failed`) |
| `tools/vram_balloon.py` | the balloon: `hipMalloc` (ctypes), 64 MiB steps, 2 s pause, hold 20 s, release | reads free VRAM before EVERY allocation; step cap 20 (1.25 GiB at most); STOP file, kernel log, time cap 15 min, SIGTERM; frees on every exit path; checks that HIP device 0 is the card whose sysfs it reads (bus id); heartbeat file every second; no memset, no kernel |
| `tools/vram_watchdog.py` | separate process | kills the balloon and the canary by PID (SIGKILL) when the heartbeat is older than 5 s or the job is gone; ends when the balloon ended itself |
| `bench/micro/vram_canary.cpp` | headless Vulkan client, discrete GPU only | a 64 MiB device-local buffer, a recorded command buffer with a fill, one submit and fence wait per 100 ms (fence timeout 5 s); prints latency per submission; the first failed call prints the error and exits with 2 |
| `tools/vram_level0.py` | one arm per call | starts the Tona server (port 8099, systemd scope with memory limit), a decode loop (400 tokens per request), the canary, then phases base (40 s), balloon (ladder + hold, at most 120 s), after (30 s); stops at the first stop rule (STOP file, kernel log, canary error, time) |

Graphics API check (no root): Vulkan instance version 1.4, device 0 is the RX 9060 XT (RADV GFX1200), render nodes are world-readable, `vkCreateInstance` works in this session (`vulkaninfo --summary`). HIP is the toolchain's `libamdhip64`.

## Scope

- One queue job per arm, kind **exclusive** (monitors off by the desktop guard; exit 75 means requeue). Arms in this order: default, chunked (`TONA_SLOTS_CHUNKED=1`), margin (`TONA_GTT_MARGIN_MB=3072`), both. Build `b164t`, context 140000, model and drafter as in `scripts/ab.py`.
- **Every arm also sets `TONA_VRAM_RESERVE_MB=3072`** (documented knob; default 1024). Why: with the default reserve Tona leaves about 1 GiB free, which is below the balloon's floor, so the balloon would take nothing and level 0 would show nothing. With 3072 the card has about 3 GiB free after the start, so the balloon can take its 1.25 GiB and still leave 1.5 GiB or more. The arms differ only in their own variables. (The reserve costs Tona some expert slots, so the absolute decode rate is below the production value; only the phases within one arm are compared.)
- Per arm: server start, 10 s settle, 40 s base, balloon phase, 30 s after. Wall time per arm about 6 to 8 minutes (model load dominates), 30 minutes in all. Run once per arm; no repeat unless a finding needs it.

Why this size: the question is whether the tools behave and whether a polite program is visible at all. A decode request is 400 tokens (about 5 s), so each phase holds 6 to 25 requests; that resolves a 5 % loss, not 0.5 %, which is enough here: a loss of 5 % or more would be a finding, anything below is "no visible cost". More rounds are not asked for: this level has no eviction, so the arms are expected to be equal and an A/B with CI is not the question.

## Expectation (with source)

| Quantity | Expectation | Source |
|---|---|---|
| free VRAM when the server is ready | about 3.0 GiB, tolerance 2.5 to 4.0 GiB | reserve 3072 MiB (`engine/gpu/mega_build_slots.cpp` reads `TONA_VRAM_RESERVE_MB`); research/61: the reserve is the free VRAM the plan keeps, plus rounding to slots |
| balloon steps taken | 20 (1280 MiB) if free at the start is 2.8 GiB or more, otherwise `(free - 1.5 GiB) / 64 MiB` | the rule itself |
| lowest free VRAM during the balloon phase | at least 1.5 GiB (hard rule); about 1.7 GiB if all 20 steps are taken | by construction |
| allocation latency per step | under 50 ms, no outlier over 500 ms | a guess: a 64 MiB VRAM allocation without eviction; **no earlier measurement exists**, so a value outside is a finding, not a failure |
| canary submissions | one per 100 ms, latency p50 under 1 ms, p99 under 20 ms, max under 100 ms, zero errors | a guess for a 64 MiB fill on an idle queue next to a decode loop; no earlier measurement |
| Tona decode, balloon phase against base phase | within -1 .. +1 % (nothing is evicted, no GPU work is added by the balloon) | research/62 section 3, level 0: "no eviction expected" |
| `evicted_ms` of the server (KFD) | unchanged (0 s of growth) | same |

A result outside the table is a finding. Level 1 stays unapproved whatever the outcome.

## Active tooling

`TONA_VRAM_RESERVE_MB=3072` (all arms, see above) and the arm variable(s); no `TONA_DIAG`, no profiler. The orchestrator samples the card's free VRAM and GTT use at 2 Hz and follows the kernel log (`journalctl -k`, lines scrubbed of program names). No governor (`TONA_VRAM_GOVERNOR` off). Test conditions: `tools/hw_report.py` and `tools/quiet_check.py` before and after every job into `/var/tmp/claude/166/level0-<arm>.tc`.

## Stop rules in force

Free VRAM below 1.5 GiB before any step (balloon), STOP file `DIR/STOP` (within 0.5 s), kernel log abort line, canary error, decode request error, 15 min cap, heartbeat older than 5 s (watchdog), job gone (watchdog). A stop is reported, not retried.

## Results (run 2026-11-18, build `b164t`, tools at the commit with the shutdown fix; one queue job per arm, exclusive, desktop guard on, no requeue)

Summaries (sums and times only): `2026-11-18-vram-level0-runs/<arm>-summary.json`, test conditions (`hw_report`, `quiet_check` before and after) `<arm>.tc.txt`. A first default-arm run ended with exit 3 only because the decode loop counted the request cut off by the server shutdown as a failure (a tool bug, fixed and unit-tested); its phases were complete and equal to the rerun (decode 79.4 / 80.4 / 80.4 tok/s, balloon free minimum 1717 MiB), the rerun replaced it and all four arms ran with the fixed tool. Smoke test before: canary and balloon on the idle card, 6 steps, 129 submissions, no error.

Balloon: every step allocated in 0.1 to 0.2 ms (no eviction), all 20 steps, held 20 s, released on its own; the free VRAM never went below 1.5 GiB (the lowest reading was 1701 MiB). No stop rule fired in any arm.

Against the plan:
- free at ready 3.1 GiB (expected about 3.0, 2.5 to 4.0): as expected. Steps 20 as expected. Lowest free about 1.7 GiB as expected.
- Decode balloon phase against base: +0.16 to -0.01 %, inside -1 .. +1 % in every arm. `evicted_ms` did not grow in any arm: no eviction, as expected at this level. The `evicted_ms` of 1.8 to 2.1 s present before the base phase is from the start-up itself.
- Allocation latency: 0.1 to 0.2 ms, far under the guessed 50 ms (hipMalloc of 64 MiB at this level does no eviction work).
- **Outside the expectation: canary latency.** p50 is 14 to 15 ms and p99 about 54 ms in every phase of every arm, including the base phase (before the balloon), against a guess of p50 under 1 ms and p99 under 20 ms. The same canary on the idle card (smoke test, no Tona) had p50 about 1 ms and max 1.4 ms. So the cost is the submission waiting behind Tona's compute work on the shared GPU, not the balloon: it does not change with the balloon, the arm, or the phase. Not tested further; the reading (queue sharing with the persistent kernel) is from this comparison only. It also means the canary at this level says nothing about the memory path; a compositor frame would wait about the same.
- Between the arms: decode 80.2 to 80.9 tok/s, margin and both about 0.6 % above default and chunked in all three phases; that is the start-to-start spread of the arms, not a phase effect (the phases within an arm are equal), and one run per arm cannot rank the arms. Canary p50 in margin and both is about 1 ms lower, likewise unranked.

## What level 0 says about chunked and margin

By its construction (free VRAM never below 1.5 GiB, nothing is evicted) level 0 **cannot show whether chunked slots or the larger GTT margin protect the compositor**: no arm differs from default in any quantity that depends on eviction (`evicted_ms` is flat in all four, the canary has no errors in all four, including default). The coordinator's rule for adopting chunked as default (it must measurably help the canary or Tona's eviction behaviour at level 0) is therefore **not met, and could not be met at this level**: no benefit, no cost, outside the 0.1 % noise of the phases. What a benefit would need to be measured on is level 1 (taking the card to full), which is not approved and was not built.
