# Prefill v1: own path with WMMA GEMM

Own measurement, 2026-10-23, ~20:00–20:20. Old model (coder-iq1_m), 64 GB RAM, `IE_PLAN=gpu`, profile
experts-coder.bin, text: `git show ef8dc3d:engine/gpu/mega.hip`. One run per row.

## Accuracy (perplexity of the next token)

| Text | Decode path (megakernel, int8) | Prefill (f16 GEMM) |
|---|---:|---:|
| 2,000 tokens | 6.049 (NLL 1.7999) | 6.055 (NLL 1.8009) |
| 6,000 tokens (with indexer selection from position 2,051) | 3.186 (measurements/2026-10-23-kv-int8) | 3.188 |

The deviation of 0.1 % is the different rounding (f16 weights and activations instead of int8). From 2,051 tokens
the indexer selects blocks; this part also matches.

## Speed

| | Tokens | Chunk | tok/s |
|---|---:|---:|---:|
| Decode path (passes of 4 tokens) | 2,000 | – | 26.4 |
| Prefill | 2,000 | 1,024 | 335 |
| Prefill | 6,000 | 1,024 | 252 |
| Prefill, with LM head for all tokens (teacher) | 4,096 | 1,024 / 2,048 / 4,096 | 274 / 390 / 494 |
| Claude Code request (ie-gpu-gen with drafter) | 7,454 | 1,024 | 258 (29 s instead of 204 s) |

Expert slots per layer in VRAM at chunk 1,024 / 2,048 / 4,096: 102 / 97 / 89 (the working memory of the prefill
comes out of the slots).

The answer to the Claude Code request is "hello from local" on both paths (the thinking part before it differs in wording).
Drafter after the prefill: 2.84 tokens per pass (decode path 2.68), so its context arrives. Decode afterwards 21.9 instead of
24.8 tok/s: the VRAM cache of the experts is not refilled during the prefill (hits 70.5 instead of 82.6 %).

## Where the time goes (rocprofv3, 4,096 tokens, chunk 1,024, 12.4 s GPU time)

| Kernel | Share |
|---|---:|
| GEMM | 35 % (≈ 12 TFLOPS effective; experts with ~40 tokens per tile of 128) |
| Unpacking (all formats) | 32 % (experts: reading 25 GB per chunk, writing ~100 GB f16) |
| Attention (scalar, block per token and head) | 22 % |
| DeltaNet recurrence | 3.4 % |
| Rest (norms, mixing, routing, scatter) | ~7 % |

Wall 15 s against 12.4 s GPU: waiting for the count of experts per layer and embeddings on the CPU.

## Next steps

1. Pull unpacking into the GEMM (read expert weights in their format, convert to f16 in the LDS): saves the 32 % and the
   working memory for large chunks.
2. GEMM tile of 64 tokens for experts with few tokens.
3. Attention on WMMA (flash attention over the int8 KV).
4. Fill the VRAM cache with the most used experts after the prefill.

## Addendum ~20:30: attention with WMMA, unpacking in the GEMM, experts via copy stream

6,000 tokens of code, chunk 2,048, with LM head for all tokens (teacher), 2–3 runs each:

| State | Perplexity | tok/s (prefill) |
|---|---:|---:|
| v1 (scalar attention, experts unpacked to f16) | 3.188 | 252 (chunk 1,024) |
| attention with WMMA (12 q heads of a KV group as tile rows, flash softmax) | 3.187 | 505 / 540 |
| + gemm_q (unpacking in the LDS, int8 unpacker from matvec_dev.h) | 3.187 | 560 / 477 / 559 |
| + pinned experts per batch in one piece into VRAM (copy stream, two buffers) | 3.187 | **744 / 743 / 744** |

- Without the copy stream gemm_q read the weights of pinned experts directly over PCIe, 18–98 bytes per
  row scattered per K step: k_gemm_q<IQ4_NL> 921 µs per batch against 250 µs from VRAM (ie-gemm-check).
- gemm_q computes bit-identically to unpacking + f16 GEMM (ie-gemm-check, all 6 formats of the experts).
- The spread before the copy stream (477–560) probably came from reading over PCIe; afterwards ±0.1 %.
