# Mac M1 Max: whole passes on a synthetic model in full size (decode and prefill)

First end-to-end speed of the Metal backend (`engine/backend/metal/`, commit 3c2147b): decode at pass widths 1 to 4
and prefill in passes of 8, on a synthetic model with the shapes of the Coder and the expert types of variant A, before
the real model of the variant exists. Raw rounds: [2026-11-11-mac-synth.jsonl](2026-11-11-mac-synth.jsonl).

## Plan (written before the run)

**Model.** `tools/make_synth_model.py --experts 128` (seed 1): 48 layers, d 2560, the Coder's shapes and its types per
role, routed experts gate/up IQ2_XXS and down Q2_0 (variant A). 12.36 GB of tensors; per decoded token 4.53 GB read
(3.90 GB non-expert matrices incl. LM head, 10 of 128 experts per layer), 13.6 ms at 334 GB/s
([2026-11-11-mac-bandwidth.md](2026-11-11-mac-bandwidth.md)). Control: the same with 64 experts (8.33 GB, 4.51 GB per
token). Assumptions, as agreed with the maintainers:

- 128 instead of 256 experts, so the model stays resident beside the other work on the machine (swap already held
  12.0 GB before the run). The expert kernels read exactly 10 experts per token (no sharing between the tokens of a
  pass), so the bytes per token do not depend on the expert count; what can differ is cache reuse when two tokens
  pick the same expert (more often with fewer experts). The 64-expert control shows whether the count is visible.
- Random weights route uniformly over the experts; for a resident model that changes nothing.
- The n-gram (PLE) table has 16 heads of ~65 k rows instead of 320 M rows (~29 GB); a token reads 16 rows of 160
  values either way.

**Fixed.** `TONA_SEQS=1`, `--ctx 4096`, no other `TONA_*` variable. Builds: `work/build/mtl` (kernels without fast
math, the default since 3c2147b) and `work/build/mtl-fast` (`-DTONA_METAL_FAST_MATH=ON`, same commit) as the arm for
the cost of bit-identity. No profiler, no diagnostics.

**Runs.** `tona-bench MODEL -p 256 -d 64 -b B -r 3`: per process one warmup round (not counted) and three rounds, each a
reset, a prefill of 256 tokens (passes of 8) and 64 decoded tokens in passes of B, every pass committing all B. One
process per row below, in this order, 30 s pause between processes, the free memory and swap before and after each:

| # | Model | Build | B | Purpose |
|---|---|---|---|---|
| 0 | 128 | mtl | – | `tona-check -n 6 --widths 1`: top-1 against the CPU reference and width bit-identity on 48 layers |
| 1–4 | 128 | mtl | 1, 2, 3, 4 | decode per width; prefill in every process |
| 5–6 | 64 | mtl | 1, 4 | expert count control |
| 7–8 | 128 | mtl-fast | 1, 4 | cost of the kernels without fast math |
| 9–10 | 128 | mtl | 1, 4 | repeat of 1 and 4 at the end: drift over the run |

About 30 s of full GPU load per process, ~10 min in all with the pauses.

**Expectation** (from the kernel measurements of the same day: dense mat-vecs 21.5 ms at B = 1 and 39.9 ms at B = 4
([2026-11-11-mac-densek.md](2026-11-11-mac-densek.md)), experts ~10 ms per token at B = 1
([2026-11-11-mac-expertk.md](2026-11-11-mac-expertk.md), IQ2_S/Q2_0 as the nearest pair; IQ2_XXS unmeasured), DeltaNet
0.9 ms, ~1,700 dependent dispatches at 2 µs ([2026-11-11-mac-dispatch.md](2026-11-11-mac-dispatch.md))). The expert
mat-vecs run one slot per (token, expert), so expert time grows linearly with B:

| Rate | Expected | Tolerance | Derivation |
|---|---|---|---|
| decode B = 1 | 27 tok/s (36 ms per pass) | 20 to 33 | 21.5 + 10 + 0.9 + 3.4 + ~0.5 host |
| decode B = 2 | 37 tok/s (54 ms) | 26 to 48 | dense ~28 (interpolated) + experts 20 |
| decode B = 3 | 43 tok/s (69 ms) | 30 to 56 | dense ~34 + experts 30 |
| decode B = 4 | 47 tok/s (85 ms) | 33 to 61 | dense 39.9 + experts 40 |
| prefill, passes of 8 | 48 tok/s (165 ms per pass) | 35 to 65 | two mat-vec dispatches of 4 (2 × 39.9) + experts 80 + per-token indexer and attention |
| 64 against 128 experts | equal | ±3 % | same bytes per token |
| fast math against without | 0 to 10 % faster | –3 to +15 % | the compiler may fuse and reorder the sums; unmeasured |
| rounds within a process | spread ≤ 3 % | ≤ 5 % | kernel benches of the day repeated within 1 % |
| swap growth over the run | 0 to 2 GB | ≤ 4 GB | 12.4 GB of model pages against ~17 GB free and inactive |

A value outside its tolerance is a finding and gets a cause or a hypothesis below.

## Plan of the second set (written before it ran, 15:40)

The first set stopped after process 7 (the shell that ran it was closed; rows 8 to 10 are missing). Since then the
other project no longer runs on the machine; the maintainers asked for the real expert count of variant A.

**Model.** `make_synth_model.py --experts 256`: 20.41 GB of tensors, 4.54 GB per decoded token (10 of 256 experts;
same bytes as with 128, as computed above). Control: the 128-expert file of the first set.

**Memory.** Swap still holds 11.75 GB (pages of processes that still live; macOS frees swap only when the pages are
read back), 15.3 GB free + inactive, ~5 GB in the compressor, 3.5 GB wired; most "active" pages are the file cache of
the synthetic files, which the system can drop. 20.4 GB of weights plus ~1 GB of buffers therefore push 1 to 3 GB
out. Risk: weight pages dropped during the rounds and read again from the SSD, which would slow the passes. The runner
records page-ins and swap-ins before and after every process. **Validity rule:** page-ins of a process (16 KB pages)
at most 1.1 × the model file (the first touch); above that, weights were read again during the rounds and the row is
invalid, not slow.

**Step 0, already run.** `tona-check -n 6 --widths 1` on the 256-expert file first failed: one no-copy buffer per file
cannot exceed `maxBufferLength`, 20.10 GB on this machine, and the file has 20.41 GB (so would the real variant A).
Fixed in 7a51ce6 (page-aligned buffer windows that hold whole tensors). Then: 12 of 12 steps top-1 equal to the CPU
reference (worst relative deviation 5.67e-6), 0 of 24 rows of the widths run differ. The CPU reference beside the GPU
pushed swap from 11.75 to 13.47 GB; afterwards 21.9 GB free + inactive. Both builds of the second set are at 7a51ce6;
the 128-expert control rows make the sets comparable.

**Read against the plan:**

- **Decode B = 1: 21.2 tok/s (47 ms per pass)**, inside the first plan's tolerance (20 to 33) but below its 27: the
  parts of the kernel benches add up to 36 ms; the whole pass takes 11 ms more. Not yet broken down (no per-part
  timing in the backend); candidates: the ~1,700 dependent dispatches (3.4 ms planned), the gated-residual and norm
  kernels the benches did not contain, and the IQ2_XXS expert kernel (not benched).
- **Finding: decode B = 3 and B = 4 below the tolerance** (30.9 and 34.7 against 30 to 56 and 33 to 61 planned
  around 43 and 47; B = 3 at the lower edge). A pass of 4 tokens takes 115 ms, 2.5× a pass of 1 (47 ms); planned
  were 85 ms. The expert mat-vecs grow linearly with B by design; the dense part grows more than in the kernel bench
  (39.9 ms at B = 4). Next step: time the parts of a pass per width.
- **Finding: prefill 40 tok/s (200 ms per pass of 8)**, inside the tolerance (35 to 65) but far below what prefill
  needs: two mat-vec dispatches of 4 tokens and 80 expert slots per layer are decode kernels, not GEMMs. A 30 k token
  prompt would take 12.5 min. The prefill path needs its own kernels (proposal to the maintainers, next step).
- **Expert count not visible:** 64, 128 and 256 experts within 1.8 % at B = 1 and B = 4 (rows 1, 5, 11, 17; 4, 6, 14,
  18), inside ±3 %. The bytes per token decide, as planned; the 128-expert file is a valid stand-in for decode.
- **Fast math:** +0.9 % and +1.3 % at B = 1 (rows 7, 15), +2.7 % at B = 4 (row 16 against 14), slightly outside the
  revised ±2 %; prefill +1.5 to +2.5 %. Bit-identity of the widths costs at most ~3 %.
- **Finding, cause open: the repeat at the end is slower**: row 19 −10 % decode and −20 % prefill against row 11,
  row 20 −6.7 % decode and −17 % prefill against row 14. Row 19 breaks the page-in rule (26.3 GB, weights read again:
  rows 17 and 18 had pulled the 128-expert file back in and pushed part of the 256-expert file out) and is invalid;
  row 20 keeps the rule and is slow anyway. A control with row 14 again after only 30 s (15:48) recovered within the
  process (decode rounds 32.4 / 34.4 / 34.6, warmup 32.7; prefill 26.4 warmup, then 37.1 / 37.3 / 38.5, still below
  40). Hypotheses: heat after ~9 min of almost continuous GPU load (pauses of 10 s against 30 s in the first set), or
  page cache churn between the two files. Not separable with these data (no temperature or clock reading without
  root). Next sets: one model file per set, 30 s pauses, and a repeat row at both ends.
- Row 17 breaks the page-in rule too (15.3 against 13.6 GB) without being slower: the rule is coarse (it counts all
  file reads of the process, also the CPU side); it caught row 19.
