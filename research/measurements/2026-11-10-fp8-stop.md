## Plan 3: teacher forcing of stored Claude Code turns (goals 1 and 2)

- **Question:** does FP8 prefill shift p(`<|im_end|>`) (id 248046) and p(`<tool_call>`) at the end of an announcement

  log p(tool_call), -log p(target) are compared between the arms (paired by position). Content of the dumps stays in
  `/var/tmp/claude/w104`, only lengths and numbers go here.
- **Scope:** 10 cases x 2 arms, one process per run, about 1.5 min each (30 min), `TONA_DETERMINISTIC=1`.
- **Expectation (unchecked):** mean dNLL over the turn about 0 (|d| < 0.01 nat, as in
  `2026-11-03-prefill-fp8-quality.md`); log p(end) after the announcement in both arms far below 0 (the turn
  continues with `<tool_call>` here); if FP8 shifts p(end) systematically, the mean over announcement positions moves

- **Active tooling:** `TONA_TEACHER_SPECIAL=1`, `TONA_TEACHER_DUMP`, `TONA_TEACHER_NLL`, `TONA_DETERMINISTIC=1`.

## Result 3 (11:03 to 11:17): teacher forcing, first 8 turns

Eight stored turns (33K to 64K tokens of prompt, 165 to 1,585 turn tokens), one run per arm and turn
(`TONA_DETERMINISTIC=1`, prefill FP8 on or off, the turn through the megakernel):

  six turns at most 0.003 in both arms. So the model itself puts 1e-1 probability on ending the turn right after
  some announcements, in the f16 arm as well; sampling at T 1 or a greedy near-tie then stops the turn.
- Summed over all turn positions (excluding the final `<|im_end|>`), the expected number of early stops is 0.29 (on)
  against 0.36 (off): no systematic increase with FP8. The mean shift of log p(end) over all positions is -0.005 nat.
  The shift per position is large and of both signs (up to 7.9 nat).

Reading (so far, 8 turns): FP8 does not move p(end) in one direction; it perturbs it like noise, and where the f16
arm already has p(end) around 0.1 after an announcement, one of the arms ends. Not yet a statement about the rate:
Plan 4 pairs 17 more turns.

## Result 7 (CPU, 13:05): how our server builds the prompt from a Claude Code request

Code read (`engine/server/api_anthropic.cpp`) and checked on 245 stored requests:
1. **Assistant message:** `[thinking, text, tool_use, ...]` becomes **one** assistant message (content, reasoning,
   tool_calls), as the Qwen template expects; no dump has consecutive assistant messages. (The llama.cpp #19513 pattern of
   separate text and tool-call messages does not occur.)
2. **Whitespace:** text blocks are not trimmed by us; none of the stored text blocks has leading or trailing
   whitespace; the template adds `\n\n` between text and `<tool_call>` itself (checked in the rendered prompt and in the
   GGUF template source). Equal to jinja2 byte for byte (Result 5).
3. **Thinking of earlier turns:** kept (`preserve_thinking` undefined = true in this template), rendered as
   `<think>\n...\n</think>\n\n` in front of the content, as the template does; equal to jinja2.
4. **Found, not covered by the jinja check:** Claude Code puts a mid-history message with role `system` ("ELI5 output
   style is active. Remember to follow the specific guidelines for this style.") **after every tool result**
   (7,068 such messages in the 245 dumps; the template forbids system messages after the start). We convert it to a
   **separate user turn**, so the prompt reads `user: <tool_response>...` then `user: ELI5 output style ...` then
   `assistant`. Two user turns in a row with a plain-text instruction after the tool response is not the format the
   model was trained on (a tool response is followed by the assistant). Whether that raises p(`<|im_end|>`) is the
   question of Plan 7. (Unchecked: whether Claude Code sends these messages in the same way to a real Anthropic endpoint.)

## Decision (coordinator, 13:20) and implementation

FP8 is not the cause (Results 1 to 6, 8); FP8 diagnostics and the fix of the FP8 scale are dropped for now (the
switches `TONA_PF_FP8_STATS`, `TONA_PF_FP8_SKIP` stay, default off, documented in `docs/use/environment.md`).
**Open point for a ticket of its own:** FP8 prefill costs +0.02 nat/token NLL on 5,355 + (25 turns) tokens
(Result 3, 4), i.e. it is slightly worse at predicting the f16 service's own turns.

Fix (variant V2): a system message after the start of the history is appended to the user or tool message before it,
joined with a blank line, in the Anthropic and the OpenAI path (`add_system_message` in `engine/server/api.cpp`);
before the first other message it stays a system message, after an assistant message it stays a user turn. Unit tests:
`engine/tests/test_api_anthropic.cpp`, `test_api_openai.cpp` (43 of 43 unit tests green in `work/build/w104cpu`).
