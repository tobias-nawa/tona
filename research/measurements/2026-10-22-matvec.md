# 2026-10-22: GPU matvec for all formats of the model file

Own measurement. Tool: `ie-gpu-matvec` (`engine/gpu/matvec.hip`), ROCm 10.1, gfx1200, DPM `auto`.
Repo state: commit of this file.

## Setup

- For each format, all tensors with the most common row length merged into one matrix, at most
  512 MiB. This keeps the Infinity Cache (32 MiB) out of the measurement. Exception: Q8_0 has only 2 MB (fits in the cache).
- x random (normal distribution), y checked against the CPU reference (dequantization bit-exact, sum in
  double). Error = |y − y_ref| / Σ|w·x| of the row, maximum over all rows.
- 5 warm-up calls, then 20 measurements of 10 calls each (hipEvent). Reported: median per call and the
  range. Three complete runs in a row, medians equal within ±2 GB/s.

## What made the difference

- **v1:** One wave per row, each lane unpacks a sub-block of 32 values. x was copied into the LDS
  per block (8 rows), i.e. 10 KB of x for about 7 KB of weights. That alone cost a factor of 5 to 7.
- **v2, generic:** x directly from memory (L1/L2). Otherwise unchanged.
- **v2, BF16:** Each lane reads 16 contiguous bytes, one wave 512 contiguous bytes.
- **v2, Q6_K:** 16 lanes per superblock, 16 values per lane with 16-bit reads, two superblocks per wave.

## Notable

- For the IQ formats the minimum is well below the median, e.g. IQ2_S 2.96 instead of 4.22 ms. This
  looks like clock changes (DPM `auto`, sclk levels 1431/2780 MHz). Repeat with a fixed clock (DPM `high`);
  this is the open item in research/README.
- The IQ formats (grid tables, sign bits) are compute-bound, not memory-bound. Next
  steps: tables in the LDS, x as int8 and `v_dot4`, several rows per wave, a custom layout in VRAM.

## Limits

- Large, merged matrices. The real tensors per layer are small at 2–60 MB; there, kernel launches
  (2.1 µs) and the tail effect at the end count. That is the megakernel question (phase 2).
- Batch 1 only (decode). Verification with 2–8 tokens needs its own kernels.
