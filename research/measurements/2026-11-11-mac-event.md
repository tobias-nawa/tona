# 2026-11-11: GPU waits on a CPU event inside a pass (MTLSharedEvent), M1 Max (#107)

Phase 0 of the Mac backend. A command buffer round trip costs ~170 µs
([2026-11-11-mac-dispatch.md](2026-11-11-mac-dispatch.md)), too much once per layer for expert misses read from the
SSD. The alternative: the GPU waits inside the command buffer (`encodeWait`) for an event the CPU signals once the
expert is read. Counterpart in the reference: `k_mega` waits inside the kernel for the CPU (AGENTS.md "GPU safety").
Speed numbers on this machine are provisional.

## Plan (written before the run)

**Scope.** Tool `bench/mac/event.swift`; minimal kernels as in the dispatch file plus a load kernel that reads a 1 GiB
buffer (~3.2 ms at 334 GB/s).

| Block | What runs | Rounds | Duration |
|---|---|---|---|
| E1 latency | one command buffer with 200 steps `encodeWait(event, i)` → tiny dispatch that writes i into a shared buffer; the CPU sets `signaledValue = i` and spins on the buffer until it reads i. Latency signal → the CPU sees the GPU's write, per step | 3 runs × 200 steps | < 1 s |
| E2a work before the wait | command buffer: load kernel (10 × 1 GiB, ~32 ms), `encodeWait`, tiny dispatch; the CPU signals 5 ms after commit, i.e. during the load. Expected: the tiny dispatch follows the load at once, total ≈ load alone | 5 | < 1 s |
| E2b another queue during the wait | queue A: `encodeWait` (CPU signals after 40 ms), then tiny; queue B at the same time: load kernel 10 × 1 GiB. Compare B's GPU time with B alone | 5 | < 1 s |
| E3 long waits | command buffer waits for a signal sent after 0.5, 2 and 8 s; record status, error and the time to completion | 1 each | ~11 s |

3 runs of E1, E2a, E2b; E3 once (it only checks for a timeout). 10 s pauses.

**Expectation.**

| Rate | Expected | Tolerance | Source |
|---|---|---|---|
| E1 signal → GPU write visible on the CPU | 30 µs | 10 to 150 | between a dispatch (2 µs) and a round trip (170 µs); event wake-up through the GPU firmware (knowledge, unchecked) |
| E2a total against load alone | + < 0.1 ms | - | the wait is satisfied before the load ends |
| E2b B's time during A's wait against B alone | ±5 % | - | a waiting queue holds no GPU cores (knowledge, unchecked) |
| E3 | completes without error at 0.5, 2 and 8 s | - | the watchdog acts on executing work, not on waits (knowledge, unchecked); a timeout error here is a finding |

**Active tooling and conditions.** `swiftc -O`, no validation, no capture. Load and power recorded before each run.
The CPU spin in E1 keeps one core busy for < 1 s per run.

## Results

Raw data: [2026-11-11-mac-event.jsonl](2026-11-11-mac-event.jsonl). Tool: `bench/mac/event.swift`.

**Conditions (12:29 to 12:30).** AC power. Load average 9.0 to 9.5 on 10 cores; background load: the two busiest
processes together 68 to 77 % CPU.

| Block | Run 1 | Run 2 | Run 3 | Expected | |
|---|---|---|---|---|---|
| E1 µs signal → GPU write visible on the CPU (median / p99 of 199; min to max) | 55.0 / 227 (34 to 336) | 55.3 / 224 (41 to 304) | 73.3 / 234 (40 to 336) | 10 to 150 (median) | inside |
| E2a GPU ms: load alone / load + wait + dispatch (median of 5) | 32.18 / 32.29 | 32.09 / 32.09 | 32.12 / 32.16 | + < 0.1 ms | inside |
| E2b GPU ms of queue B: alone / during A's wait (median of 5) | 32.20 / 32.10 | 32.20 / 32.22 | 32.61 / 32.66 | ±5 % | inside |

E3, long waits (once):

| Signal after | Completed after | Status | Error |
|---|---|---|---|
| 0.5 s | 0.510 s | completed | - |
| 2 s | 2.012 s | completed | - |
| **8 s** | 8.008 s | **error** | **`kIOGPUCommandBufferCallbackErrorTimeout`** ("Caused GPU Timeout Error") |

- **A CPU signal reaches the waiting GPU in ~55 µs (median), p99 ~230 µs.** That is a third of a command buffer round
  trip at the median, and about the same at p99. Per layer and token (48 waits) the median costs ~2.6 ms, the tail more.
- **Work encoded before the wait is not held up** (E2a), and **a waiting command buffer holds no GPU capacity**: a
  second queue runs at full speed meanwhile (E2b). So a pass can encode the hit experts of a layer before the wait
  and only the missed experts after it, and other slots or prefill can run on a second queue.
- **Finding: macOS treats a long event wait as a GPU timeout.** Between 2 s and 8 s (not narrowed down) the command
  buffer is aborted with `kIOGPUCommandBufferCallbackErrorTimeout`. Only that command buffer reported the error; the
  process ended normally. unchecked: whether the queue accepts further command buffers after the timeout (E3 was the
  last test) and whether the desktop noticed anything (nobody watched the screen). Consequence for a backend: a wait inside a pass needs
  an upper bound well below 2 s and a recovery path (the counterpart of `TONA_MEGA_YIELD_MS` in the reference), and
  a stalled SSD read must not leave a command buffer waiting. Not tested: a kernel that spins on CPU memory as
  `k_mega` does (it occupies GPU cores and the watchdog would hit executing work; left out on purpose).
