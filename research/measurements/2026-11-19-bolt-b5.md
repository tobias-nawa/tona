## Prior art

Change type: `technique` (new MoE variant for a new architecture); the shared-file generalization is a `refactor` with C1 and C3 as proof.

- [NVIDIA Nemotron 3, arXiv 2512.20856](https://arxiv.org/abs/2512.20856), status: read. LatentMoE: the token is projected from `d`
  to a latent width `l < d`, routed experts work there and the sum is projected back; per-expert weight loads and traffic fall by
  `d/l`, and expert count and top-k grow by the same factor. Adopted: exactly this structure (`ffn_latent_down`, experts in 1024,
  `ffn_latent_up`); the router and the shared expert stay on the full width. Consequence for the engine: expert slots are small (1.35
  MB at IQ2_XXS) and many (up to 496 per layer), so slot count, mailbox row width (512) and the union size (`UMAX`, 9 x 8 = 72)
  are the limits, not the width of one expert.
- llama.cpp b11822 `src/models/nemotron-h-moe.cpp` and `llama-graph.cpp` (`build_moe_ffn`), the pinned checkout: the order router on
  `cur`, shared expert on `cur`, latent down on `cur`, experts with `LLM_FFN_RELU_SQR` and no gate tensor, latent up on the weighted
  sum, `moe_out + ffn_shexp`, then the residual. Adopted as the reference semantics (the oracle already matches it to 0.0027 on the mini
  model). Not adopted: its `ffn_*_s` scale tensors (the Bolt file has none for experts).
- Expert offload with many small experts: [FineMoE / fMoE, arXiv 2502.05370](https://arxiv.org/abs/2502.05370) (EuroSys 2026;
  prefetching and caching by fine-grained "expert maps"), [HybriMoE, arXiv 2504.05897](https://arxiv.org/abs/2504.05897) (CPU computes
  cache misses, dynamic balance), [TriMoE, arXiv 2603.01058](https://arxiv.org/abs/2603.01058) (GPU, AMX CPU and near-data units by
  expert temperature). Status: read as abstracts via a web search, not tested. Transferable: per-layer prediction of the next layer's
  router for prefetch (Tona already predicts with `pred_out`; the latent path skips it while the CPU experts do not run the
  squared-ReLU form). Not adopted here: no change of the cache policy in this ticket; it is a later measured ticket once Bolt runs.

Search: tools/papers/scan.py was not run for this ticket (no scan of the coverage book); two web searches by hand ("LatentMoE Nemotron
3", "MoE expert offloading many small experts"), llama.cpp source at b11822; window 12 months; `research/papers.md` not updated. A fresh
scan is an open item before the pull request text.

### What was not checked, and open items

- N2c, a whole MoE layer against the oracle at widths 1/4/8 and a prefill chunk: needs a Bolt program (B6: `arch/nemotron_h/program.cpp`,
  kernel translation unit, registry entry). `LatentMoe::build` and `PrefillRun::moe_latent` compile and are reviewed against the
  oracle, but have not run. B6 runs this check first.
- C3 goldens: run by the maintainer on the merged tree.
- The shared prefill driver and the per-layer cache/slot code now work on tensors of any width; B6 must (a) give the Bolt kernel profile
  `max_experts = MEGA_MAX_EXPERTS_WIDE` (the router rows of 496 experts are 512 wide, the host wait copies `MaxE` floats per token),
  (b) call `LatentMoe::alloc_buffers()` before the first `build()`, (c) call `latent_check_shapes`, (d) size the prefill descriptors
  per block (`pf_` has one entry per MoE ordinal today; the Bolt prefill sequence indexes by block).
- CPU experts for the squared-ReLU form (B3's `cpu/experts*`): until they exist `cpu_mode_` is off for Bolt and misses are copied by the
  GPU; `LatentMoe::build` throws if CPU mode is on.
- The extra barrier of `moe.add` and `quant.lat` per layer is a candidate for fusion into the neighbouring steps (not measured).
