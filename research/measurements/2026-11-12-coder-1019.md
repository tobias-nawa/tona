## Question

## Expectation (with tolerance)

All numbers are unchecked unless a source is named.

- **Header (source: the ISTA allocation files of both revisions, same tensor count and types in the repo listing):**
  tensor names, shapes and types identical; the key-value block identical; only expert-related tensors differ.
- **a) Speed:** B against A within -3 to +3 % for decode and for prefill (both at 30K and 130K). Source: same shapes and
  quant types, so the same kernels and bytes per token; noise of the workloads in `bench/noise.toml` (sd 0.02 to 0.4 %).
  The wider tolerance is for the expert cache: 25 % of the experts differ (unchecked, see header result), so hit rates
  can differ. Outside this range is a finding.
- **b) NLL:** the sign cannot be predicted (the card claims better coding, the pruning mask was chosen by ISTA and is not
  ours). Tolerance for "equal in practice": |mean dNLL| below 0.05 nats on code and below 0.15 on text (new minus old,
  same tokens). Source: the pure cut DM of the requant run, 164 of 256 experts (92 removed), had delta-PPL +0.031 on
  code (about 0.02 nats) and +0.333 on text (about 0.09 nats) against the Coder, and a swap of about a quarter of the
  experts is of the same order. KLD of new against old: 0.03 to 0.2 on code, 0.1 to 0.4 on text (DM and D: 0.053 / 0.106
  code, 0.199 / 0.252 text). A decisive effect is read from the 95 % interval.
- **c) JSON:** old at least 30 of 32 (the llama.cpp server gave 32 of 32 in the requant run; on `tona-server` unchecked).
  New within 2 of old (binomial standard error near 30 of 32 is about 1.4).
- **d) Loops:** the card says loops are reduced. Expectation: old loops in 5 to 9 of 23 at `high` greedy (source: 16 of
  23 passed in the 2026-10-26 run, almost all failures were thinking until the context was full); new fewer. With
  n = 23 a difference below about 30 pp is not resolved; that outcome is reported as not resolved, not as equal.

## Results

(appended below)

### 1. Header and data compare (CPU only)

Tools: `tools/gguf_info.py` reader, own byte compare (`work/coder-1019/expert_map.py`, `alloc_overlap.py`; not committed),
allocation files of both revisions from the repo (`tensor-allocation/...rco-allocation.txt`).

- **Header identical.** Version 3, 1223 tensors, 67 key-value pairs; the bytes of the whole header (key-value block and
  tensor directory, up to the data start at offset 11,024,416) are identical. All names, shapes, quant types and
  offsets are identical. Total size equal (29,608,446,496 bytes). By type: IQ2_S 40, IQ3_S 20, IQ3_XXS 34, IQ4_NL 86,
  IQ4_XS 45, Q2_0 9, Q4_K 47, Q5_K 35, Q6_K 129, Q8_0 1, BF16 484, F32 292, F16 1, same in both.
- **Tensor data: only 192 of 1223 tensors differ**: for each of the 48 layers `ffn_gate_exps`, `ffn_up_exps`,
  `ffn_down_exps` and the router `ffn_gate_inp`. Everything else (attention, DeltaNet, embeddings, output, shared
  expert, norms, hyper-connection tensors) is byte-identical.
- **Which experts.** The model is pruned from 512 to 256 experts per layer (allocation file: "256 of 512 retained per
  layer"); the stacked tensors hold the retained experts in the order of their original index. The sets of retained
  original indices differ: per layer 170 to 221 (mean 192.2) of 256 retained experts are in both, 9,225 of 12,288 =
  **75.1 %** (a random second choice would share 128 per layer); 63.9 per layer on average, 3,063 in total, were swapped
  for others. The experts present in both are **byte-identical** (gate, up, down and router row, 9,225 of 9,225 each),
  and so are their per-expert quant types (per-tensor type unchanged). The new experts have the same quant types
  per tensor as the old ones. So the new shard is the old one with a changed pruning mask: 25 % of the experts (and
  their router rows) exchanged, nothing else touched. The key-value block and tensor directory give no hint of the
  change (the model card was updated: 2026-10-17 update note, benchmark numbers).
- Consequence for us: no loader change needed (same shapes, types, metadata). Everything that depends on expert
  identity is stale for the new shard: `work/profile/experts-coder.bin` (pinned and hot sets), the routing trace and
  the selections of the middle tier (`keep*.json`, imatrix of the old Coder), and the `coder-dm` model made from the
  old shard. The profile for the new shard (`experts-coder-1019.bin`) was made on 2026-10-23.

### 5. d) Thinking loops and task benchmark (`scripts/bench-effort.py`, 23 own Python tasks with tests)

`tona-server` with MTP, `--ctx 16384`, `MAX_TOKENS` 24000, adaptive thinking, one run per shard and level, each with its
own expert profile. `high` greedy (`SAMPLING=0`, the setup of 2026-10-26) and `medium` with the server's default
sampling. Loop = answer cut at the limit with a repetitive thinking tail (`work/coder-1019/loops.py`: tail compresses
below 20 %). Exact Fisher test for differences.

| Level | Shard | Passed | Hit the token limit / loops | Thinking tokens (median / sum) | Time |
|---|---|---|---|---|---|
| high, greedy | old | 22 / 23 | 0 / 0 | 2,804 / 143,053 | 1820 s |
| high, greedy | new | 21 / 23 | 0 / 0 | 4,622 / 157,805 | 2012 s |
| medium, default | old | 22 / 23 | 0 / 0 | 876 / 37,569 | 577 s |
| medium, default | new | 22 / 23 | 0 / 0 | 817 / 37,245 | 579 s |

- Failures: `roman` fails with both shards at `high` (wrong code, 14.2K thinking tokens, not a loop); new additionally
  fails `edit` at `high`, old fails `roman` at `medium` and new `flatten`. No pass-rate difference is detectable (p = 1.0).
- **No loops on either shard, at either level.** The setup that produced 6 loops in 8 hard tasks on 2026-10-26 (old
  shard, older engine) does not loop any more: 0 of 23 with the old shard today. So this test has no resolving power
  for "looping is reduced"; the claim of the model card is neither confirmed nor refuted here. The engine changed in
  between (unchecked which change removed the loops; the paper of 2026-11-09 on recurrent-state rounding is one
  candidate). The longest thinking is 14.2K tokens for both shards, the same task (`roman`).
- The new shard thinks more at `high` on 10 of 23 tasks (more than 1.5 times the old count; 4 tasks less than 0.67
  times), +10 % in sum, +65 % in the median; at `medium` it is equal in sum (7 tasks more, 8 less). Greedy decoding with
  thinking is a chaotic path, so per-task counts differ without meaning; the sum at `high` is the one number to watch.
- The level `max` gave exactly the same thinking tokens and results as `high` for the old shard (143,053 tokens, 22 of
  23): the engine maps both to the same thinking budget (unchecked, the run was stopped after the old arm), so it was
  not repeated for the new shard.
- Greedy runs are reproducible (the repeated old `high` run matches token for token).
- **Not run: the task benchmark of the threshold work (#76).** It needs the pinned foreign repositories (`fetch.py`,

  server `--ctx` of 69,632; none of that exists on this machine now (`work/tmp/w76` is gone), so it cannot fit the two

## Findings

1. The new shard is a drop-in: same header and tensors, only the pruning mask changed (25 % of the retained experts and their
   router rows exchanged, 3,063 of 12,288; the other 75 % byte-identical). No loader or kernel work.
2. Quality by NLL is equal on code and slightly better on prose (-0.023 nats on 32K tokens, one text); the two shards
   disagree token by token (KLD 0.16 code, 0.36 prose against the old shard), as expected for 3,063 other experts.
3. Speed is equal where it can be compared without the text effect (prefill, long-context decode). Decode at 30K
   is faster with the new shard by 8 %, cause unchecked.
4. The claims of the card (less looping, SWE-bench Verified 75.6 to 79.2) are not confirmed or refuted by anything here:
   the loop test is saturated at zero, the tool-call test at 32 of 32, the pass rates equal within one task. Our
   evidence says "not worse"; the SWE-bench numbers are the vendor's.
5. Anything that is tied to expert identity must be redone for a switch: pinned/hot-set profile (exists for the new
   shard from 2026-10-23), the decode routing trace and the selections `keep*.json` of the middle tier, the imatrix
   (made on the old shard), the DM model and the bring-up file. The requant results of 2026-11-11 are all measured
   against the old shard as reference.
6. Licence and provenance: the replaced file keeps the same name; the pin in `toolchain/models.toml` must change revision
   and sha256 (bfa3644d...) together, and `tools/get_model.py` users must re-download shard 1 (29.6 GB).
