- The heads differ at the memory path, **before** the checkpoint at the start of the last message (4,505 / 8,918). That
  checkpoint covers the second session of a project, `/compact` and a restart, but not a new project. For a new project
  only the fork helps (3,744 / 8,157), and it exists only after a second, diverging session has paid the full prefill.
- The effort line of the template sits at the very start of the prompt (before the tools): another effort level shares

- `cache_control` markers: Claude Code sets them on `system[0]`, `system[1]` and the last block of the last message, none

  message needs 4,096 computed tokens, so none is written).

## 2. The change

`max_tokens: 0` (or `max_completion_tokens: 0`) on both APIs: compute the prompt, store checkpoints, sample nothing;
class `warm` (lowest priority, starts only when nothing else runs, gives way at every slice boundary); checkpoints at the
head (16 tokens before the end of the last message's text) and at the end of the prompt, SSD only (RAM stash without
`IE_PROMPT_CACHE`); checkpoint directory 0700 and files 0600; an existing file is never overwritten. Contract in
`docs/use/environment.md`.

### 2.1 Same output as the path main takes today

A request that continues a warm-up head and a request on main that gets a checkpoint at the same token through a normal
request compute the same way (prefill of the first p-1 tokens, the last one through forward, the rest from there).
Main's way to a checkpoint at the end of a shared head is the fork: a first request `H + " Task: ..."`, then
`R = H + " Question: ..."`; the fork lands 16 tokens before the first differing token, which is the head checkpoint of the
warm-up of `H`. `IE_DETERMINISTIC=1`, greedy, 200 tokens, OpenAI API; the heads are repository sources (10K and 14K
tokens, two different file sets):

| Head | Position (fork on main = head of the warm-up) | main: pre-request, then R | w79: warm-up(H), then R | w79 again (second server start) | cold R (no cache) |
|---|---:|---|---|---|---|
| a1, 10K | 9,597 | `9592a59e5972f32e` | `9592a59e5972f32e` | `9592a59e5972f32e` | `456118c437adeec0` |
| a2, 14K | 13,978 | `01fdb2b314f0664f` | `01fdb2b314f0664f` | `01fdb2b314f0664f` | `902c3d8618d3e965` |
| b1, 10K | 9,914 | `bd3344b04dbc45a7` | `bd3344b04dbc45a7` | `bd3344b04dbc45a7` | `0c4ba52911d6fa62` |
| b2, 14K | 13,939 | `ff1164b9502f711a` | `ff1164b9502f711a` | `ff1164b9502f711a` | `a47910dcdcd19fd8` |

(SHA-256 prefix of the answer text.) Warm-up + R equals the fork path of main in all four cases, and the warm-up path is
deterministic. In all four, R computed 41 tokens after the head (reused 9,597 / 13,978 / 9,914 / 13,939 of 9,638 /
14,019 / 9,955 / 13,980). Slicing is not a factor: an unsliced warm-up (`IE_PREFILL_SLICE=1000000`) gave the same SHA as
the sliced one in an earlier run (12K head).

**Why not cold = warm:** a cache hit at p splits the prefill into [0, p) and [p, n). The chunk plan of the prefill
(`PrefillRun::choose_plan`: chunk 2,048 or layered up to 6,144, depending on n) and the single token through forward at
p change the order of float operations, so the state differs at the last digits. The same is true for every checkpoint
main writes today (an earlier run with a 12K head: after a fork checkpoint the answer equals the cold one for 13 of 885 characters, after a warm-up for 252). A cold request
cannot be reproduced by a hit unless the cut falls on a chunk boundary of the cold run, which depends on the length of
R. A fixed chunk partition would make a hit equal a cold run; it is not part of this change.

**Interrupted warm-up:** a warm-up of a 15K head interrupted after 8,193 tokens (the second slice boundary; the real
request arrived 2.5 s into the first slice) followed by R: `e71523d494634883`, reused 8,193, computed 6,926. Main has no
way to a checkpoint at a slice boundary, so there is nothing to compare with; the quality check below covers a split at
4,097 (what one slice leaves). Cold R of that head: `98280a9a933f6f54`.

## 3. Step 3 (head checkpoint at the end of the tool block for every request): decided against

Draft and decision of 2026-10-30. Cut at the end of the tool block minus 16 tokens: slim 3,240, default 7,614, subagent
2,809. Per file 263 / 324 / 257 MB; a file per tool set and effort class (none, low, xhigh), about 12-15 files and
3.5-4.5 GB for the usual tool sets; own quota of 25 % of `IE_PROMPT_CACHE_GB`, file name suffix `-h`, unused heads
evicted first; cost 55-170 ms stash and ~30 ms for the extra forward token, once per head.

Effect against today (prefill 1,550 tok/s), from the table in section 1:

| Case | Today | With the head cut |
|---|---|---|
| 1 second session | covered (4,505 / 8,918) | same |
| 2 first project ever | full (4.9 / 8.5 s) | same (writes the head) |
| 2 second new project | full (5.2 / 8.8 s), writes the fork | saves 3,240 / 7,614 tokens = 2.1 / 4.9 s |
| 2 third and later | fork 3,744 / 8,157 | 0.3 s worse (the fork is 504 / 543 tokens further) |
| 3 compact, 5 restart | covered | same |
| 4 second subagent of a type | full (3,803: 2.3 s) | 0.6 s (saves 1.7 s once per type); from the third on the fork |

Result: it saves one full head per variant (2.1-4.9 s once) and loses 0.3 s in the steady state, for a quota, a file
naming scheme, a further cut in `plan_checkpoints` and a numeric change for every request. Not built. The fork threshold
stays at 2,048 tokens; lowering it to 1,024 would create the fork at the second project instead of the third and is not
measured. A warm-up (section 2.3) covers more (up to the end of CLAUDE.md) and costs nothing for normal requests.

Variant "move the effort line behind the tool block" (own ticket, changes the prompt and needs the Δ-NLL rule and
`bench-effort`): all effort classes would share one head per tool set, 4-5 files (~1.3 GB) instead of 12-15 (-65 %), and
an effort change in a running session (`/effort`) would keep the tool block (3,256 / 7,630 tokens = 2.1 / 4.9 s of the
recomputation, e.g. out of 43 s at 64K context).
