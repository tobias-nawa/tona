# 2026-11-03: does the FP8 prefill run for a 512K prompt at ctx 1M?

## Plan (written before the run)

Question: the scale run (`2026-11-03-scale-run.md`, block c4) saw no FP8 gain at 512K and 1M (+0.0 / -0.1 % **prefill**
against FP8 off in part 1) and the same text SHAs, while 30K and 130K gained +3.8 to +4.9 %. Block h showed that FP8 is
active for a 2K prompt at ctx 1048576 (different SHA, +1.9 % **prefill**). A 2K prompt runs chunk by chunk; a 512K
prompt runs layer by layer, possibly with KV staging. The code (`engine/gpu/prefill_dense.cpp:34`) has no switch that
depends on the context or the plan, so either FP8 runs and the gain is hidden, or a path skips it.

- **Scope:** one server start per arm, `work/build/merged` (main c017316, fresh by `scripts/build-fresh.sh`), ctx
  1048576, `IE_SEQS=1`, one 512,000-token prompt from the code corpus, 50 decode tokens; arm "on" (default) then arm
  "off" (`IE_PREFILL_FP8=0`), 60 s apart. About 7 min per arm.
- **Why this size:** the effect in question appears only for long prompts that take the layer-by-layer plan; 512K is
  the shorter of the two lengths that showed it. One round each: the question is whether the text SHA changes (a
  deterministic yes/no) and whether the prefill moves by about 3 %, well above the day spread of `huge` (1,398 to 1,434
  tok/s across three days, ±1.3 %).
- **Expectation:** if FP8 runs in this plan, the SHAs differ and **prefill** on is +3 % (±1.5 %) over off, the same
  dense-time saving per token as at 30K (0.021 ms per token on a pass of 0.70 ms per token). Same SHA and a prefill
  within ±1.5 % = FP8 does not run in this plan (a finding).
- **Active tooling:** `IE_DIAG=1`, `IE_PF_DEBUG=1` (plan line: chunk, group, staging), `IE_PREFILL_FP8=0` in arm "off".

## Result

Run 1 (11:44 to 11:58, `--targets 512000:50`, the same 511,946-token prompt as `huge`; logs
`2026-11-03-fp8-huge-logs/`):

| Arm | Prefill tok/s | Prompt time | Text SHA (50 tokens) | Tokens per pass | Slots |
|---|---:|---:|---|---:|---:|
| FP8 on (default) | 1,457.7 | 351.2 s | `cb7dbf78e7e4f794` | 2.58 | 74 |
| `IE_PREFILL_FP8=0` | 1,403.6 | 364.7 s | `1992a04f0eb8a03e` | 2.78 | 74 |

Plan line in both: layer by layer, chunk 4096, group 8192, KV staging, 21 layers borrowed. FP8 runs in this plan:
**prefill** +3.85 %, inside the expectation (+3 % ±1.5 %), and the text differs.

This contradicts block c4 of the scale run: the same prompt gave 360.0 s (part 1, 83791bb, FP8 off, 72 slots) and
360.1 s (part 2, dd89748, FP8 on, 71 slots) with the same 200-token SHA `2b5e4d00485e53ae`. Checked: the part 2 binary
(`work/build/merged`, linked 09:22:45) predates the part 2 `huge` start (09:53), and the env of both starts has only
`IE_DIAG=1`, `IE_SEQS=1` (`scripts/ab_server.py:60` drops every other `IE_` variable). Not checked: the FP8 rebuild of
491bccb (started 08:23:52 in `/var/tmp/claude/fp8def/rerecord.sh`, after `just check`, under the GPU lock) and the part
1 `huge` start (about 08:24, 60 s after `mid`/`long` ended at 08:23:23) raced for the lock; which binary part 1 `huge`
loaded is not logged. Run 2 settles it.

### Run 2: the `huge` request exactly

- **Scope:** the same as run 1 with 200 decode tokens (`--targets 512000:200`, the first request of `huge`), on then
  off, about 7 min each.
- **Expectation:** if FP8 behaves as in run 1, arm "off" reproduces `2b5e4d00485e53ae` (part 1) and arm "on" gives a
  different SHA at about +3.9 % **prefill**; arm "on" giving `2b5e4d00485e53ae` would mean part 1 already ran with FP8.
- **Active tooling:** as run 1.

Result (12:00 to 12:14):

| Arm | Prefill tok/s | Prompt time | Text SHA (200 tokens) | Tokens per pass | Slots |
|---|---:|---:|---|---:|---:|
| FP8 on (default) | 1,472.7 | 347.6 s | `2b5e4d00485e53ae` | 2.69 | 75 |
| `IE_PREFILL_FP8=0` | 1,418.1 | 361.0 s | `f7f5488a6a60d401` | 2.86 | 74 |

**Prefill** +3.85 % again. Arm "on" reproduces the SHA of **both** parts of the scale run; arm "off" reproduces the
11-02 SHA (`2026-11-02-scale-run-huge.md`). So part 1 `huge` already ran with FP8: the rebuild of 491bccb took the GPU
lock before it, and its binary (FP8 on by default) was loaded. The "no FP8 gain at 512K/1M" finding of the scale run is
a comparison of FP8 against FP8, and the change of the `huge` SHAs since 11-02 (addendum of part 1) is FP8. The cause is
a coordinator error: a build of the measured build directory during a worker's measurement.

### Run 3: the 1M request without FP8

- **Question (#104):** the 1M answer of `huge` ends after 26 tokens since 11-03 (SHA `e5c950ff2fae95bc`), 200 tokens on
  11-02 (`f12ab3b48409a583`). All 11-03 runs had FP8 on (run 2), so FP8 may be the cause, not the slot count.
- **Scope:** one start, ctx 1048576, `IE_SEQS=1`, `--targets 1000000:200` (the second request of `huge`),
  `IE_PREFILL_FP8=0`; about 16 min (prefill 1M takes 884 s).
- **Expectation:** if FP8 is the cause, 200 tokens and SHA `f12ab3b48409a583` (the 11-02 answer; slots may differ, so a
  different 200-token SHA also counts as "FP8 is the cause" if it is not 26 tokens). 26 tokens with `e5c950ff2fae95bc`
  would rule FP8 out.
- **Active tooling:** `IE_DIAG=1`, `IE_PF_DEBUG=1`, `IE_PREFILL_FP8=0`.

Result (12:15 to 12:31): `IE_PREFILL_FP8=0`, 74 slots, plan layer by layer, chunk 2048, group 8192: **200 tokens**, SHA
`53cca9d9044bff02`, **prefill** 1,094.8 tok/s (912.5 s), **decode** 62.6 tok/s, 3.85 tokens per pass. Not the 11-02 SHA
(`f12ab3b48409a583`), but a full 200-token answer like 11-02. With FP8 (both parts of the scale run and the route
trace, 71 to 72 slots) the same prompt ends after 26 tokens. So the short 1M answer comes with FP8, not with the slot
count (that note in the scale run was a guess). One prompt only: whether the 26-token answer is worse is not measured
(the text is not stored); the 1M needle with FP8 stayed within its range (17/40 against 19/40 on 11-02, ±3).
**Prefill** at 1M: FP8 on 1,129.5 / 1,130.4 tok/s (scale run, other starts) against 1,094.8 off, about +3.2 % (not a
paired run).

## Conclusions

1. FP8 runs in the layer-by-layer plan with KV staging and gains the same there as at 30K and 130K: **prefill** +3.85 %
   at 512K (two paired runs), about +3 % at 1M.
2. The scale-run finding "no FP8 gain at 512K/1M" is wrong: part 1 `huge` ran on the FP8 binary (my rebuild of
   `work/build/merged` took the GPU lock between two blocks of the worker). Corrected in `2026-11-03-scale-run.md` and
   in BENCHMARKS.md.
3. The 1M answer of 26 tokens (#104) comes with FP8. Open: is the shorter answer worse? Needs the text of both answers.

## Run 4: the text of both 1M answers (#104)

- **Question:** is the 26-token answer with FP8 worse than the 200-token answer without? Runs 1 to 3 stored only SHAs.
- **Scope:** two starts on `work/build/merged` (main 15bc6be, fresh by `scripts/build-fresh.sh`), ctx 1048576,
  `IE_SEQS=1`, `--targets 1000000:200`: arm "on" (default), 60 s pause, arm "off" (`IE_PREFILL_FP8=0`). About 17 min
  per arm. The driver is the run 3 driver with the answer text written to a file
  (`/var/tmp/claude/fp8text/text1m.py`).
- **Why this size:** the short answer appears only at 1M; one answer per arm is enough because the question is what
  the two texts say, not a rate.
- **Expectation:** arm "on" gives 26 tokens and SHA `e5c950ff2fae95bc` (scale run, route trace), arm "off" 200 tokens
  and `53cca9d9044bff02` (run 3); a different SHA in either arm is a finding (slot count or nondeterminism).
  **Prefill** on 1,130 tok/s, off 1,095 tok/s, each ±1.5 %.
- **Active tooling:** `IE_DIAG=1`, `IE_PF_DEBUG=1`, `IE_PREFILL_FP8=0` in arm "off".

Result (arm "on" 17:26 to 17:41 after waiting for the lock, arm "off" 18:02 to 18:17; logs and both texts in
`2026-11-03-fp8-huge-logs/run4-*`):

| Arm | Prefill tok/s | Decode tok/s | Tokens | Text SHA | Slots |
|---|---:|---:|---:|---|---:|
| FP8 on (default) | 1,124.4 | 41.0 | 26 | `e5c950ff2fae95bc` | 74 |
| `IE_PREFILL_FP8=0` | 1,094.4 | 62.7 | 200 | `53cca9d9044bff02` | 74 |

Both SHAs as expected, both prefill rates inside ±1.5 %. Both arms had 74 slots, so the slot count is ruled out as
the cause of the short answer (checked, not only argued). The texts share the first sentence ("This is a comprehensive
C++ LLM inference engine project.") and part at the next token: with FP8 the model writes "Let me explore the structure
to understand what's being asked of me." and ends; without FP8 it writes "Here's a summary of what it does:" and a
correct summary (platform, model layers, megakernel). The prompt asks for a summary as a bullet list, so the FP8 answer
does not do the task and the f16 answer does. One prompt, one divergence point: this shows that FP8 can flip a
near-tie at 1M into a worse answer; it does not show how often. The 1M needle with FP8 (17/40 against 19/40, ±3) did
not drop outside its range.

## Field observation and experiment (#104)

In a Claude Code session on the service (ctx 262144, FP8 on, all tools and MCP: first request 84,823 tokens) the model
twice ended its turn right after announcing a tool call ("Rewriting `Json.cs` with numeric char codes:"), with no
tool call. Checked in the Claude Code transcript and the server log: stop_reason `end_turn`, output tokens = thinking
plus about 20 tokens of text, the thinking planned "One Write call" and holds no tool-call markup, so the model emitted
the end of the turn itself; the parser lost nothing. Count over all transcripts with the engine model since 2026-10-21:
turns that end with text ending in ":" were 1 of 1,061 until 2026-11-02 and 2 of 46 on 2026-11-03. Two changes are new
that day: the FP8 prefill (default since dd89748) and the full tool set (~85K instead of ~20K tokens up front). The
1M answer of run 4 shows the same pattern (announce, then end).

Experiment, decided by the maintainer: the service on this machine runs with `IE_PREFILL_FP8=0` and `IE_DUMP_DIR`
(work/ie.conf, passed through by `scripts/ie-service.sh`), so every `/v1/messages` request is stored. A stall with FP8
off points to the large prompt; a stored stall can be replayed with FP8 on and off.
