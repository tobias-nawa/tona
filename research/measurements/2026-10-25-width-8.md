k_mega<1>, <4>, <8>; splits (attention pieces, HC norm) by PNB = 4, so that passes up to 4 tokens stay bit-exact
(teacher NLL 2.190080910 as before). `--batch-check 120` with passes of 8 against single steps: 120/120
bit-exact; widths round-robin 1–8, partly rejected: top-1 170/170, deviation 0.

dn.in 4,604 → 9,066, head.out 1,679 → 3,452, gr.down 2,211 → 3,777, host.y 1,565 → 3,062, qsa.in 1,480 → 2,740.

- The rest grows with the tokens: from 8 tokens the int8 matvecs are no longer memory-bound but compute-bound

- Passes up to 4 tokens: B = 4 39.15–39.26 → 39.27–39.31 ms (+0.1), B = 1 equal. Therefore not on main yet.

Way there: dense matvecs from 5 tokens via WMMA (int8, like the GEMMs of the prefill), expert budget of the CPU per pass.

## Dense matvec alone: int8 path against f16 WMMA (`ie-wide-probe`)

Real weights with row length 2,560 (Q6_K 268 MB, Q4_K 163 MB, above the Infinity Cache), median of 20 runs.
int8 = row_q8 as in the megakernel (x in the LDS, 32 blocks × 16 waves); f16 WMMA = gemm_q of the prefill (unpacking into
the LDS, tile 64 tokens × 128 outputs).

| Format | nb | int8 µs | GB/s | f16 WMMA µs | GB/s |
|---|---:|---:|---:|---:|---:|
| Q6_K | 1 | 952 | 282 | 1,732 | 155 |
| Q6_K | 2 | 1,374 | 195 | 1,736 | 155 |
| Q6_K | 4 | 1,535 | 175 | 1,751 | 153 |
| Q6_K | 6 | 1,868 | 144 | 1,745 | 154 |
| Q6_K | 8 | 2,166 | 124 | 1,746 | 154 |
| Q4_K | 1 | 614 | 266 | 1,507 | 108 |
| Q4_K | 4 | 943 | 173 | 1,506 | 108 |
| Q4_K | 6 | 1,586 | 103 | 1,504 | 109 |
| Q4_K | 8 | 1,868 | 87 | 1,510 | 108 |

- int8 costs ~17 instructions per token and sub-block (8 dot4, x and metadata from the LDS, scales); compute-bound
  from 4 tokens.
- f16 WMMA is independent of nb but limited by unpacking (154 and 108 GB/s); better only from ~6 tokens.
- int8 WMMA with exact integer partial sums (bit-exact with row_q8) does not pay off: per sub-block and token the
  float epilogue remains (scales of weight and x), and at 8 tokens half the lanes of a 16×16 tile sit idle.
  Calculation: ~6.3 instructions per (row, sub-block) against 5.2 today.
- f16 computes differently from int8: passes from 5 tokens would have different rounding than passes up to 4. The
  repeatability with speculation would then no longer hold.

## Own WMMA kernel for few tokens (`k_wide` in `ie-wide-probe`)

One wave per 16 rows, f16 WMMA 16×16×16: B = weights, unpacked directly into registers (decode_q8, then per 4 bytes via
v_perm into the mantissa of 1024, packed −1024 and fma with scale/offset), A = x of the tokens as f16 (up to 16, unused ones
doubled), D: lane holds row l % 16 for 8 tokens. Error against gemm_q (f16) relative 3·10⁻⁴ (Q6_K) and 1·10⁻³ (Q4_K).

- First version: both lanes of a row pair unpacked the same sub-block (each used half): 140–149 and
  95–105 GB/s, i.e. exactly half the unpacking rate of the int8 path (281 GB/s at nb = 1).
- Second version: lane g unpacks sub-block sub + g, the missing halves (4 words, 4 scales) via permlanex16.

| Format | nb | int8 (row_q8) GB/s | gemm_q GB/s | k_wide GB/s |
|---|---:|---:|---:|---:|
| Q6_K | 1 | 281 | 155 | 202 |
| Q6_K | 2 | 195 | 155 | 201 |
| Q6_K | 4 | 175 | 155 | 199 |
| Q6_K | 6 | 144 | 153 | 194 |
| Q6_K | 8 | 125 | 154 | 191 |
| Q4_K | 1 | 269 | 109 | 244 |
| Q4_K | 2 | 212 | 108 | 238 |
| Q4_K | 4 | 172 | 108 | 225 |
| Q4_K | 6 | 103 | 108 | 213 |
| Q4_K | 8 | 87 | 108 | 203 |

k_wide is faster than the int8 path from 2 tokens, at 8 tokens 1.5× (Q6_K) and 2.3× (Q4_K). Since it barely depends
on nb, all widths (including 1) could run through it: the same rounding for every width, hence repeatable as today,
but B = 1 slower in the dense part (Q6_K 202 instead of 281 GB/s).

## k_wide in the megakernel (branch `breite-8`, `IE_WIDE_MIN`, `IE_WIDE_ROWS`)

`wide_loop` in run_phase: dense int8 tasks of the target model with ≥ IE_WIDE_ROWS rows (default 4,096) compute from
IE_WIDE_MIN tokens per pass via f16 WMMA (unit = 16 rows, x as float from device memory). Dependency
dn.in → dn.conv with the row layout of wide_loop. Experts stay int8 (CPU mirror).

- Bit-exact across the width with IE_WIDE_MIN = 1: passes of 8 against 1 and against 3, 120 of 120 positions equal.
- NLL teacher text 600 tokens (B = 1): int8 2.488, k_wide 2.477 (within noise).

## Server with passes up to 8 tokens (default from now on)

`scripts/bench-openai.py`, 3 requests per case, median, server with `--ctx 16384`, desktop on the GPU. Server: up to 7
drafts, calibration `DraftCalib<7>`, drafter block 8 only after a pass that accepted all drafts, otherwise 4; k_wide from
6 tokens in target and drafter. `IE_DETERMINISTIC=1`: up to 3 drafts, no k_wide (old state, bit-exact).

| Case | IE_DETERMINISTIC=1 | up to 8, calibration reset per request (default) | up to 8, calibration across requests |
|---|---:|---:|---:|
| csv | 90.4 (84.7–91.0) | 101.3 (93.8–102.4) | 104.4 (93.8–105.5) |
| rust | 77.8 | 81.3 | 80.8 |
| long, decode after 12K | 51.5 | 53.4 | 53.2 |
| explain | 58.4 | 56.5 | 56.8 |

More series (calibration across requests): csv 104.5 / 104.5, rust 80.0 / 81.0 / 80.8, explain 56.6 / 57.0 / 57.0.

- explain loses ~1.5–2 tok/s although almost no wide passes occur (4 of 240): drafter block 8 after a
  fully accepted small pass costs ~1 ms more and is mostly not used on text.
- Stricter rules for the large block (`IE_DRAFT_STAY` 4/5, `IE_DRAFT_ENTER_P` 0.5/0.7, `IE_DRAFT_BIG_AT=3`): explain
  +0.5–1, csv −3 to −6 tok/s. Rejected, the focus is code.
- Without calibration (`IE_DRAFT_CALIB=0`) explain 56.9; drafter without k_wide (`IE_WIDE_DRAFT=0`) 55.6.
- **Repeatability:** with calibration across requests the same request A gave a different answer after another one
  (`det.py`: A, B, A, B, A → three different A), because the choice of width depended on the history and passes from
  6 round differently. With calibration, probe counter and block size per request from the same state: A three times equal, B twice
  equal. Cost: csv 104.4 → 101.3, otherwise within noise. `IE_DRAFT_CALIB_KEEP=1` keeps learning across requests.
