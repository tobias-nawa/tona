# RAM and VRAM limit: who gets the RAM, and how fast is it with less memory?

2026-10-27, build engine-b45 (after 95978df, with `IE_RAM_GB`/`IE_VRAM_GB`), Coder IQ1_M, MTP drafter, context 16K, one
conversation. `scripts/bench-set.py` (11 code, 3 text prompts, greedy, decode) and `scripts/bench-openai.py … lang`
(13K tokens, prefill). Before every run the page cache of the model files was cleared (`POSIX_FADV_DONTNEED`), so that no
run benefits from the previous one.

A machine with less RAM is emulated: `systemd-run -p MemoryMax=` set to the limit. Checked: the pinned
experts count in the cgroup (`memory.stat` shmem 23.3 GB, `memory.current` at the limit), so the emulation
is honest.

## Who gets the RAM? (limit 26 GiB, like a 32 GB machine minus system)

| Split | pinned | Decode code | Decode text | Prefill |
|---|---:|---:|---:|---:|
| ¼ of the limit for saved conversations (first version of `IE_RAM_GB`) | 17.1 GB | 38.1 | 37.9 | 845 |
| 2 GB for saved conversations, rest experts | 21.7 GB | **51.2** | **51.7** | **1,207** |
| only 10 GB pinned (`IE_PIN_GB=10`) | 10.1 GB | 33.3 | 30.2 | 616 |
| nothing pinned, everything via the page cache (previous behavior on 32 GB) | 0.1 GB | 51.9 | 35.8 | 667 |

tok/s decode and prefill respectively, one run each. Pinned experts clearly outperform the page cache (text +44 %, prefill
+81 % against "nothing pinned"). The page cache alone is only as fast for code because the code prompts
run first and fill it. From this the rule in `engine/backend/budget.h`: with `IE_RAM_GB` the experts first, saved
conversations only the rest (1–12 GB), 0.5 GB of headroom for the page cache (PLE rows).

## Partial pinning at tight limits (series `IE_PIN_GB`)

Limit `MemoryMax` = `IE_RAM_GB`, pin amount fixed, page cache cleared before each run. Aborts: passes with
"barrier aborted (timeout)" (HTTP 500), run then incomplete.

| Limit | pinned | Decode code | Decode text | Prefill | Aborts |
|---|---:|---:|---:|---:|---:|
| 26 GB | 20.6 GB | 20.9 | 30.8 | 556 | 0 |
| 26 GB | 21.7 GB | – | – | 582 | 1 |
| 20 GB | 15.6 GB | – | – | – | 2 |
| 20 GB | 14.1 GB | – | – | – | 3 |
| 20 GB | 10.1 GB | – | – | 307 | 1 |
| 20 GB | 0.1 GB | 43.7 | 35.2 | 629 | 0 |

Partial pinning is the worst choice at tight limits: pins and page cache displace each other, the CPU experts
arrive via page faults from the NVMe, and every fault waits for release in the cgroup. It only ran well with
≥ 4.3 GB next to pins and fixed RAM (26 GiB = 27.9 GB, 21.7 GB pinned: 51.2), badly from 3.5 GB.

Fixed RAM of the server when pinning (`ram_held_bytes`, `IE_VRAM_LOG=1`): 1.93 GB. All experts together: 25.15 GB.

**Rule from this** (`engine/backend/budget.h`): with `IE_RAM_GB` pin all experts or none; all only if
0.5 GB of headroom, 1 GB for saved conversations and 3 GB of page cache remain beside them (from a limit of ~31.6 GB).

(29 GB: two runs.) No more aborts at any limit. Between 29 and 32 GB lies the step from 53 to

## Yield instead of abort (research/23-waiting-in-kernel)

If block 0 waits longer than `IE_MEGA_YIELD_MS` (default 100) for the CPU, all blocks end at their next
barrier, and the CPU restarts the kernel from the waiting step as soon as it is done. Test case: the worst one
from above, 26 GB limit with 21.7 GB pinned, page cache cleared.

| Version | Runs | Yields | Aborts | Decode code | Decode text | Prefill | Decode after 13K |
|---|---:|---:|---:|---:|---:|---:|---:|
| without yield (`IE_MEGA_YIELD_MS=0`) | 1 | 0 | 1 | – | – | 675 | 26.7 |
| yield after 100 ms or at the deadline | 2 | 1 / 1 | 1 / 1 | – | – | 679 / 585 | 29.6 / 28.3 |
| yield after 100 ms or 50 ms before the deadline | 2 | 5 / 4 | **0 / 0** | 16.5 / 15.8 | 29.0 / 29.4 | 640 / 647 | 23.2 / 29.2 |

The remaining abort of the first version: in prefill each of the 48 layers waits briefly for the CPU; individually under
100 ms, together over the deadline of the pass (1.5 s). At the deadline the barriers of the other blocks expired at the same time
(they wait for block 0) and counted an abort. A 50 ms head start for the yield fixes that.

This case stays slow nonetheless (the page cache overflows); the yield only makes it safe. No GPU reset,
no entry in the kernel log.

## Pin only the experts outside VRAM?

Idea: the 83–84 most frequent experts per layer sit in VRAM anyway; pin only the remaining 172 (16.9 instead of
25.2 GB), then it fits from ~26 GB. `IE_PIN_GB=16.9` (pin_experts then takes exactly the ranks from the VRAM slots on).

| Limit | pinned | Decode code | Decode text | Prefill | Decode after 13K | Yields | Aborts |
|---|---:|---:|---:|---:|---:|---:|---:|
| 26 GB | 17.0 GB | 29.4 / 31.0 | 29.8 / 30.1 | 631 / 639 | 33.4 / 32.5 | 1 / 5 | 0 |
| 23 GB | 17.0 GB | 7.1 | 10.1 | 355 | 10.9 | 87 | 0 |

Worse than pinning nothing (26 GB: 50.3 decode code). The VRAM cache is not fixed: evicted frequent
experts have to come back from the page cache, and that is too small next to 17 GB of pins. Rejected; it stays at "all or
none". The yield also withstands 87 long wait points without an abort.

## Slower drives (emulated)

`systemd-run -p IOReadBandwidthMax=` (and `IOReadIOPSMax=`) on `/dev/dm-0`. systemd sets the limit on the NVMe device
underneath (259:0); through dm-crypt roughly 2.2 times as much arrives. Calibrated with the installer's drive measurement
(`ie-install --print` in the same scope): 250M → 552 MB/s sequential, 132K random 4 KiB reads/s (like a
SATA SSD); 80M + 150 IOPS → 87 MB/s, ~200/s (like a hard disk). Without a limit: 2,653 MB/s, 457K/s. Page cache cleared before
every run.

| Drive | Limit | pinned | Start | Decode code | Decode text | Prefill | Decode after 13K | Yields | Aborts |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|
| SATA | 26 GB | 0.1 GB | 34.0 s | 43.5 | 36.1 | 734 | 33.9 | 61 | 0 |
| SATA | 58 GB | 25.3 GB | 61.5 s | 88.9 | 64.4 | 1,700 | 62.7 | 0 | 0 |
| HDD | 26 GB | 0.1 GB | 443.7 s | 120 tokens not in 20 min (< 0.1 tok/s) | | | | | 0 |
| HDD | 58 GB | 25.3 GB | 820.8 s | 120 tokens including prefill in 11.7 s | | | | 0 | 0 |
| NVMe (above) | 26 GB | 0.1 GB | 10.5 s | 50.3 | 35.9 | 659 | 34.3 | – | 0 |
| NVMe (above) | 32 GB | 25.3 GB | 22.9 s | 89.2 | 64.6 | 1,741 | 62.9 | 0 | 0 |

With all experts pinned the drive only matters for the start. Without pins SATA costs ~13 % decode code; a
hard disk is unusable without pins. From this in the installer (`installer/modules/hip_gfx1200.cpp`): below a ~32 GB limit
and below 300 MB/s the error "drive too slow", above that only a note about the long start; start time and penalty from
these points (logarithmic in MB/s).
