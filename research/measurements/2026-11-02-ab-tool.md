# A/B measurement tool with a statistical stop (#88)

## Plan (written before the runs)

Question: does `scripts/ab.py` stop early on a clear effect, call identical builds "equal", stay honest on noise, and
how much time does it save against a fixed 3 rounds?

Scope: `work/build/merged` (main e3660c0) on the GPU, `--ctx 140000`, MTP, workload `server` at 30000 and 130000
tokens (200 tokens each), corpus from commit e3660c0 (`scripts/make_corpus.py`), `MemoryMax=54G`, port 8097. Three
blocks, at least 60 s apart, under the GPU lock:

1. **A/A**: `merged` against `merged`, defaults (2 to 6 rounds). About 8 min per round (two server starts of about
   90 s, 30K and 130K prefill about 100 s, decode, estimate printed by the tool), 16 to 48 min.
2. **Known effect**: `merged` against `merged` with `OMP_NUM_THREADS=3` in B. Same cost per round, 16 to 48 min.
3. **Bit-exact**: `--env IE_DETERMINISTIC=1`, `merged` against `merged`, 2 rounds, to record the reference SHAs of the
   new corpus (the old corpus was a mix of other projects and cannot be rebuilt, so the old SHAs 065922c2ff602991 and
   439aad472c59ae6f do not apply). About 16 min.

Expectation (B against A in percent):

| Block | Metric | Expected | Source |
|---|---|---|---|
| A/A | Decode tok/s, Prefill tok/s at both lengths | -1 to +1 % | spread of earlier repeated runs: decode 130K 63.3-64.2 tok/s (+-0.7 %), prefill 1806 and 1712 tok/s equal in both arms (BENCHMARKS.md, 2026-11-01 rows) |
| A/A | decision | "equal" at the latest at round 6, not "faster"/"slower" | alpha 0.05 (false call in at most 5 % of A/A runs) |
| OMP 3 | Decode tok/s | -30 to -2 % | no earlier measurement; the CPU experts and the host side of the megakernel use the threads, the size of the effect is a guess |
| OMP 3 | Prefill tok/s | -30 to +1 % | same; the prefill may not depend on the threads |
| OMP 3 | decision | decode "B slower" after 2 to 3 rounds | |
| bit-exact | SHA | equal in both arms and over both rounds | deterministic mode (rule 3) |

Active tooling: none of the engine diagnostics. Environment of every server: `OMP_NUM_THREADS=6`,
`ROCR_VISIBLE_DEVICES=0`, `IE_EXPERT_PROFILE=work/profile/experts-coder.bin`; block 2 B: `OMP_NUM_THREADS=3`; block 3:
`IE_DETERMINISTIC=1` on both. The tool prints its own plan block with the build commits before each run (files
`work/ab/*-plan.md`).

## Plan 2 (written after the first three runs, before the second ones)

The first runs (results below) showed two things: (1) round 1 favors B in every block (A starts cold: +0.7 % prefill,
+1.0 to +2.7 % decode in round 1, then 0.0 to +0.3 %), and (2) metrics that cannot be decided (prefill in the OMP
block, where nothing is expected) keep the run going to round 6, so there was no time gain. Changes in the tool:
a discarded warm-up start of A before round 1 (`--no-warmup` switches it off) and `--primary` (only these metrics
decide when to stop; the others are measured and reported). The same three blocks run again, each about 2 min longer
for the warm-up start; the first runs stay in this file.

| Block | Metric | Expected | Source |
|---|---|---|---|
| A/A | all four rates | -1 to +1 %; **prefill** "equal" (round-to-round spread 0.03 % without round 1), **decode** probably still "open" (spread 0.3 to 0.4 % against a margin of 0.5 %) | first A/A run, rounds 2 to 6 |
| OMP 3, `--primary decode` | Decode tok/s | -8 to -4 %, decision "B slower" after round 2, run ends after round 2 (about 10 min with the warm-up) | first OMP run: -6.5 % / -5.8 % |

| bit-exact | rates | -1 to +1 %; SHA equal | as before |

Active tooling: as in the first plan.

## Plan 3 (before the OMP rerun, after adding the noise table)

Second A/A run (with warm-up) is in: no round-1 bias any more (round 1: +0.05 / -0.19 / -0.00 / -0.14 %), prefill
"equal" after round 6 at both lengths, decode open, all as planned in plan 2. Since then `ab.py` gained
`bench/noise.toml` (known noise from the two A/A runs, df 9), `--why-size` (mandatory) and `--decode-tokens`. The
rerun of the OMP block with the new tool is the only further GPU run (the bit-exact block is not repeated: its
SHAs are already recorded, its rates only show the missing warm-up).

- Scope: `merged` against `merged` with `OMP_NUM_THREADS=3` in B, `--primary decode`, workload server 30K/130K,

  ends after 1 round; Prefill tok/s -1 to +1 %.
- Tooling: as before (`OMP_NUM_THREADS=6`, B `3`).

### Replay of the stop rule with the noise table on the runs above (no GPU)

Noise table from the two A/A runs (df 9), decisions by round (`ab_report.decide`): run 4 (with warm-up) decides prefill
30K / 130K after round 1 ("equal"), decode 30K after round 3 ("equal"), decode 130K stays open: 3 rounds instead of 6.
Runs 1 to 3 (no warm-up) would call "B faster" after round 1 in the A/A and the deterministic run: the table only
knows random noise, not the cold first start. Therefore `--no-warmup` switches the table off.

  the first prefill of this server, not the tool). For `ctx` this means: the prefill at `--ctx 262144` needs more
  rounds or a throw-away request before; the decode rates and the 140000 values are stable (sd 0.2 to 0.3 %).
